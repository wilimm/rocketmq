# RocketMQ 技术架构分析 - 核心概念篇

> 本篇深入介绍 RocketMQ 的核心概念、消息标识体系、队列类型和领域模型，是理解 RocketMQ 底层原理的基础。

---

## 一、核心概念

### 1.1 基本概念总览

| 概念 | 说明 | 关键属性（源码字段） |
| --- | --- | --- |
| **Topic** | 消息主题，消息的第一级分类 | `topicName`, `readQueueNums`, `writeQueueNums`, `perm` |
| **Queue** | Topic 的分区，消息存储和消费的实际单元 | `topic`, `brokerName`, `queueId` |
| **Message** | 消息传递的基本单元 | `topic`, `body`, `properties`, `transactionId` |
| **Producer** | 消息生产者，无状态可水平扩展 | `producerGroup`, `sendMsgTimeout`, `retryTimesWhenSendFailed` |
| **Consumer** | 消息消费者，支持 Push/Pull 模式 | `consumerGroup`, `messageModel` |
| **ConsumerGroup** | 消费者组，组内消费者共同消费实现负载均衡 | 负载均衡、消费进度共享 |
| **Broker** | 消息服务器，支持 Master-Slave 架构 | `brokerName`, `brokerId`, `brokerRole` |
| **NameServer** | 路由注册中心 | 无状态、心跳检测、路由映射 |
| **Offset** | 消费位点，记录消费进度 | 值等于下一条待消费消息的 `queueOffset` |

### 1.2 偏移量术语详解

RocketMQ 中有多个与"偏移量/位点"相关的术语，容易混淆：

> **示例场景**：队列中有 5 条消息 (Msg1~Msg5)，消费者已消费到 Msg3，下次将从 Msg4 开始消费。

| 术语 | 含义 | 所属层级 | 使用场景 | 示例值 |
| --- | --- | --- | --- | --- |
| **消息偏移量 (Queue Offset)** | 消息在队列中的逻辑序号，从 0 开始 | Broker 端 | 消息定位、消费进度记录 | Msg3 的偏移量为 2 |
| **消费位点 (Consumer Offset)** | 下次要消费的位置 | 消费者端 | 断点续传、消息回溯 | 消费位点 = 3 |
| **最小偏移量 (MinOffset)** | 队列中最早消息的偏移量 | Broker 端 | 消息过期清理边界 | MinOffset = 0 |
| **最大偏移量 (MaxOffset)** | 队列中最新消息的偏移量 | Broker 端 | 堆积量计算 | MaxOffset = 4 |
| **CommitLog 偏移量** | 消息在 CommitLog 中的物理字节位置 | Broker 端 | 消息实体读取 | Msg3 物理位置 = 200 字节 |

**偏移量关系图**：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│  CommitLog（物理存储）                                                       │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐                       │
│  │  Msg1   │  Msg2   │  Msg3   │  Msg4   │  Msg5   │                       │
│  │ phyOff=0│phyOff=100│phyOff=200│phyOff=300│phyOff=400│                    │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘                       │
│       ↑                                           ↑                         │
│  CommitLog Offset=0                         CommitLog Offset=400            │
│                                                                             │
│  ConsumeQueue（逻辑索引）                                                    │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐                       │
│  │ Entry1  │ Entry2  │ Entry3  │ Entry4  │ Entry5  │                       │
│  │ qOff=0  │ qOff=1  │ qOff=2  │ qOff=3  │ qOff=4  │                       │
│  │phyOff=0 │phyOff=100│phyOff=200│phyOff=300│phyOff=400│                    │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘                       │
│       ↑                  ↑            ↑           ↑                         │
│  MinOffset=0        Queue Offset=2  消费位点=3  MaxOffset=4                  │
│                                                                             │
│  关系：消费位点 = 下一条待消费消息的队列偏移量 = 3                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**关系总结**：`消费位点 = 下一条待消费消息的队列偏移量`

## 二、消息标识体系

RocketMQ 消息有多种标识和属性，理解它们的区别至关重要。

### 2.1 标识概念总览

| 概念 | 设置方式 | 存储位置 | 主要用途 | 索引支持 |
| --- | --- | --- | --- | --- |
| **Tags** | `setTags()` | properties | 消息过滤 | ✅ ConsumeQueue |
| **Keys** | `setKeys()` | properties | 消息查询、追踪、幂等 | ✅ IndexFile |
| **MsgId/UNIQ_KEY** | 系统自动 | properties | 唯一标识 | ✅ IndexFile |
| **Sharding Key** | `putUserProperty()` | properties | 顺序消息路由 | ❌ |
| **路由参数** | `send(msg, selector, arg)` | 不存储 | 队列选择 | ❌ |

### 2.2 Tags（标签）

Tags 用于**消息过滤**，同一 Topic 下区分不同业务类型：

```java
// 生产者设置 Tag
Message msg = new Message("TopicTest", "TagA", "OrderID123", body);

// 消费者按 Tag 订阅（支持多个 Tag，用 || 分隔）
consumer.subscribe("TopicTest", "TagA || TagB || TagC");
```

**Tags 特点**：
- 一个消息**只能有一个 Tag**
- Tag 存储在 ConsumeQueue 的 8 字节 hashcode 中，Broker 端高效过滤
- 适用于同一 Topic 下区分不同业务类型的消息

**典型场景**：
- 订单消息：`Tag_OrderCreate`、`Tag_OrderPay`、`Tag_OrderCancel`
- 用户消息：`Tag_UserRegister`、`Tag_UserLogin`

**注意事项**：
- Tag 存储为 8 字节 hashcode，存在**哈希冲突**可能，极端情况下过滤可能不准确
- Tag 过长不影响存储，但建议保持简短便于阅读

#### 2.2.1 SQL92 属性过滤

除了 Tag 过滤，RocketMQ 还支持 **SQL92 表达式过滤**，可以基于消息属性进行更灵活的过滤：

```java
// 生产者设置消息属性
Message msg = new Message("TopicTest", "TagA", body);
msg.putUserProperty("orderStatus", "PAID");
msg.putUserProperty("amount", "1000");
msg.putUserProperty("region", "BJ");

// 消费者使用 SQL92 表达式订阅
consumer.subscribe("TopicTest", 
    MessageSelector.bySql("orderStatus = 'PAID' AND amount > 500"));
```

**SQL92 过滤语法** ([ExpressionType.java](file:///d:/work/github/rocketmq/common/src/main/java/org/apache/rocketmq/common/filter/ExpressionType.java))：

| 语法元素 | 说明 | 示例 |
| --- | --- | --- |
| **比较运算符** | `>`, `>=`, `<`, `<=`, `=` | `amount > 100` |
| **逻辑运算符** | `AND`, `OR`, `NOT` | `a > 10 AND b = 'test'` |
| **BETWEEN** | 范围查询 | `amount BETWEEN 100 AND 500` |
| **IN** | 集合匹配 | `region IN ('BJ', 'SH', 'GZ')` |
| **IS NULL / IS NOT NULL** | 空值判断 | `orderId IS NOT NULL` |
| **TRUE / FALSE** | 布尔值判断 | `isVip = TRUE` |

**数据类型支持**：

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| Boolean | 布尔值 | `TRUE`, `FALSE` |
| String | 字符串（单引号） | `'abc'` |
| Decimal | 整数 | `123` |
| Float | 浮点数 | `3.1415` |

**Tag 过滤 vs SQL92 过滤对比**：

| 对比项 | Tag 过滤 | SQL92 过滤 |
| --- | --- | --- |
| **表达式类型** | `ExpressionType.TAG` | `ExpressionType.SQL92` |
| **过滤依据** | 消息 Tag | 消息用户属性 |
| **语法复杂度** | 简单（`TagA \|\| TagB`） | 复杂（支持 SQL92 语法） |
| **性能** | 高（ConsumeQueue 中直接过滤） | 较低（需读取消息属性） |
| **适用场景** | 简单分类过滤 | 多维度属性过滤 |

**注意事项**：
- SQL92 过滤需要 Broker 开启 `enablePropertyFilter=true`
- 属性名区分大小写
- 只有通过 `putUserProperty()` 设置的属性才能参与过滤

### 2.3 Keys（业务 Key）

Keys 用于**消息查询、追踪、幂等**，不参与消费过滤：

```java
// 设置单个 Key
message.setKeys("OrderID123");

// 设置多个 Key（空格分隔）
message.setKeys("OrderID123 UserID456 ProductID789");
```

**Keys 使用场景**：

| 场景 | 说明 |
| --- | --- |
| **消息查询** | 通过 `topic + key` 在 IndexFile 中检索消息 |
| **链路追踪** | 在 TraceBean 中记录，用于消息轨迹追踪 |
| **事务关联** | 事务消息场景下关联业务流水 |

**Keys vs Body 存储业务 ID 对比**：

| 对比项 | Keys（消息属性） | Body（消息体） |
| --- | --- | --- |
| **存储位置** | IndexFile 索引文件 | CommitLog 消息体 |
| **查询方式** | `mqadmin queryMsgByKey` 直接查询 | 需消费后反序列化 |
| **获取成本** | 无需反序列化 | 需反序列化消息体 |
| **运维可见性** | ✅ 可通过命令行工具查询 | ❌ 无法直接查看 |

**推荐做法**：两者结合使用，Keys 用于消息追踪和运维查询，Body 中包含业务 ID 用于消费端幂等判断。

**注意事项**：
- Keys 过多会增加 IndexFile 索引条目，影响索引文件大小和查询性能
- 建议每条消息设置 1-3 个 Key，避免过多

### 2.4 MsgId / UNIQ_KEY（唯一消息标识）

MsgId 是系统自动生成的消息唯一标识，存储在 properties 中：

```java
// 格式：IP(4B/16B) + PID(2B) + ClassLoader Hash(4B) + 时间差(4B) + 序列号(2B)
// IPv4 场景：4 + 2 + 4 + 4 + 2 = 16字节（32位十六进制字符）
// IPv6 场景：16 + 2 + 4 + 4 + 2 = 28字节（56位十六进制字符）
// 示例（IPv4）：AC1100012A9F00000010000000000001
```

**MsgId 结构解析（IPv4 场景）**：

```plain
MsgId: AC1100012A9F00000010000000000001
       ├──────┤├──┤├──────┤├──────┤├────┤
         IP    PID 类加载器  时间差   自增序列
        4B     2B   哈希4B   4B       2B

AC110001 = 172.17.0.1 (客户端 IP 地址的十六进制)
2A9F = 进程ID (PID)
00000010 = 类加载器哈希
00000000 = 时间差 (与本月1日0点的时间差)
0001 = 自增序列
```

**MsgId 生成源码** ([MessageClientIDSetter.java](file:///d:/work/github/rocketmq/common/src/main/java/org/apache/rocketmq/common/message/MessageClientIDSetter.java))：

```java
public static String createUniqID() {
    char[] sb = new char[LEN * 2];
    System.arraycopy(FIX_STRING, 0, sb, 0, FIX_STRING.length);
    
    long current = System.currentTimeMillis();
    if (current >= nextStartTime) {
        setStartTime(current);  // 跨月时重置起始时间
    }
    int diff = (int)(current - startTime);  // 与本月1日0点的时间差
    if (diff < 0 && diff > -1000_000) {
        diff = 0;  // NTP 时间校准处理，防止时钟回拨导致负值
    }
    
    int pos = FIX_STRING.length;
    UtilAll.writeInt(sb, pos, diff);        // 时间差 (4字节)
    pos += 8;
    UtilAll.writeShort(sb, pos, COUNTER.getAndIncrement());  // 自增序列 (2字节)
    return new String(sb);
}
```

### 2.5 Sharding Key（分片键）

Sharding Key 用于**顺序消息队列路由**，相同 Sharding Key 的消息会路由到同一队列，保证顺序。

#### 2.5.1 设置方式

| 方式 | 适用场景 | 示例 |
| --- | --- | --- |
| `putUserProperty(SHARDING_KEY)` | 5.x 新版 API、Proxy 模式 | `msg.putUserProperty(MessageConst.PROPERTY_SHARDING_KEY, "ORDER_12345")` |
| `MessageQueueSelector` | 4.x 传统方式、Remoting 模式 | `producer.send(msg, new SelectMessageQueueByHash(), orderId)` |

> ⚠️ **重要区别**：`MessageQueueSelector` 的分片键参数**不会存入消息 properties**，仅用于客户端计算队列选择。如需存储分片键用于查询追踪，需额外调用 `msg.setKeys()` 或 `msg.putUserProperty()`。

> 详细的顺序消息实现原理和代码示例见 [高级特性篇 - 顺序消息](./06-高级特性篇.md#一顺序消息)。

#### 2.5.2 Keys vs Sharding Key 区别

| 特性 | Keys | Sharding Key |
| --- | --- | --- |
| **主要用途** | 消息查询、追踪、幂等 | 顺序消息路由 |
| **存储位置** | IndexFile（支持按 Key 查询） | 消息 properties |
| **参与路由** | ❌ 不参与 | ✅ 参与 |
| **设置方式** | `msg.setKeys("OrderID123")` | `msg.putUserProperty(SHARDING_KEY, "...")` |

**两种分片键方式对比**：

| 特性 | MessageQueueSelector (4.x) | PROPERTY_SHARDING_KEY (5.x) |
| --- | --- | --- |
| **分片键存储** | ❌ 不存储 | ✅ 存入 properties |
| **队列选择位置** | 客户端 | Broker/Proxy |
| **适用模式** | Remoting 模式 | Proxy 模式、gRPC 模式 |
| **可查询追踪** | ❌ 需额外设置 Keys | ✅ 已存储 |

**顺序消息必须指定分片键**：

| 场景 | 是否需要指定分片键 | 说明 |
| --- | --- | --- |
| 普通消息 | ❌ 不需要 | 自动轮询路由到各队列 |
| 顺序消息 | ✅ 必须指定 | 相同 Key 路由到同一队列 |
| Keys 设置 | 可选 | 仅用于查询/追踪，不影响路由 |

**不指定分片键的后果**：

| 发送方式 | 队列选择 | 顺序性 | 说明 |
| --- | --- | --- | --- |
| `send(msg)` | 轮询（Round-Robin） | ❌ 无法保证 | 消息分散到各队列，并行消费 |
| `send(msg, selector, key)` | Hash(key) % 队列数 | ✅ 保证 | 相同 Key 进入同一队列，串行消费 |

```plain
订单 Order_001 的消息（不指定分片键）：
├── Msg1 → Queue0 (轮询)
├── Msg2 → Queue1 (轮询)
└── Msg3 → Queue2 (轮询)
结果：消息分散到不同队列，可能被不同消费者并行消费，顺序无法保证

订单 Order_001 的消息（指定分片键 "Order_001"）：
├── Msg1 → Queue2 (Hash("Order_001") % 4 = 2)
├── Msg2 → Queue2 (Hash("Order_001") % 4 = 2)
└── Msg3 → Queue2 (Hash("Order_001") % 4 = 2)
结果：所有消息进入同一队列，单线程串行消费，顺序得到保证
```

## 三、队列类型

### 3.1 业务队列类型

RocketMQ 有 **3 种业务队列类型**：

| 队列类型 | Topic 格式 | 用途 | 特点 |
| --- | --- | --- | --- |
| **普通队列** | 用户定义的 Topic | 业务消息存储 | 用户创建的业务 Topic |
| **重试队列** | `%RETRY%` + ConsumerGroup | 消费失败消息重试 | 自动创建，使用延迟消息机制 |
| **死信队列** | `%DLQ%` + ConsumerGroup | 存储无法消费的消息 | 永久存储，需人工处理 |

### 3.2 系统内部队列

| 队列类型 | Topic 格式 | 用途 | 特点 |
| --- | --- | --- | --- |
| **延迟队列** | `SCHEDULE_TOPIC_XXXX` | 延迟消息中转存储 | 18 个队列对应 18 个延迟级别 |

> 延迟级别详细说明见 [高级特性篇 - 延迟消息](./06-高级特性篇.md#三延迟消息)。

### 3.3 队列流转关系

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                     场景一：普通延迟消息流转                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│  Producer                          SCHEDULE_TOPIC_XXXX         Consumer     │
│  ┌──────────┐                      ┌──────────────┐          ┌──────────┐  │
│  │发送延迟  │   Topic替换          │  延迟队列    │  到期    │ 订阅     │  │
│  │消息      │ ──────────────────► │              │ ───────► │ OrderTopic│  │
│  │delayLevel│                      │  按级别分队列 │ 恢复Topic│          │  │
│  └──────────┘                      └──────────────┘          └──────────┘  │
│                                                                             │
│  流程：业务Topic → SCHEDULE_TOPIC_XXXX → 到期恢复业务Topic → Consumer消费   │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│                     场景二：消费失败重试流转                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│  普通队列              SCHEDULE_TOPIC_XXXX        重试队列         死信队列  │
│  ┌──────────┐          ┌──────────────┐        ┌──────────────┐ ┌────────┐ │
│  │OrderTopic│ 消费失败 │  延迟队列    │        │%RETRY%+Group │ │%DLQ%+  │ │
│  │          │ ───────► │              │ ──────►│              │ │Group   │ │
│  └──────────┘          └──────────────┘        └──────────────┘ └────────┘ │
│       ▲                      ▲                       │            ▲        │
│       │                      │                       │ 重试超限   │        │
│       │        ┌─────────────┴─────────────┐         └────────────┘        │
│       │        │ Consumer 订阅重试队列      │                               │
│       └────────┴───────────────────────────┘                               │
│                                                                             │
│  流程：消费失败 → SCHEDULE_TOPIC_XXXX → %RETRY%+Group → Consumer重新消费   │
│        重试超限（默认16次）→ %DLQ%+Group（死信队列）                        │
└─────────────────────────────────────────────────────────────────────────────┘
```

**两种场景对比**：

| 对比项 | 普通延迟消息 | 重试消息 |
| --- | --- | --- |
| 触发方式 | Producer 主动设置 delayLevel | Consumer 消费失败自动触发 |
| 延迟后目标 | 原始业务 Topic | 重试队列 `%RETRY%+Group` |
| Consumer 订阅 | 业务 Topic | 业务 Topic + 重试队列 |
| 延迟级别 | 1-18 均可 | 固定从级别 4 开始递增 |
| 是否进入死信队列 | 否 | 重试超限后进入 |

> 重试延迟级别详细说明见 [消息消费篇 - 消费失败处理](./05-消息消费篇.md#七消费失败处理)，死信队列详细说明见 [高级特性篇 - 死信队列](./06-高级特性篇.md#五死信队列)。

##### 4.1.2.1 commitLogOffset 跨文件定位机制

`commitLogOffset` 是**全局物理偏移量**，在整个 CommitLog 目录中唯一。CommitLog 由多个固定大小的 `MappedFile` 组成，通过以下机制定位：

**定位流程**：

```plain
CommitLog 目录结构：
┌─────────────────────────────────────────────────────────────────┐
│  00000000000000000000.mappedfile  (0 ~ 1GB)                     │
│  00000000001073741824.mappedfile  (1GB ~ 2GB)                   │
│  00000000002147483648.mappedfile  (2GB ~ 3GB)                   │
└─────────────────────────────────────────────────────────────────┘

commitLogOffset = 1,500,000,000 (约1.5GB)
                    │
                    ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: 找到对应的 MappedFile                                   │
│  index = 1,500,000,000 / 1,073,741,824 = 1                      │
│  → mappedFiles[1] = 00000000001073741824.mappedfile             │
├─────────────────────────────────────────────────────────────────┤
│  Step 2: 计算文件内位置                                          │
│  pos = 1,500,000,000 % 1,073,741,824 = 426,258,176              │
│  → 从该文件的第 426,258,176 字节处读取消息                        │
└─────────────────────────────────────────────────────────────────┘
```

**核心源码** ([MappedFileQueue.java](file:///d:/work/github/rocketmq/store/src/main/java/org/apache/rocketmq/store/MappedFileQueue.java))：

```java
public MappedFile findMappedFileByOffset(final long offset, final boolean returnFirstOnNotFound) {
    MappedFile firstMappedFile = this.getFirstMappedFile();
    MappedFile lastMappedFile = this.getLastMappedFile();
    
    // 计算文件索引
    int index = (int) ((offset / this.mappedFileSize) 
                     - (firstMappedFile.getFileFromOffset() / this.mappedFileSize));
    MappedFile targetFile = this.mappedFiles.get(index);
    
    // 验证偏移量在该文件范围内
    if (offset >= targetFile.getFileFromOffset()
        && offset < targetFile.getFileFromOffset() + this.mappedFileSize) {
        return targetFile;
    }
    // ...
}
```

**CommitLog 读取消息** ([CommitLog.java](file:///d:/work/github/rocketmq/store/src/main/java/org/apache/rocketmq/store/CommitLog.java))：

```java
public SelectMappedBufferResult getMessage(final long offset, final int size) {
    int mappedFileSize = this.defaultMessageStore.getMessageStoreConfig().getMappedFileSizeCommitLog();
    MappedFile mappedFile = this.mappedFileQueue.findMappedFileByOffset(offset, offset == 0);
    if (mappedFile != null) {
        int pos = (int) (offset % mappedFileSize);  // 取模得到文件内位置
        return mappedFile.selectMappedBuffer(pos, size);
    }
    return null;
}
```

**关键概念**：

| 概念 | 说明 |
| --- | --- |
| **commitLogOffset** | 全局物理偏移量，在整个 Broker 中唯一 |
| **mappedFileSize** | 单个 MappedFile 大小，默认 1GB |
| **fileFromOffset** | 文件名，表示该文件的起始偏移量 |
| **定位公式** | `文件索引 = offset / mappedFileSize`，`文件内位置 = offset % mappedFileSize` |

这种设计使得消息定位非常高效，时间复杂度为 O(1)。

##### 4.1.2.2 storeSize 与消息读取

`getMessage(offset, size)` 中的 `size` 参数就是 `MessageExt.storeSize`，即消息在 CommitLog 中的完整字节数。数据流向如下：

| 来源 | 字段名 | 说明 |
| --- | --- | --- |
| CommitLog 消息头 | TOTALSIZE | 消息存储时的第一个字段，记录消息总字节数 |
| MessageExt | storeSize | 解码后保存的值，与 TOTALSIZE 相同 |
| ConsumeQueue 条目 | size (4字节) | 索引中记录的值，与 storeSize 相同 |
| getMessage 参数 | size | 读取时传入的值，与 storeSize 相同 |

读取消息时，先从 ConsumeQueue 获取 `offsetPy` 和 `sizePy`，然后调用 `commitLog.getMessage(offsetPy, sizePy)`：

```java
// DefaultMessageStore.java
CqUnit cqUnit = bufferConsumeQueue.next();
long offsetPy = cqUnit.getPos();    // CommitLog 物理偏移量
int sizePy = cqUnit.getSize();       // 消息大小 (即 storeSize)

SelectMappedBufferResult selectResult = this.commitLog.getMessage(offsetPy, sizePy);
```

| 问题 | 答案 |

}

**MessageQueue vs ProcessQueue 对比**：

| 属性 | MessageQueue | ProcessQueue |
| --- | --- | --- |

**逻辑队列映射原理**：

```plain
逻辑队列 (固定ID)          物理队列 (实际存储)
┌─────────────┐           ┌──────────────────────────────────┐
│ Queue-0     │ ────────► │ Broker-A: Queue-0 (gen=0)        │
│ Queue-1     │ ────────► │ Broker-A: Queue-1 (gen=0)        │
│ Queue-2     │ ────────► │ Broker-B: Queue-0 (gen=0)        │
│ ...         │           │                                  │
│ Queue-9     │ ────────► │ Broker-B: Queue-4 (gen=0)        │
└─────────────┘           └──────────────────────────────────┘
        10个逻辑队列                    分布在多个Broker

迁移后:
┌─────────────┐           ┌──────────────────────────────────┐
│ Queue-0     │ ────────► │ Broker-C: Queue-0 (gen=1)        │  ← 迁移到新Broker
│ Queue-1     │ ────────► │ Broker-A: Queue-1 (gen=0)        │
│ ...         │           │                                  │
└─────────────┘           └──────────────────────────────────┘
        10个逻辑队列                    队列数不变！
```

> **应用场景**：静态 Topic 允许跨 Broker 分片，通过 `currIdMap` 将全局逻辑队列映射到各 Broker 的物理队列，实现 Topic 的水平扩展能力。详细使用场景、命令示例、迁移流程详见 [06-高级特性篇 - 静态 Topic](06-高级特性篇.md#十静态-topic)。

### 4.5 订阅与心跳数据

#### 4.5.1 SubscriptionData（订阅数据）

`SubscriptionData` 是消费者订阅信息的核心数据结构，封装了 Topic 订阅表达式和过滤信息 ([SubscriptionData.java](file:///d:/work/github/rocketmq/common/src/main/java/org/apache/rocketmq/common/protocol/heartbeat/SubscriptionData.java))：

```java
public class SubscriptionData implements Comparable<SubscriptionData> {
    public final static String SUB_ALL = "*";           // 订阅所有消息
    
    private boolean classFilterMode = false;            // 是否类过滤模式
    private String topic;                               // 订阅的 Topic
    private String subString;                           // 订阅表达式（如 "TagA || TagB"）
    private Set<String> tagsSet = new HashSet<String>(); // 解析后的 Tag 集合
    private Set<Integer> codeSet = new HashSet<Integer>(); // Tag 的 hashcode 集合
    private long subVersion = System.currentTimeMillis(); // 订阅版本号
    private String expressionType = ExpressionType.TAG; // 表达式类型：TAG 或 SQL92
    
    @JSONField(serialize = false)
    private String filterClassSource;                   // 过滤类源码（类过滤模式）
}
```

**核心属性说明**：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `topic` | String | 订阅的 Topic 名称 |
| `subString` | String | 原始订阅表达式，如 `"TagA || TagB"` 或 SQL92 表达式 |
| `tagsSet` | Set\<String\> | 解析后的 Tag 字符串集合 |
| `codeSet` | Set\<Integer\> | Tag 的 hashcode 集合，用于 Broker 端快速过滤 |
| `expressionType` | String | 表达式类型：`TAG` 或 `SQL92` |
| `subVersion` | long | 订阅版本号，用于判断订阅是否变更 |

**订阅表达式示例**：

| 订阅方式 | subString | expressionType | 说明 |
| --- | --- | --- | --- |
| 订阅所有 | `"*"` | `TAG` | 接收所有消息 |
| 单 Tag | `"TagA"` | `TAG` | 只接收 TagA 消息 |
| 多 Tag | `"TagA \|\| TagB"` | `TAG` | 接收 TagA 或 TagB 消息 |
| SQL92 | `"amount > 100"` | `SQL92` | 按属性过滤 |

**SubscriptionData 生成流程**：

```plain

                    │
                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  SubscriptionData 构建过程                                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│  1. 解析订阅表达式                                                          │
│     subString = "TagA || TagB"                                              │
│     expressionType = "TAG"                                                  │
│                                                                             │
│  2. 解析 Tag 集合                                                           │
│     tagsSet = {"TagA", "TagB"}                                              │
│                                                                             │
│  3. 计算 Tag hashcode                                                       │
│     codeSet = {TagA.hashCode(), TagB.hashCode()}                            │
│                                                                             │
│  4. 生成版本号                                                              │

                    │
                    ▼
        存入 ConsumerData.subscriptionDataSet
```

## 九、总结

本篇深入介绍了 RocketMQ 的核心概念体系，要点如下：

1. **核心概念**：Topic、Queue、Message、Producer、Consumer、ConsumerGroup、Broker、NameServer、Offset
2. **消息标识**：Tags（过滤）、Keys（查询、追踪、幂等）、MsgId（唯一标识）、Sharding Key（顺序路由）、MessageConst（消息常量）
3. **消息过滤**：Tag 过滤（简单高效）、SQL92 属性过滤（灵活多维度）、ExpressionType（TAG/SQL92）
4. **队列类型**：普通队列、重试队列、死信队列、延迟队列
5. **领域模型**：
   - 消息模型：Message、MessageExt、系统标志位
   - 主题与队列模型：Topic、TopicConfig、MessageQueue、ProcessQueue
   - Broker 模型：Broker、BrokerData、BrokerRole、FlushDiskType
   - 路由数据模型：TopicRouteData、QueueData
   - 订阅与心跳数据：SubscriptionData、ConsumerData、ProducerData
6. **发送与拉取结果**：SendResult、SendStatus、PullResult、PullStatus 等（详见 [03-消息发送篇](./03-消息发送篇.md)）
7. **消费模式**：集群模式、广播模式、MessageModel、ConsumeFromWhere（详见 [05-消息消费篇](./05-消息消费篇.md)）
8. **队列分配策略**：AllocateMessageQueueAveragely、AllocateMessageQueueConsistentHash 等（详见 [05-消息消费篇](./05-消息消费篇.md)）
9. **消费状态与监听器**：ConsumeConcurrentlyStatus、ConsumeOrderlyStatus、MessageListener（详见 [05-消息消费篇](./05-消息消费篇.md)）

理解这些核心概念是深入学习 RocketMQ 消息发送、存储、消费流程的基础。
