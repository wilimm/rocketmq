# RocketMQ 技术架构分析 - 核心概念篇

> 本篇深入介绍 RocketMQ 的核心概念、消息标识体系、队列类型和领域模型，是理解 RocketMQ 底层原理的基础。

---

## 一、核心概念

本节介绍 RocketMQ 的基本概念和偏移量术语，是理解整个消息系统的基础。

### 1.1 基本概念总览

| 概念 | 说明 | 关键属性（源码字段） |
| --- | --- | --- |
| **Topic** | 消息主题，消息的第一级分类 | `topicName`, `readQueueNums`, `writeQueueNums`, `perm` |
| **MessageQueue** | 队列的逻辑标识，消息发送和消费的基本单位 | `topic`, `brokerName`, `queueId` |
| **Message** | 消息传递的基本单元 | `topic`, `body`, `properties`, `transactionId` |
| **Producer** | 消息生产者，无状态可水平扩展 | `producerGroup`, `sendMsgTimeout`, `retryTimesWhenSendFailed` |
| **ProducerGroup** | 生产者组，标识一类生产者 | 用于事务消息回查、客户端标识 |
| **Consumer** | 消息消费者，支持 Push/Pull 模式 | `consumerGroup`, `messageModel` |
| **ConsumerGroup** | 消费者组，组内消费者共同消费实现负载均衡 | 负载均衡、消费进度共享 |
| **Broker** | 消息服务器，支持 Master-Slave 架构 | `brokerName`, `brokerId`, `brokerRole` |
| **NameServer** | 路由注册中心 | 无状态、心跳检测、路由映射 |
| **Offset** | 消费位点，记录消费进度 | 值等于下一条待消费消息的 `queueOffset` |

### 1.2 MessageQueue（消息队列）

`MessageQueue` 是队列的逻辑标识，是消息发送和消费的基本单位 ([MessageQueue.java](../../common/src/main/java/org/apache/rocketmq/common/message/MessageQueue.java))：

```java
public class MessageQueue implements Comparable<MessageQueue>, Serializable {
    private String topic;        // 主题名称
    private String brokerName;   // Broker名称
    private int queueId;         // 队列ID
}
```

**MessageQueue 核心属性**：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `topic` | String | 主题名称 |
| `brokerName` | String | Broker 名称 |
| `queueId` | int | 队列 ID（从 0 开始） |

**MessageQueue 使用场景**：

| 场景 | 说明 |
| --- | --- |
| **消息发送** | Producer 选择 MessageQueue 发送消息 |
| **消息消费** | Consumer 从 MessageQueue 拉取消息 |
| **队列分配** | Rebalance 将 MessageQueue 分配给消费者 |
| **消费进度** | 以 MessageQueue 为单位记录消费位点 |

**MessageQueue 唯一性**：`topic + brokerName + queueId` 三者唯一确定一个队列。

### 1.3 ProducerGroup（生产者组）

ProducerGroup 是生产者的逻辑分组，用于标识一类生产者。

**ProducerGroup 核心作用**：

| 作用 | 说明 |
| --- | --- |
| **事务消息回查** | Broker 通过 producerGroup 查找生产者进行事务状态回查 |
| **客户端标识** | 在心跳和注册时标识生产者身份 |
| **运维管理** | 通过 producerGroup 查询生产者连接信息 |

**源码定义** ([SendMessageRequestHeader.java](../../common/src/main/java/org/apache/rocketmq/common/protocol/header/SendMessageRequestHeader.java))：

```java
public class SendMessageRequestHeader extends TopicQueueRequestHeader {
    @CFNotNull
    private String producerGroup;    // 生产者组名
    @CFNotNull
    private String topic;
    // ...
}
```

**ProducerGroup vs ConsumerGroup 对比**：

| 特性 | ProducerGroup | ConsumerGroup |
| --- | --- | --- |
| **主要作用** | 事务消息回查、客户端标识 | 负载均衡、消费进度共享 |
| **组成员关系** | 无协调关系，可独立运行 | 需协调队列分配 |
| **状态管理** | 无状态 | 维护消费进度 |
| **事务支持** | 事务消息必须设置 | 不涉及 |

### 1.4 偏移量术语详解

RocketMQ 中有多个与"偏移量/位点"相关的术语，容易混淆：

> **示例场景**：队列中有 5 条消息 (Msg1~Msg5)，消费者已消费到 Msg3，下次将从 Msg4 开始消费。

| 术语 | 含义 | 所属层级 | 使用场景 | 示例值 |
| --- | --- | --- | --- | --- |
| **消息偏移量 (Queue Offset)** | 消息在队列中的逻辑序号，从 0 开始 | Broker 端 | 消息定位、消费进度记录 | Msg3 的偏移量为 2 |
| **消费位点 (Consumer Offset)** | 下次要消费的位置 | 消费者端 | 断点续传、消息回溯 | 消费位点 = 3 |
| **最小偏移量 (MinOffset)** | 队列中最早消息的偏移量 | Broker 端 | 消息过期清理边界 | MinOffset = 0 |
| **最大偏移量 (MaxOffset)** | 队列中最新消息的偏移量 | Broker 端 | 堆积量计算 | MaxOffset = 4 |
| **CommitLog 偏移量** | 消息在 CommitLog 中的物理字节位置 | Broker 端 | 消息实体读取 | Msg3 物理位置 = 200 字节 |

**偏移量关系图**：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│  CommitLog（物理存储）                                                       │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐                       │
│  │  Msg1   │  Msg2   │  Msg3   │  Msg4   │  Msg5   │                       │
│  │ phyOff=0│phyOff=100│phyOff=200│phyOff=300│phyOff=400│                    │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘                       │
│       ↑                                           ↑                         │
│  CommitLog Offset=0                         CommitLog Offset=400            │
│                                                                             │
│  ConsumeQueue（逻辑索引）                                                    │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐                       │
│  │ Entry1  │ Entry2  │ Entry3  │ Entry4  │ Entry5  │                       │
│  │ qOff=0  │ qOff=1  │ qOff=2  │ qOff=3  │ qOff=4  │                       │
│  │phyOff=0 │phyOff=100│phyOff=200│phyOff=300│phyOff=400│                    │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘                       │
│       ↑                  ↑            ↑           ↑                         │
│  MinOffset=0        Queue Offset=2  消费位点=3  MaxOffset=4                  │
│                                                                             │
│  关系：消费位点 = 下一条待消费消息的队列偏移量 = 3                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**关系总结**：`消费位点 = 下一条待消费消息的队列偏移量`

## 二、消息标识体系

RocketMQ 消息有多种标识和属性，理解它们的区别至关重要。本节详细介绍 Tags、Keys、MsgId、Sharding Key 等标识的用途和区别。

### 2.1 标识概念总览

| 概念 | 设置方式 | 存储位置 | 主要用途 | 索引支持 |
| --- | --- | --- | --- | --- |
| **Tags** | `setTags()` | properties | 消息过滤 | ✅ ConsumeQueue |
| **Keys** | `setKeys()` | properties | 消息查询、追踪、幂等 | ✅ IndexFile |
| **MsgId/UNIQ_KEY** | 系统自动 | properties | 唯一标识 | ✅ IndexFile |
| **Sharding Key** | `putUserProperty()` | properties | 顺序消息路由 | ❌ |
| **路由参数** | `send(msg, selector, arg)` | 不存储 | 队列选择 | ❌ |

### 2.2 Tags（标签）

Tags 用于**消息过滤**，同一 Topic 下区分不同业务类型：

```java
// 生产者设置 Tag
Message msg = new Message("TopicTest", "TagA", "OrderID123", body);

// 消费者按 Tag 订阅（支持多个 Tag，用 || 分隔）
consumer.subscribe("TopicTest", "TagA || TagB || TagC");
```

**Tags 特点**：
- 一个消息**只能有一个 Tag**
- Tag 存储在 ConsumeQueue 的 8 字节 hashcode 中，Broker 端高效过滤
- 适用于同一 Topic 下区分不同业务类型的消息

**典型场景**：
- 订单消息：`Tag_OrderCreate`、`Tag_OrderPay`、`Tag_OrderCancel`
- 用户消息：`Tag_UserRegister`、`Tag_UserLogin`

**注意事项**：
- Tag 存储为 8 字节 hashcode，存在**哈希冲突**可能，极端情况下过滤可能不准确
- Tag 过长不影响存储，但建议保持简短便于阅读

> **SQL92 属性过滤**：除了 Tag 过滤，RocketMQ 还支持基于消息属性的 SQL92 表达式过滤，详见 [高级特性篇 - SQL92 过滤](./07-高级特性篇.md#43-sql92-过滤)。

### 2.3 Keys（业务 Key）

Keys 用于**消息查询、追踪、幂等**，不参与消费过滤：

```java
// 设置单个 Key
message.setKeys("OrderID123");

// 设置多个 Key（空格分隔）
message.setKeys("OrderID123 UserID456 ProductID789");
```

**Keys 使用场景**：

| 场景 | 说明 |
| --- | --- |
| **消息查询** | 通过 `topic + key` 在 IndexFile 中检索消息 |
| **链路追踪** | 在 TraceBean 中记录，用于消息轨迹追踪 |
| **事务关联** | 事务消息场景下关联业务流水 |

**Keys vs Body 存储业务 ID 对比**：

| 对比项 | Keys（消息属性） | Body（消息体） |
| --- | --- | --- |
| **存储位置** | IndexFile 索引文件 | CommitLog 消息体 |
| **查询方式** | `mqadmin queryMsgByKey` 直接查询 | 需消费后反序列化 |
| **获取成本** | 无需反序列化 | 需反序列化消息体 |
| **运维可见性** | ✅ 可通过命令行工具查询 | ❌ 无法直接查看 |

**推荐做法**：两者结合使用，Keys 用于消息追踪和运维查询，Body 中包含业务 ID 用于消费端幂等判断。

**注意事项**：
- Keys 过多会增加 IndexFile 索引条目，影响索引文件大小和查询性能
- 建议每条消息设置 1-3 个 Key，避免过多

### 2.4 MsgId / UNIQ_KEY（唯一消息标识）

MsgId 是系统自动生成的消息唯一标识，存储在 properties 中：

```java
// 格式：IP(4B/16B) + PID(2B) + ClassLoader Hash(4B) + 时间差(4B) + 序列号(2B)
// IPv4 场景：4 + 2 + 4 + 4 + 2 = 16字节（32位十六进制字符）
// IPv6 场景：16 + 2 + 4 + 4 + 2 = 28字节（56位十六进制字符）
// 示例（IPv4）：AC1100012A9F00000010000000000001
```

**MsgId 结构解析（IPv4 场景）**：

```plain
MsgId: AC1100012A9F00000010000000000001
       ├──────┤├──┤├──────┤├──────┤├────┤
         IP    PID 类加载器  时间差   自增序列
        4B     2B   哈希4B   4B       2B

AC110001 = 172.17.0.1 (客户端 IP 地址的十六进制)
2A9F = 进程ID (PID)
00000010 = 类加载器哈希
00000000 = 时间差 (与本月1日0点的时间差)
0001 = 自增序列
```

**MsgId 生成源码** ([MessageClientIDSetter.java](../../common/src/main/java/org/apache/rocketmq/common/message/MessageClientIDSetter.java))：

```java
public static String createUniqID() {
    char[] sb = new char[LEN * 2];
    // 1. 复制固定前缀（IP + PID + 类加载器哈希）
    System.arraycopy(FIX_STRING, 0, sb, 0, FIX_STRING.length);
    
    // 2. 计算时间差（与本月1日0点的时间差）
    long current = System.currentTimeMillis();
    if (current >= nextStartTime) {
        setStartTime(current);  // 跨月时重置起始时间
    }
    int diff = (int)(current - startTime);
    if (diff < 0 && diff > -1000_000) {
        diff = 0;  // NTP 时间校准处理，防止时钟回拨导致负值
    }
    
    // 3. 写入时间差和自增序列
    int pos = FIX_STRING.length;
    UtilAll.writeInt(sb, pos, diff);        // 时间差 (4字节)
    pos += 8;
    UtilAll.writeShort(sb, pos, COUNTER.getAndIncrement());  // 自增序列 (2字节)
    return new String(sb);
}
```

### 2.5 Sharding Key（分片键）

Sharding Key 用于**顺序消息队列路由**，相同 Sharding Key 的消息会路由到同一队列，保证顺序。

#### 2.5.1 设置方式

| 方式 | 适用场景 | 示例 |
| --- | --- | --- |
| `putUserProperty(SHARDING_KEY)` | 5.x 新版 API、Proxy 模式 | `msg.putUserProperty(MessageConst.PROPERTY_SHARDING_KEY, "ORDER_12345")` |
| `MessageQueueSelector` | 4.x 传统方式、Remoting 模式 | `producer.send(msg, new SelectMessageQueueByHash(), orderId)` |

> ⚠️ **重要区别**：`MessageQueueSelector` 的分片键参数**不会存入消息 properties**，仅用于客户端计算队列选择。如需存储分片键用于查询追踪，需额外调用 `msg.setKeys()` 或 `msg.putUserProperty()`。

> 详细的顺序消息实现原理和代码示例见 [高级特性篇 - 顺序消息](./07-高级特性篇.md#一顺序消息)。

#### 2.5.2 Keys vs Sharding Key 区别

| 特性 | Keys | Sharding Key |
| --- | --- | --- |
| **主要用途** | 消息查询、追踪、幂等 | 顺序消息路由 |
| **存储位置** | IndexFile（支持按 Key 查询） | 消息 properties |
| **参与路由** | ❌ 不参与 | ✅ 参与 |
| **设置方式** | `msg.setKeys("OrderID123")` | `msg.putUserProperty(SHARDING_KEY, "...")` |

**两种分片键方式对比**：

| 特性 | MessageQueueSelector (4.x) | PROPERTY_SHARDING_KEY (5.x) |
| --- | --- | --- |
| **分片键存储** | ❌ 不存储 | ✅ 存入 properties |
| **队列选择位置** | 客户端 | Broker/Proxy |
| **适用模式** | Remoting 模式 | Proxy 模式、gRPC 模式 |
| **可查询追踪** | ❌ 需额外设置 Keys | ✅ 已存储 |

**顺序消息必须指定分片键**：

| 场景 | 是否需要指定分片键 | 说明 |
| --- | --- | --- |
| 普通消息 | ❌ 不需要 | 自动轮询路由到各队列 |
| 顺序消息 | ✅ 必须指定 | 相同 Key 路由到同一队列 |
| Keys 设置 | 可选 | 仅用于查询/追踪，不影响路由 |

**不指定分片键的后果**：

| 发送方式 | 队列选择 | 顺序性 | 说明 |
| --- | --- | --- | --- |
| `send(msg)` | 轮询（Round-Robin） | ❌ 无法保证 | 消息分散到各队列，并行消费 |
| `send(msg, selector, key)` | Hash(key) % 队列数 | ✅ 保证 | 相同 Key 进入同一队列，串行消费 |

```plain
订单 Order_001 的消息（不指定分片键）：
├── Msg1 → Queue0 (轮询)
├── Msg2 → Queue1 (轮询)
└── Msg3 → Queue2 (轮询)
结果：消息分散到不同队列，可能被不同消费者并行消费，顺序无法保证

订单 Order_001 的消息（指定分片键 "Order_001"）：
├── Msg1 → Queue2 (Hash("Order_001") % 4 = 2)
├── Msg2 → Queue2 (Hash("Order_001") % 4 = 2)
└── Msg3 → Queue2 (Hash("Order_001") % 4 = 2)
结果：所有消息进入同一队列，单线程串行消费，顺序得到保证
```

### 2.6 消息常量 MessageConst

**MessageConst** 定义了所有消息属性的常量 ([MessageConst.java](../../common/src/main/java/org/apache/rocketmq/common/message/MessageConst.java))。

> 以下仅列出常用常量，完整列表见源码。

**消息标识相关**：

| 常量 | 值 | 说明 | 使用场景 |
| --- | --- | --- | --- |
| `PROPERTY_KEYS` | KEYS | 消息 Key | 消息查询、链路追踪、幂等判断。通过 `mqadmin queryMsgByKey` 命令查询消息 |
| `PROPERTY_TAGS` | TAGS | 消息 Tag | 消息过滤。消费者订阅时指定 Tag，如 `consumer.subscribe("Topic", "TagA \|\| TagB")` |
| `PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX` | UNIQ_KEY | 消息唯一 ID | 系统自动生成，全局唯一标识消息，用于消息追踪和去重 |

**延迟/定时消息相关**：

| 常量 | 值 | 说明 | 使用场景 |
| --- | --- | --- | --- |
| `PROPERTY_DELAY_TIME_LEVEL` | DELAY | 延迟级别（1-18） | 延迟消息。通过 `msg.setDelayTimeLevel(3)` 设置，消息将在指定延迟级别对应的时间后投递 |
| `PROPERTY_TIMER_DELAY_SEC` | TIMER_DELAY_SEC | 定时消息延迟秒数 | 精确延迟消息（5.x 新特性）。指定延迟秒数，支持任意时间延迟 |

| `PROPERTY_TIMER_DELIVER_MS` | TIMER_DELIVER_MS | 定时消息投递时间戳（毫秒） | 指定投递时间。设置消息在特定时间点投递，如订单超时取消场景 |
| `PROPERTY_TIMER_DELAY_LEVEL` | TIMER_DELAY_LEVEL | Timer 延迟级别 | 内部使用，Timer 模块处理延迟消息时的级别标识 |
| `PROPERTY_TIMER_ENQUEUE_MS` | TIMER_ENQUEUE_MS | Timer 入队时间戳 | 内部使用，记录消息进入 Timer 轮的时间，用于计算投递时间 |
| `PROPERTY_TIMER_DEQUEUE_MS` | TIMER_DEQUEUE_MS | Timer 出队时间戳 | 内部使用，记录消息从 Timer 轮取出的时间 |
| `PROPERTY_TIMER_ROLL_TIMES` | TIMER_ROLL_TIMES | Timer 滚动次数 | 内部使用，记录消息在 Timer 轮中的滚动次数 |
| `PROPERTY_TIMER_OUT_MS` | TIMER_OUT_MS | Timer 超时时间 | 内部使用，消息在 Timer 中的超时时间 |
| `PROPERTY_TIMER_DEL_UNIQKEY` | TIMER_DEL_UNIQKEY | Timer 删除唯一键 | 内部使用，用于删除 Timer 中待投递的消息 |

**事务消息相关**：

| 常量 | 值 | 说明 | 使用场景 |
| --- | --- | --- | --- |
| `PROPERTY_TRANSACTION_PREPARED` | TRAN_MSG | 事务消息标志 | 标识半消息（Half Message）。事务消息发送时自动设置，Broker 据此将消息存入 `RMQ_SYS_TRANS_HALF_TOPIC` |

| `PROPERTY_PRODUCER_GROUP` | PGROUP | 生产者组（事务回查用） | Broker 回查事务状态时，根据此属性找到对应的生产者组进行回查 |

| `PROPERTY_CHECK_IMMUNITY_TIME_IN_SECONDS` | CHECK_IMMUNITY_TIME_IN_SECONDS | 事务免疫检查时间 | 事务消息发送后，在此时间内不进行回查，等待本地事务执行完成 |

**重试消息相关**：

| 常量 | 值 | 说明 | 使用场景 |
| --- | --- | --- | --- |
| `PROPERTY_RETRY_TOPIC` | RETRY_TOPIC | 重试 Topic | 消费失败后消息进入重试队列，Topic 格式为 `%RETRY%+ConsumerGroup` |
| `PROPERTY_REAL_TOPIC` | REAL_TOPIC | 真实 Topic | 记录消息原始 Topic，重试消息投递时恢复为原始 Topic |
| `PROPERTY_REAL_QUEUE_ID` | REAL_QID | 真实队列 ID | 记录消息原始队列 ID，重试消息投递时恢复为原始队列 |
| `PROPERTY_RECONSUME_TIME` | RECONSUME_TIME | 重试次数 | 记录消息已被重试消费的次数，用于判断是否进入死信队列 |
| `PROPERTY_MAX_RECONSUME_TIMES` | MAX_RECONSUME_TIMES | 最大重试次数 | 消费者可配置的最大重试次数，超过后消息进入死信队列 |

**消息元数据相关**：

## 三、队列类型

RocketMQ 定义了多种队列类型，用于支持不同的业务场景。本节介绍业务队列类型、系统内部队列和队列流转关系。

### 3.1 业务队列类型

RocketMQ 有 **3 种业务队列类型**：

| 队列类型 | Topic 格式 | 用途 | 特点 |
| --- | --- | --- | --- |
| **普通队列** | 用户定义的 Topic | 业务消息存储 | 用户创建的业务 Topic |
| **重试队列** | `%RETRY%` + ConsumerGroup | 消费失败消息重试 | 自动创建，使用延迟消息机制 |
| **死信队列** | `%DLQ%` + ConsumerGroup | 存储无法消费的消息 | 永久存储，需人工处理 |

### 3.2 系统内部队列

RocketMQ 定义了多个系统内部 Topic，用于支持不同的系统功能 ([TopicValidator.java](../../common/src/main/java/org/apache/rocketmq/common/topic/TopicValidator.java))：

| 队列类型 | Topic 格式 | 用途 | 特点 |
| --- | --- | --- | --- |
| **延迟队列** | `SCHEDULE_TOPIC_XXXX` | 延迟消息中转存储 | 18 个队列对应 18 个延迟级别 |
| **事务半消息队列** | `RMQ_SYS_TRANS_HALF_TOPIC` | 事务消息预处理存储 | 存储未提交的事务消息 |
| **事务操作队列** | `RMQ_SYS_TRANS_OP_HALF_TOPIC` | 事务消息操作记录 | 记录已提交/回滚的事务消息 |
| **消息轨迹队列** | `RMQ_SYS_TRACE_TOPIC` | 消息轨迹数据存储 | 存储消息发送/消费轨迹 |
| **超时检查队列** | `TRANS_CHECK_MAX_TIME_TOPIC` | 事务消息超时检查 | 超过最大检查次数的事务消息 |
| **自测队列** | `SELF_TEST_TOPIC` | 系统自测使用 | 用于系统功能测试 |
| **偏移量移动事件** | `OFFSET_MOVED_EVENT` | 偏移量移动事件通知 | 消费进度异常时通知消费者 |
| **自动创建标识** | `TBW102` | 自动创建 Topic 标识 | Broker 开启自动创建时使用 |

**系统 Topic 前缀**：以 `rmq_sys_` 开头的 Topic 也被视为系统 Topic，如 `rmq_sys_SYNC_BROKER_MEMBER_` 用于 Broker 成员同步。

**禁止发送的系统 Topic**：

| Topic | 说明 |
| --- | --- |
| `SCHEDULE_TOPIC_XXXX` | 延迟消息内部使用 |
| `RMQ_SYS_TRANS_HALF_TOPIC` | 事务消息内部使用 |
| `RMQ_SYS_TRANS_OP_HALF_TOPIC` | 事务消息内部使用 |
| `TRANS_CHECK_MAX_TIME_TOPIC` | 事务检查内部使用 |
| `SELF_TEST_TOPIC` | 系统测试使用 |
| `OFFSET_MOVED_EVENT` | 系统事件使用 |

> 延迟级别详细说明见 [高级特性篇 - 延迟消息](./07-高级特性篇.md#三延迟消息)。
> 事务消息详细说明见 [高级特性篇 - 事务消息](./07-高级特性篇.md#二事务消息)。

### 3.3 队列流转关系

RocketMQ 的队列流转主要涉及两种场景：

| 场景 | 流程 | 详见 |
| --- | --- | --- |
| **普通延迟消息** | 业务Topic → SCHEDULE_TOPIC_XXXX → 到期恢复业务Topic | [高级特性篇 - 延迟消息](./07-高级特性篇.md#三延迟消息) |
| **消费失败重试** | 消费失败 → SCHEDULE_TOPIC_XXXX → %RETRY%+Group → 重试超限 → %DLQ%+Group | [消息消费篇 - 消费失败处理](./06-消息消费篇.md#六消费失败处理)、[高级特性篇 - 死信队列](./07-高级特性篇.md#五死信队列) |

**两种场景对比**：

| 对比项 | 普通延迟消息 | 重试消息 |
| --- | --- | --- |
| 触发方式 | Producer 主动设置 delayLevel | Consumer 消费失败自动触发 |
| 延迟后目标 | 原始业务 Topic | 重试队列 `%RETRY%+Group` |
| Consumer 订阅 | 业务 Topic | 业务 Topic + 重试队列 |
| 延迟级别 | 1-18 均可 | 固定从级别 4 开始递增 |
| 是否进入死信队列 | 否 | 重试超限后进入 |

## 四、领域模型

本节深入介绍 RocketMQ 的领域模型，包括消息模型、主题与队列模型、Broker 模型、路由数据模型和订阅与心跳数据。

### 4.1 消息模型

#### 4.1.1 Message（消息）

**Message 基础属性** ([Message.java](../../common/src/main/java/org/apache/rocketmq/common/message/Message.java))：

```java
public class Message implements Serializable {
    private String topic;                      // 消息主题
    private int flag;                          // 消息标志
    private Map<String, String> properties;    // 消息属性（tags、keys等存储于此）
    private byte[] body;                       // 消息体
    private String transactionId;              // 事务ID
}
```

**Message 属性说明**：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `topic` | String | 消息主题，消息的第一级分类 |
| `flag` | int | 消息标志，用于 RPC 通信 |
| `properties` | Map | 扩展属性，存储 tags、keys 等 |
| `body` | byte[] | 消息体，实际业务数据 |
| `transactionId` | String | 事务消息 ID |

#### 4.1.2 MessageExt（扩展消息）

`MessageExt` 继承自 `Message`，增加了消息在传输和存储过程中的元数据 ([MessageExt.java](../../common/src/main/java/org/apache/rocketmq/common/message/MessageExt.java))：

```java
public class MessageExt extends Message {
    private String brokerName;              // Broker名称
    private int queueId;                    // 队列ID
    private int storeSize;                  // 存储大小（字节）
    private long queueOffset;               // 队列偏移量
    private int sysFlag;                    // 系统标志
    private long bornTimestamp;             // 消息生成时间戳
    private SocketAddress bornHost;         // 消息来源地址
    private long storeTimestamp;            // 存储时间戳
    private SocketAddress storeHost;        // 存储Broker地址
    private String msgId;                   // 消息唯一ID
    private long commitLogOffset;           // CommitLog物理偏移量
    private int bodyCRC;                    // 消息体CRC校验码
    private int reconsumeTimes;             // 重试消费次数
    private long preparedTransactionOffset; // 事务消息预处理偏移量
}
```

**MessageExt 属性分类**：

| 分类 | 属性 | 说明 |
| --- | --- | --- |
| **位置信息** | brokerName, queueId, queueOffset, commitLogOffset | 消息在 Broker 中的位置 |
| **时间信息** | bornTimestamp, storeTimestamp | 消息生命周期时间点 |
| **重试信息** | reconsumeTimes | 消息重试次数 |

**关键结论**：

| 问题 | 答案 |
| --- | --- |
| 消费重试是否生成新消息？ | **是**，每次重试都生成一条全新的消息 |
| 多次重试是否生成多条消息？ | **是**，每次重试都会在 CommitLog 中写入新消息 |
| MsgId 是否变化？ | **是**，每次重试生成新的 MsgId |
| commitLogOffset 是否变化？ | **是**，每次重试占用新的物理空间 |
| reconsumeTimes 如何变化？ | 每次重试 +1，存储在消息属性中 |

> **消费重试机制详解**：包括重试消息生成流程、延迟级别计算、重试队列分配机制等，详见 [消息消费篇 - 消费失败处理](./06-消息消费篇.md#六消费失败处理)。

### 4.2 主题与队列模型

#### 4.2.1 TopicConfig（主题配置）

Topic 是消息主题，消息的第一级分类。**TopicConfig** 是主题的完整配置信息 ([TopicConfig.java](../../common/src/main/java/org/apache/rocketmq/common/TopicConfig.java))：

```java
public class TopicConfig {
    public static int defaultReadQueueNums = 16;    // 默认读队列数
    public static int defaultWriteQueueNums = 16;   // 默认写队列数
    
    private String topicName;              // 主题名称
    private int readQueueNums = defaultReadQueueNums;   // 读队列数，默认 16
    private int writeQueueNums = defaultWriteQueueNums; // 写队列数，默认 16
    private int perm = PermName.PERM_READ | PermName.PERM_WRITE;  // 权限，默认读写
    private TopicFilterType topicFilterType = TopicFilterType.SINGLE_TAG; // 过滤类型，默认单标签
    private int topicSysFlag = 0;          // 系统标志
    private boolean order = false;         // 是否顺序消息，默认 false
    private Map<String, String> attributes; // 扩展属性（如消息类型）
}
```

**TopicConfig 使用场景**：

| 场景 | 说明 |
| --- | --- |
| **主题创建** | 创建新 Topic 时指定队列数和权限 |
| **主题管理** | 通过管理工具查询和修改主题配置 |
| **路由信息** | NameServer 存储和返回主题配置信息 |

**TopicConfig 默认值**：

| 属性 | 默认值 | 说明 |
| --- | --- | --- |
| `readQueueNums` | 16 | 读队列数 |
| `writeQueueNums` | 16 | 写队列数 |
| `perm` | 6 (PERM_READ \| PERM_WRITE) | 读写权限 |
| `topicFilterType` | SINGLE_TAG | 单标签过滤 |
| `topicSysFlag` | 0 | 普通主题 |
| `order` | false | 非顺序消息 |

**TopicFilterType 过滤类型说明** ([TopicFilterType.java](../../common/src/main/java/org/apache/rocketmq/common/TopicFilterType.java))：

| 枚举值 | 说明 | 使用场景 |
| --- | --- | --- |
| `SINGLE_TAG` | 单标签过滤（默认值） | 消息只有一个 Tag，Broker 使用哈希值快速过滤 |
| `MULTI_TAG` | 多标签过滤 | 消息可能有多个 Tag，需要更复杂的过滤逻辑 |

> **实现原理**：当 Topic 配置为 `MULTI_TAG` 时，发送消息会在 `sysFlag` 中设置 `MULTI_TAGS_FLAG (0x2)` 标志位，Broker 端据此选择不同的 Tag 解码方式。详见 [MessageSysFlag.java](../../common/src/main/java/org/apache/rocketmq/common/sysflag/MessageSysFlag.java)。

#### 4.2.2 ProcessQueue（处理队列）

`ProcessQueue` 是消费者端的消息处理快照 ([ProcessQueue.java](../../client/src/main/java/org/apache/rocketmq/client/impl/consumer/ProcessQueue.java))：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│  Broker端                           消费者端                                │
│  ┌──────────────────┐              ┌──────────────────────────────────────┐ │
│  │   MessageQueue   │              │           ProcessQueue               │ │
│  │  (逻辑队列标识)    │   Pull      │         (消息处理快照)                 │ │
│  │                  │  ───────►   │                                      │ │
│  │ topic: Order     │              │  msgTreeMap: {offset → MessageExt}   │ │
│  │ brokerName: A    │              │  msgCount: 消息数量                    │ │
│  │ queueId: 0       │              │  msgSize: 消息总大小                   │ │
│  └──────────────────┘              │  queueOffsetMax: 最大偏移量           │ │
│                                    │  dropped: 是否已丢弃                  │ │
│                                    │  locked: 是否已锁定(顺序消费)          │ │
│                                    └──────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────┘
```

**ProcessQueue 核心属性**：

```java
public class ProcessQueue {
    public static final long REBALANCE_LOCK_MAX_LIVE_TIME = 30000L;  // 锁最大存活时间，默认 30s
    public static final long REBALANCE_LOCK_INTERVAL = 20000L;       // 锁续期间隔，默认 20s
    private static final long PULL_MAX_IDLE_TIME = 120000L;          // 拉取最大空闲时间，默认 120s（2min）
    
    private final TreeMap<Long, MessageExt> msgTreeMap = new TreeMap<>();  // 待消费消息
    private final TreeMap<Long, MessageExt> consumingMsgOrderlyTreeMap = new TreeMap<>();  // 顺序消费中
    private final AtomicLong msgCount = new AtomicLong();    // 消息数量
    private final AtomicLong msgSize = new AtomicLong();     // 消息总大小
    private volatile long queueOffsetMax = 0L;               // 最大偏移量
    private volatile boolean dropped = false;                // 是否已丢弃
    private volatile boolean locked = false;                 // 是否已锁定
    private volatile long lastPullTimestamp;                 // 最后拉取时间戳
    private volatile long lastConsumeTimestamp;              // 最后消费时间戳
    private volatile long lastLockTimestamp;                 // 最后锁定时间戳
}
```

**MessageQueue vs ProcessQueue 对比**：

| 属性 | MessageQueue | ProcessQueue |
| --- | --- | --- |
| 所在位置 | 消费者端（标识 Broker 端队列） | 消费者端 |
| 本质 | 队列的逻辑标识（不可变） | 队列的消费状态快照（动态变化） |
| 核心属性 | topic, brokerName, queueId | msgTreeMap, msgCount, dropped, locked |
| 生命周期 | Topic 创建时存在 | 消费者订阅队列时创建 |

**两个 TreeMap 的作用**：

| Map | 含义 | 使用场景 |
| --- | --- | --- |
| `msgTreeMap` | 待消费消息 | 所有消费模式 |
| `consumingMsgOrderlyTreeMap` | 正在消费的消息 | 仅顺序消费 |

**ProcessQueue 核心方法**：

| 方法 | 功能 | 使用场景 |
| --- | --- | --- |
| `putMessage()` | 将拉取的消息存入 msgTreeMap | PullMessage 后调用 |
| `takeMessages()` | 批量取出消息准备消费 | 顺序消费前调用 |
| `removeMessage()` | 移除已消费消息 | 并发消费成功/失败后调用 |
| `makeMessageToConsumeAgain()` | 消息放回队列头部 | 顺序消费失败重试 |
| `commit()` | 提交消费进度 | 顺序消费成功 |

#### 4.3.3 BrokerRole（Broker 角色）

### 4.4 权限模型

#### 4.4.1 PermName（权限常量）

**PermName** 定义了 Topic 和 Broker 的权限常量 ([PermName.java](../../common/src/main/java/org/apache/rocketmq/common/constant/PermName.java))：

```java
public class PermName {
    public static final int INDEX_PERM_PRIORITY = 3;
    public static final int INDEX_PERM_READ = 2;
    public static final int INDEX_PERM_WRITE = 1;
    public static final int INDEX_PERM_INHERIT = 0;

    public static final int PERM_PRIORITY = 0x1 << INDEX_PERM_PRIORITY;  // 8
    public static final int PERM_READ = 0x1 << INDEX_PERM_READ;          // 4
    public static final int PERM_WRITE = 0x1 << INDEX_PERM_WRITE;        // 2
    public static final int PERM_INHERIT = 0x1 << INDEX_PERM_INHERIT;    // 1
}
```

**权限常量说明**：

| 常量 | 值 | 二进制 | 说明 |
| --- | --- | --- | --- |
| `PERM_INHERIT` | 1 | 0001 | 继承权限（用于系统 Topic） |
| `PERM_WRITE` | 2 | 0010 | 写权限（Producer 可发送） |
| `PERM_READ` | 4 | 0100 | 读权限（Consumer 可消费） |
| `PERM_PRIORITY` | 8 | 1000 | 优先级权限 |

**常用权限组合**：

| 权限值 | 二进制 | 组合 | 说明 |
| --- | --- | --- | --- |
| 6 | 0110 | READ + WRITE | 读写权限（默认） |
| 4 | 0100 | READ | 只读权限 |
| 2 | 0010 | WRITE | 只写权限 |
| 1 | 0001 | INHERIT | 继承权限（系统 Topic） |
| 7 | 0111 | INHERIT + READ + WRITE | 继承 + 读写权限 |

**权限判断方法**：

```java
public static boolean isReadable(final int perm) {
    return (perm & PERM_READ) == PERM_READ;
}

public static boolean isWriteable(final int perm) {
    return (perm & PERM_WRITE) == PERM_WRITE;
}

public static boolean isInherited(final int perm) {
    return (perm & PERM_INHERIT) == PERM_INHERIT;
}
```

**权限字符串表示**：

```java
public static String perm2String(final int perm) {
    final StringBuilder sb = new StringBuilder("---");
    if (isReadable(perm)) {
        sb.replace(0, 1, "R");    // 第1位：R 表示可读
    }
    if (isWriteable(perm)) {
        sb.replace(1, 2, "W");    // 第2位：W 表示可写
    }
    if (isInherited(perm)) {
        sb.replace(2, 3, "X");    // 第3位：X 表示继承
    }
    return sb.toString();
}
```

**权限字符串示例**：

| 权限值 | perm2String | 含义 |
| --- | --- | --- |
| 6 | `"RW-"` | 可读可写 |
| 4 | `"R--"` | 只读 |
| 2 | `"-W-"` | 只写 |
| 1 | `"--X"` | 继承 |
| 7 | `"RWX"` | 继承 + 可读可写 |

#### 4.5.2 QueueData（队列数据）

```java

    private String brokerName;     // Broker 名称
    private int readQueueNums;     // 读队列数
    private int writeQueueNums;    // 写队列数
    private int perm;              // 权限
    private int topicSysFlag;      // 主题系统标志
```

**QueueData 属性说明**：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `brokerName` | String | Broker 名称 |
| `readQueueNums` | int | 读队列数量，Consumer 根据此值分配队列，默认值 16 |
| `writeQueueNums` | int | 写队列数量，Producer 根据此值选择队列，默认值 16 |
| `perm` | int | 权限，默认值 6（读写），详见 [4.4 权限模型](#44-权限模型) |
| `topicSysFlag` | int | 主题系统标志，用于静态 Topic 标识，默认值 0 |

**为什么 QueueData 不包含 topic 字段？**

QueueData 的读写队列数量确实与 Topic 关联，但不存储 topic 字段是合理的设计：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│  NameServer 存储结构                                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│  HashMap<String/* topic */, TopicRouteData> topicRouteTable;                │
│                                                                             │
│  "TopicTest" → TopicRouteData                                               │
│                ├── queueDatas: [QueueData(broker-a), QueueData(broker-b)]   │
│                └── brokerDatas: [...]                                       │
│                                                                             │
│  topic 信息存储在 Map 的 key 中，QueueData 作为 value 的子结构无需重复       │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  客户端调用流程                                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│  1. 客户端调用: getTopicRouteInfoFromNameServer("TopicTest")                │
│     ↓                                                                       │
│  2. NameServer 返回: TopicRouteData                                         │
│     └── queueDatas: [QueueData, QueueData, ...]                             │
│                                                                             │
│  3. 此时客户端已知 topic="TopicTest"                                         │
│     每个 QueueData 的 readQueueNums/writeQueueNums                          │
│     就是 "TopicTest" 在该 Broker 上的队列数量                                │
└─────────────────────────────────────────────────────────────────────────────┘
```

**类比理解**：类似 SQL 查询 `SELECT brokerName, readQueueNums FROM config WHERE topic='TopicTest'`，返回结果行不需要包含 topic 列，因为查询条件已指定。

**读写队列分离**：
- readQueueNums 和 writeQueueNums 可以不同
- 常用于灰度发布：先增加 writeQueueNums，再增加 readQueueNums

> ⚠️ **风险提示**：读写队列数不一致会导致消息丢失或消费空转，详见 [消息发送篇 - 队列选择策略](./03-消息发送篇.md#三队列选择策略)。生产环境建议保持一致。

#### 4.5.3 路由转换与队列映射

Producer 和 Consumer 从 NameServer 获取 `TopicRouteData` 后，需要转换为各自使用的队列列表。两者的转换逻辑存在显著差异：

**转换逻辑对比**：

```java
// Producer 端转换：提取可写队列
public static TopicPublishInfo topicRouteData2TopicPublishInfo(String topic, TopicRouteData route) {
    TopicPublishInfo info = new TopicPublishInfo();
    for (QueueData qd : route.getQueueDatas()) {
        if (PermName.isWriteable(qd.getPerm())) {  // 检查写权限
            // 使用 writeQueueNums 构建可写队列列表
            for (int i = 0; i < qd.getWriteQueueNums(); i++) {
                MessageQueue mq = new MessageQueue(topic, qd.getBrokerName(), i);
                info.getMessageQueueList().add(mq);
            }
        }
    }
    return info;
}

// Consumer 端转换：提取可读队列
public static Set<MessageQueue> topicRouteData2TopicSubscribeInfo(String topic, TopicRouteData route) {
    Set<MessageQueue> mqList = new HashSet<>();
    for (QueueData qd : route.getQueueDatas()) {
        if (PermName.isReadable(qd.getPerm())) {  // 检查读权限
            // 使用 readQueueNums 构建可读队列列表
            for (int i = 0; i < qd.getReadQueueNums(); i++) {
                MessageQueue mq = new MessageQueue(topic, qd.getBrokerName(), i);
                mqList.add(mq);
            }
        }
    }
    return mqList;
}
```

**Producer vs Consumer 路由处理差异**：

| 维度 | Producer | Consumer |
| --- | --- | --- |
| **缓存结构** | `TopicPublishInfo`（含轮询计数器） | `Set<MessageQueue>`（简单集合） |
| **转换方法** | `topicRouteData2TopicPublishInfo()` | `topicRouteData2TopicSubscribeInfo()` |
| **关注队列** | `writeQueueNums`（可写队列） | `readQueueNums`（可读队列） |
| **权限检查** | `PermName.isWriteable()` | `PermName.isReadable()` |
| **队列可见性** | Topic 的**全部**可写队列 | **分配给自己**的队列（经 Rebalance） |
| **选择策略** | 轮询 + 故障规避 | Rebalance 分配 |

**路由转换流程**：

```plain
NameServer
    │
    │ getRouteInfoByTopic(topic)
    ▼
TopicRouteData
├── QueueData (brokerName, readQueueNums, writeQueueNums, perm)
└── BrokerData (brokerName, brokerAddrs)
    │
    ├─────────────────────────────────────────┐
    │                                         │
    ▼                                         ▼
Producer 转换                            Consumer 转换
topicRouteData2TopicPublishInfo()        topicRouteData2TopicSubscribeInfo()
    │                                         │
    ▼                                         ▼
TopicPublishInfo                         Set<MessageQueue>
├── messageQueueList                      ├── MessageQueue{topic, brokerName, queueId}
│   (基于 writeQueueNums)                 │   (基于 readQueueNums)
└── sendWhichQueue (轮询计数器)           └── 用于 Rebalance 分配
    │
    ▼
轮询选择队列发送
```

**设计差异原因**：

| 场景 | Producer 需求 | Consumer 需求 |
| --- | --- | --- |
| **队列选择** | 轮询选择队列，需要 `ThreadLocalIndex` | Rebalance 分配，无需轮询 |
| **消息顺序** | 多 Producer 发同一队列无影响 | 同一队列只能被一个 Consumer 消费 |
| **缓存目的** | 发送时快速选择队列 | Rebalance 时快速获取全量队列 |

> **关键差异**：Producer 使用 `writeQueueNums`，Consumer 使用 `readQueueNums`。这就是读写队列数可以不同的原因——Producer 只看到可写队列，Consumer 只看到可读队列。

```java
}
```

**核心属性说明**：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `topic` | String | 订阅的 Topic 名称 |
| `subString` | String | 原始订阅表达式，如 `"TagA || TagB"` 或 SQL92 表达式 |
| `tagsSet` | Set\<String\> | 解析后的 Tag 字符串集合 |
| `codeSet` | Set\<Integer\> | Tag 的 hashcode 集合，用于 Broker 端快速过滤 |
| `expressionType` | String | 表达式类型：`TAG` 或 `SQL92` |
| `subVersion` | long | 订阅版本号，用于判断订阅是否变更 |

**订阅表达式示例**：

| 订阅方式 | subString | expressionType | 说明 |
| --- | --- | --- | --- |
| 订阅所有 | `"*"` | `TAG` | 接收所有消息 |
| 单 Tag | `"TagA"` | `TAG` | 只接收 TagA 消息 |
| 多 Tag | `"TagA \|\| TagB"` | `TAG` | 接收 TagA 或 TagB 消息 |
| SQL92 | `"amount > 100"` | `SQL92` | 按属性过滤 |

**SubscriptionData 生成流程**：

```plain
consumer.subscribe("TopicTest", "TagA || TagB")
                    │
                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  SubscriptionData 构建过程                                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│  1. 解析订阅表达式                                                          │
│     subString = "TagA || TagB"                                              │
│     expressionType = "TAG"                                                  │
│                                                                             │
│  2. 解析 Tag 集合                                                           │
│     tagsSet = {"TagA", "TagB"}                                              │
│                                                                             │
│  3. 计算 Tag hashcode                                                       │
│     codeSet = {TagA.hashCode(), TagB.hashCode()}                            │
│                                                                             │
│  4. 生成版本号                                                              │
│     subVersion = System.currentTimeMillis()                                 │
└─────────────────────────────────────────────────────────────────────────────┘
                    │
                    ▼
        存入 ConsumerData.subscriptionDataSet
```

#### 4.6.2 ConsumerData（消费者数据）

ConsumerData 是客户端向 Broker 发送心跳时携带的消费者元数据 ([ConsumerData.java](../../common/src/main/java/org/apache/rocketmq/common/protocol/heartbeat/ConsumerData.java))：

```java
public class ConsumerData {
```

```plain

│                                                                             │

│  ┌──────────────┐                           ┌──────────────────────────────┐│
│  │              │   HeartbeatData           │  consumerTable               ││
```

**心跳数据用途**：

| 用途 | 说明 |
| --- | --- |
| **存活检测** | Broker 通过心跳判断客户端是否在线 |
| **订阅同步** | Consumer 将订阅信息同步给 Broker |
| **Rebalance 触发** | Broker 感知消费者变化后通知所有消费者重新分配队列 |
| **生产者管理** | 记录生产者连接信息，用于查询和管理 |

## 六、总结

本篇深入介绍了 RocketMQ 的核心概念体系，要点如下：

1. **核心概念**：Topic、MessageQueue、Message、Producer、ProducerGroup、Consumer、ConsumerGroup、Broker、NameServer、Offset
2. **消息标识**：Tags（过滤）、Keys（查询、追踪、幂等）、MsgId（唯一标识）、Sharding Key（顺序路由）、MessageConst（消息常量）
3. **队列类型**：普通队列、重试队列、死信队列、延迟队列
4. **领域模型**：消息模型、主题与队列模型、Broker 模型、权限模型、路由数据模型、订阅与心跳数据
5. **权限模型**：PermName 定义读、写、继承权限，支持灵活的权限组合
6. **Broker 角色**：ASYNC_MASTER、SYNC_MASTER、SLAVE，配合刷盘方式决定可靠性
7. **延伸阅读**：消息发送、消息消费、消费模式、队列分配等详见对应专题文档

理解这些核心概念是深入学习 RocketMQ 消息发送、存储、消费流程的基础。
