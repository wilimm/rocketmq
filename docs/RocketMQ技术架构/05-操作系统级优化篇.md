### 1.1 优化手段分类

| 优化类型 | 优化手段 | 核心收益 |
| --- | --- | --- |
| **内存映射** | mmap | 零拷贝读写，避免用户态/内核态切换 |
| **内存锁定** | mlock + madvise | 防止热点数据被 swap，提升访问速度 |
| **堆外内存** | TransientStorePool | 减少 PageCache 锁竞争，提升写入性能 |
| **文件预热** | warmMappedFile | 提前加载到 PageCache，避免运行时缺页 |
| **文件预分配** | AllocateMappedFileService | 避免文件创建阻塞写入线程 |
| **内存映射交换** | swapMap | 清理 Page Table 条目，释放内核内存 |

## 二、PageCache 核心概念

PageCache 是操作系统内核维护的磁盘数据缓存，是理解 RocketMQ 存储优化的前置知识。所有文件读写操作都经过 PageCache（除非使用 O_DIRECT），RocketMQ 的 mmap、mlock、文件预热等优化手段均围绕 PageCache 展开。

### 2.1 PageCache 概述

**PageCache** 是操作系统内核维护的磁盘数据缓存，位于用户程序与磁盘之间。所有文件读写操作都经过 PageCache（除非使用 O_DIRECT）：

| 作用 | 说明 |
|------|------|
| **读缓存** | 数据首次读取后缓存在内存，后续读取直接从内存返回 |
| **写缓存** | 写入先到 PageCache，OS 异步刷盘，减少磁盘 I/O |
| **预读** | 顺序读取时，OS 预测性地加载后续数据到 PageCache |

**关于 Buffer Cache**：在 Linux 内核 2.4 之前，PageCache（缓存文件页）和 Buffer Cache（缓存磁盘块）是分开的。从 Linux 2.4 开始，**两者统一到 Page Cache 中管理**，Buffer Cache 仅用于缓存文件系统元数据（inode、dentry 等）。对于文件 I/O 操作（read/write/mmap），主要使用 PageCache。

> **📌 重要：内核缓冲区 = PageCache（文件 I/O 场景）**
>
> 在文件 I/O 上下文中，"内核缓冲区"和"PageCache"是**同一概念**的不同称呼：
>
> | 场景 | "内核缓冲区"指代 |
> |------|------------------|
> | **文件 I/O（read/write/mmap）** | ✅ 就是 PageCache |
> | **块设备 I/O** | PageCache 中的 Buffer 部分 |
> | **网络 I/O** | Socket Buffer（不是 PageCache） |
>
> **RocketMQ 使用文件 I/O**，因此文档中提到的"内核缓冲区"均指 PageCache。理解这一点有助于消除概念混淆。

### 2.2 文件读写与 Page Cache 的关系

**所有文件读写操作都经过 Page Cache**（除非使用 O_DIRECT）：

```plain
│  │                                                                     │   │
│  │  方式一：write() 系统调用                                            │   │

```

**详细对比**：

| 操作方式 | 是否经过 Page Cache | 数据拷贝次数 | 说明 |
|----------|---------------------|--------------|------|
| `read()` | ✅ 是 | 1 次（内核→用户） | 从 Page Cache 拷贝到用户缓冲区 |
| `write()` | ✅ 是 | 1 次（用户→内核） | 从用户缓冲区拷贝到 Page Cache |
| `mmap()` 读 | ✅ 是 | 0 次 | 用户空间直接映射到 Page Cache |
| `mmap()` 写 | ✅ 是 | 0 次 | 用户空间直接映射到 Page Cache |
| `O_DIRECT` | ❌ 否 | 0 次 | 绕过 Page Cache，直接 I/O |

**RocketMQ 的选择**：使用 `mmap()` 内存映射方式，实现零拷贝读写 Page Cache。

**特殊情况：Direct I/O**：

使用 `O_DIRECT` 标志可以绕过 Page Cache，直接在用户缓冲区和磁盘之间传输数据。适用场景包括：
- 数据库系统（自行管理缓存）
- 大文件顺序读写（避免污染 Page Cache）
- 对数据一致性要求极高的场景

RocketMQ **不使用 Direct I/O**，因为 Page Cache 已经提供了高效的缓存，顺序写入模式下性能极佳。

### 2.4 PageCache 数据持久性分析

数据写入 PageCache 后，其持久性与故障类型密切相关：

```plain

│                                                                             │
│  应用写入 → PageCache（内核态内存）→ 磁盘                                     │
│              │                  │                                           │
│              │                  └── 异步刷盘（由操作系统控制）                 │
│              │                                                              │
│              └── 数据已在内核态，应用崩溃不影响                               │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  场景分析:                                                                   │
│                                                                             │
│  ┌─────────────────────┬─────────────────────────────────────────────────┐ │
│  │       场景          │  数据是否丢失                                    │ │
│  ├─────────────────────┼─────────────────────────────────────────────────┤ │
│  │ 应用崩溃（JVM 退出）│  ❌ 不丢失 - 数据已在 PageCache（内核态）          │ │
│  ├─────────────────────┼─────────────────────────────────────────────────┤ │
│  │ 系统崩溃/断电       │  ⚠️ 可能丢失 - PageCache 中未刷盘的数据           │ │
│  ├─────────────────────┼─────────────────────────────────────────────────┤ │
│  │ 正常关机            │  ❌ 不丢失 - 关机前 OS 会 flush 所有 PageCache   │ │
│  └─────────────────────┴─────────────────────────────────────────────────┘ │
│                                                                             │
│  关键点: PageCache 属于内核态内存，应用崩溃不会影响内核数据                   │
│                                                                             │

```

**刷盘模式与数据安全**：

| 刷盘模式 | 应用崩溃 | 系统崩溃/断电 | 说明 |
|----------|----------|---------------|------|
| **ASYNC_FLUSH**（异步刷盘） | ✅ 安全 | ⚠️ 可能丢失 | 依赖 OS 定期刷盘，延迟约 5s |
| **SYNC_FLUSH**（同步刷盘） | ✅ 安全 | ✅ 安全 | 每次写入都强制 fsync |

> **📌 为什么应用崩溃数据不丢失？**
>
> PageCache 位于**内核态内存**，由操作系统管理。当应用（JVM）崩溃时：
> 1. 应用进程退出，但内核继续运行
> 2. PageCache 中的数据仍然存在
> 3. 操作系统会继续完成异步刷盘
> 4. 下次启动时，数据可从磁盘正常恢复
>
> 这也是 RocketMQ 在 ASYNC_FLUSH 模式下，应用崩溃不丢数据的原因。

### 2.5 PageCache 内存释放时机

理解 PageCache 内存的释放机制，有助于分析 RocketMQ 的内存使用行为和优化策略。

#### 2.5.1 操作系统层面的释放机制

PageCache 内存释放由操作系统内核管理，主要有以下触发时机：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Page Cache 内存释放时机                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. 内存压力触发（被动）                                                      │
│     ┌──────────────────────────────────────────────────────────────────┐   │
│     │  系统内存不足 → 内核 LRU 算法 → 选择"干净"页面释放                    │   │
│     │  (脏页需先刷盘才能释放)                                             │   │
│     └──────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  2. 显式系统调用（主动）                                                      │
│     ┌──────────────────────────────────────────────────────────────────┐   │
│     │  munmap()     → 解除映射，Page Cache 引用计数减一                   │   │
│     │  fadvise()    → 告知内核访问模式，可释放缓存                         │   │
│     │  msync()      → 刷脏页，使页面变为"干净"可回收状态                   │   │
│     └──────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  3. 进程终止                                                                 │
│     ┌──────────────────────────────────────────────────────────────────┐   │
│     │  进程退出 → 自动 munmap 所有映射 → Page Cache 引用计数归零           │   │
│     └──────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 2.5.2 引用计数机制

每个 Page Cache 页面维护一个引用计数（`_count`），这是理解内存释放的关键：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Page Cache 引用计数机制                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  mmap 映射文件时：                                                           │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  file_channel.map() → 页面加入 Page Cache → _count++                 │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  munmap 解除映射时：                                                         │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  munmap() → _count-- → 若 _count == 0 且页面干净 → 可被回收           │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  多进程 mmap 同一文件：                                                      │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  进程A mmap → _count = 1                                             │   │
│  │  进程B mmap → _count = 2                                             │   │
│  │  进程A munmap → _count = 1 (不能释放)                                 │   │
│  │  进程B munmap → _count = 0 (可以释放)                                 │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 2.5.3 Page Cache 可释放的充要条件

Page Cache 页面可被释放需同时满足以下条件：

| 条件 | 说明 |
|------|------|
| **引用计数 _count == 0** | 所有 mmap 该页面的进程都已 munmap |
| **页面状态为"干净"** | 脏页必须先刷盘（sync/fsync）才能释放 |
| **没有被 mlock 锁定** | mlock 会阻止页面被换出或回收 |
| **内核决定回收** | 即使满足上述条件，也需内核实际执行回收 |

> **📌 重要：munmap ≠ 立即释放**
>
> `munmap` 只是让 Page Cache **可以被释放**，并不保证立即释放。实际释放时机由内核的内存管理策略决定。当系统内存充足时，Page Cache 可能长期保留；当内存紧张时，内核会通过 LRU 算法回收"干净"页面。

#### 2.5.4 RocketMQ 的实现方式

RocketMQ 通过 **swapMap** 清理 Page Table，释放内核内存，详见 [八、内存映射交换 (swapMap)](#八内存映射交换-swapmap)。

```java
// MappedFile#swapMap 核心逻辑
public void swapMap() {
    // 1. 保存旧映射引用
    MappedByteBuffer oldMappedByteBuffer = this.mappedByteBuffer;
    
    // 2. 重新映射文件（创建新的 MappedByteBuffer）
    this.mappedByteBuffer = this.fileChannel.map(
        FileChannel.MapMode.READ_ONLY, 0, fileSize);
    
    // 3. 释放旧映射（触发 Cleaner 执行 munmap）
    UtilAll.cleanBuffer(oldMappedByteBuffer);
}
```

**swapMap 的真正价值：清理 Page Table**

> **📌 重要：swapMap 不减少虚拟地址空间**
>
> swapMap 对单个文件执行后，虚拟地址空间不变（释放旧映射 + 创建新映射，净变化为 0）。其真正价值是**清理 Page Table 条目**，释放内核内存。

| 概念 | swapMap 效果 | 说明 |
|------|-------------|------|
| **虚拟地址空间** | 不变 | 释放 1GB + 分配 1GB = 净变化 0 |
| **Page Table 条目** | 清空 | 旧映射的 PTE 被释放，新映射尚未访问 |
| **内核内存** | 减少 | Page Table 是内核内存，无法被 swap |

**为什么需要清理 Page Table？**

1GB 文件被完全访问后，会创建约 262144 个 Page Table 条目（1GB / 4KB），占用约 2MB 内核内存。长期运行的 Broker 累积大量文件，Page Table 占用的内核内存会持续增长。swapMap 通过重新映射清理旧的 Page Table，释放内核内存。

## 三、Page Table 核心概念

Page Table（页表）是操作系统内存管理的核心数据结构，用于将虚拟地址翻译为物理地址。理解 Page Table 对于深入理解 mmap、缺页中断、swapMap 等机制至关重要。

### 3.1 什么是 Page Table

**Page Table（页表）** 是操作系统内核维护的数据结构，记录**虚拟地址到物理地址的映射关系**。当程序访问虚拟地址时，CPU 通过 Page Table 找到对应的物理内存位置。

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Page Table 在内存管理中的位置                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   程序访问内存的完整路径：                                                    │
│                                                                             │
│   ┌──────────────┐                                                          │
│   │   程序代码    │   int x = *ptr;   // ptr = 0x7f1234567890              │
│   │  (虚拟地址)   │                                                      │
│   └──────────────┘                                                          │
│          │                                                                  │
│          │ CPU 执行指令，访问虚拟地址                                        │
│          ▼                                                                  │
│   ┌──────────────┐                                                          │
│   │     MMU      │   Memory Management Unit (内存管理单元)                  │
│   │  (硬件组件)   │   位于 CPU 内部，负责地址翻译                            │
│   └──────────────┘                                                          │
│          │                                                                  │
│          │ 查询 Page Table                                                  │
│          ▼                                                                  │
│   ┌──────────────────────────────────────────────────────────────────────┐ │
│   │                        Page Table (页表)                              │ │
│   │  ┌─────────────────────────────────────────────────────────────────┐ │ │
│   │  │  虚拟页号 (VPN)  │  物理页帧号 (PFN)  │  权限位  │  状态位      │ │ │
│   │  ├─────────────────────────────────────────────────────────────────┤ │ │
│   │  │   0x7f12345     │     0x8A3BC       │  RW-    │  Present=1   │ │ │
│   │  │   0x7f12346     │     0x8A3BD       │  RW-    │  Present=1   │ │ │
│   │  │   0x7f12347     │     (未分配)       │  ---    │  Present=0   │ │ │
│   │  │      ...        │        ...         │  ...    │     ...      │ │ │
│   │  └─────────────────────────────────────────────────────────────────┘ │ │
│   └──────────────────────────────────────────────────────────────────────┘ │

│          │ 地址翻译成功                                                     │

│   │  (RAM/DIMM)  │   例：0x8A3BC * 4096 + 0x890 = 0x8A3BC890              │
│   └──────────────┘                                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Page Table 的核心组成

每个 Page Table 条目（Page Table Entry, PTE）包含以下关键信息：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Page Table Entry (PTE) 结构                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   64位系统中的 PTE 结构（简化）：                                             │
│                                                                             │
│   ┌───────────────────────────────────────────────────────────────────────┐│
│   │  位范围  │    字段名    │                    说明                      ││
│   ├───────────────────────────────────────────────────────────────────────┤│
│   │  0      │ Present      │ 页面是否在物理内存中 (1=在, 0=不在)          ││
│   │  1      │ Read/Write   │ 写权限 (1=可写, 0=只读)                      ││
│   │  2      │ User/Supervisor│ 访问权限 (1=用户态可访问, 0=仅内核态)       ││
│   │  3      │ Write-Through│ 写透模式（缓存策略）                         ││
│   │  4      │ Cache Disable│ 是否禁用缓存                                 ││
│   │  5      │ Accessed     │ 页面是否被访问过                             ││
│   │  6      │ Dirty        │ 页面是否被修改过（脏页）                      ││
│   │  7      │ Page Size    │ 页面大小（4KB 或大页）                       ││
│   │  8      │ Global       │ 全局页面（不随 CR3 切换而刷新）               ││
│   │  9-11   │ Available    │ 操作系统可用位                               ││
│   │ 12-51   │ Physical Frame│ 物理页帧号（PFN），共 40 位                 ││
│   │ 52-62   │ Available    │ 操作系统可用位                               ││
│   │  63     │ No Execute   │ 禁止执行（NX 位）                            ││
│   └───────────────────────────────────────────────────────────────────────┘│
│                                                                             │
│   关键标志位说明：                                                           │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │  Present=0: 页面不在物理内存，访问时触发 Page Fault                   │  │
│   │  Present=1: 页面在物理内存，可以进行地址翻译                          │  │
│   │  Dirty=1:   页面被修改过，需要刷盘后才能释放                          │  │
│   │  Accessed=1: 页面最近被访问过，LRU 算法参考                           │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.4 Page Table 与 mmap 的关系

mmap 系统调用创建内存映射时，内核会建立 Page Table 条目，但此时页面尚未加载到物理内存：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    mmap 与 Page Table 的交互                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   阶段 1: mmap() 系统调用                                                    │
│   ┌─────────────────────────────────────────────────────────────────────┐  │

│   │  1. 在进程虚拟地址空间分配一段区域                                    │  │
│   │  2. 创建 VMA (Virtual Memory Area) 结构                              │  │
│   │  3. Page Table 条目：Present = 0（页面不在物理内存）                  │  │
│   │  4. 记录映射关系：虚拟地址 ←→ 文件偏移量                              │  │
│   │                                                                     │  │
│   │  注意：此时没有分配物理内存，也没有加载文件数据！                      │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   阶段 2: 首次访问虚拟地址                                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │  CPU 操作：                                                          │  │
│   │  1. 程序访问虚拟地址                                                 │  │
│   │  2. MMU 查询 Page Table                                             │  │
│   │  3. 发现 Present = 0                                                │  │
│   │  4. 触发 Page Fault（缺页中断）                                      │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   阶段 3: Page Fault 处理                                                    │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │  内核操作：                                                          │  │
│   │  1. 检查 VMA，确认这是合法的 mmap 区域                               │  │
│   │  2. 分配物理页帧（从 PageCache 获取或新分配）                         │  │
│   │  3. 从磁盘加载文件页到 PageCache                                     │  │
│   │  4. 更新 Page Table：                                               │  │
│   │     • Physical Frame = 新分配的页帧                                  │  │

│   │     • Dirty = 0（如果是读操作）                                      │  │
│   │  5. 重新执行访问指令                                                 │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   阶段 4: 后续访问                                                           │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │  CPU 操作：                                                          │  │
│   │  1. MMU 查询 Page Table                                             │  │
│   │  2. Present = 1，直接获取物理地址                                    │  │
│   │  3. 访问物理内存（PageCache）                                        │  │
```

```plain
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.7 Page Table 与 RocketMQ 优化

理解 Page Table 有助于理解 RocketMQ 的多项优化：

| 优化手段 | 与 Page Table 的关系 |
|---------|---------------------|
| **mmap** | 创建 Page Table 条目，建立虚拟地址到文件的映射 |
| **缺页中断** | Page Table 中 Present=0 时触发，加载页面到内存 |
| **文件预热** | 主动触发缺页中断，提前建立 Page Table 映射 |
| **swapMap** | 清理旧的 Page Table 条目，释放内核内存 |
| **mlock** | 防止 Page Table 条目对应的页面被换出 |

> **📌 重要：Page Table 是内核内存**
>
> Page Table 存储在内核内存中，无法被 swap 换出。当进程映射大量文件时，Page Table 会持续占用内核内存。这就是 RocketMQ 实现 swapMap 的核心原因——通过重新映射清理旧的 Page Table 条目，释放宝贵的内核内存资源。

## 四、mmap 内存映射

mmap（Memory-mapped file）将文件映射到进程的虚拟地址空间，实现**用户态直接访问文件数据**，无需系统调用，是 RocketMQ 实现高性能存储的核心技术。

### 4.1 原理概述

### 4.2 缺页中断原理

mmap 建立映射后，页面并未实际加载到内存。首次访问时触发缺页中断，由操作系统将页面从磁盘加载到 PageCache：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    mmap 缺页中断流程                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. mmap() 系统调用                                                         │
│     ┌──────────────┐                                                        │
│     │ 进程虚拟地址空间│  ←── 只建立映射关系，不加载实际数据                      │
│     └──────────────┘                                                        │
│            ↓                                                                │
│  2. 第一次访问某页面（读/写）                                                  │
│     ┌──────────────┐                                                        │
│     │ CPU 发现页面  │  ←── 页表项无效，该页不在物理内存中                        │
│     │ 不在物理内存  │                                                        │
│     └──────────────┘                                                        │
│            ↓                                                                │
│  3. 触发缺页中断（Page Fault）                                                │
│     ┌──────────────┐      ┌──────────────┐                                  │
│     │   操作系统    │ ───→ │ 从磁盘加载页面 │ ───→ PageCache                   │
│     │  处理中断     │      │  到物理内存    │                                  │
│     └──────────────┘      └──────────────┘                                  │
│            ↓                                                                │
│  4. 建立页表映射                                                             │
│     ┌──────────────┐                                                        │
│     │ 虚拟地址 ───→ │  ←── 更新页表，指向 PageCache 中的物理页                  │
│     │   物理内存    │                                                        │
│     └──────────────┘                                                        │
│            ↓                                                                │
│  5. 继续执行                                                                 │
│     ┌──────────────┐                                                        │
```

**对比：新文件 vs 已存在文件**：

| 场景 | mmap 时 | 第一次访问时 | 说明 |
|------|---------|--------------|------|
| **新创建文件** | 建立映射 | 无缺页中断（预热已加载） | `warmMappedFile()` 提前触发缺页并写入 0 |
| **已存在文件** | 建立映射 | **触发缺页中断** | 按需从磁盘加载到 PageCache |

#### 4.2.1 内存按页分配机制

mmap 映射后的内存分配（无论是虚拟内存还是物理内存），**全程都是按操作系统的"页（Page）"来分配的**——这是理解 swapMap 为什么能"低成本建新 MMap、高性价比释放旧 MMap"的核心前提。

**操作系统的页是内存分配的最小单位**：

| 概念 | 说明 |
|------|------|
| **页大小** | Linux 系统默认页大小是 **4KB**（可用 `getconf PAGESIZE` 命令查看） |
| **RocketMQ 定义** | `OS_PAGE_SIZE = 4 * 1024`（源码常量，与系统一致） |
| **分配规则** | 所有内存分配/释放、MMap 映射，**都必须是页大小的整数倍** |

**MMap 映射的内存分配过程**：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    MMap 内存分配：虚拟内存先分配，物理内存按需分页分配          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. 虚拟内存：映射时一次性分配（无成本）                                       │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  执行 fileChannel.map(READ_WRITE, 0, 1G) 时：                         │  │
│  │  • 操作系统一次性分配 1G 连续的虚拟内存地址（虚拟内存几乎无成本）        │  │
│  │  • 这些虚拟内存被分成 262144 个 4KB 的页                               │  │
│  │  • 此时**没有分配任何物理内存**                                        │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                              ↓                                              │
│  2. 物理内存："缺页中断"触发按需分配（核心）                                   │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  线程读写某个 4KB 页的地址时：                                         │  │
│  │  • 操作系统发现该页没有对应的物理内存 → 触发**缺页中断**               │  │
│  │  • 操作系统从空闲物理内存中分配 1 个 4KB 页                           │  │
│  │  • 冷文件的 MMap 只有少量页被分配物理内存                              │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  示例：1GB CommitLog 文件                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  • 总页数: 1GB / 4KB = 262,144 页                                     │  │
│  │  • 虚拟内存: 映射时一次性分配 262,144 个虚拟页                         │  │
│  │  • 物理内存: 按需分配，只分配实际访问的页                              │  │
│  │  • 冷文件: 可能只有前 100 页被分配物理内存（400KB）                    │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**按页分配对 swapMap 的意义**：

| 特性 | 说明 |
|------|------|
| **低成本建新 MMap** | 新 MMap 只分配虚拟页，无物理页分配，不会导致内存翻倍 |
| **精准释放旧 MMap** | 按页回收已分配的物理页，冷文件释放极快 |
| **物理内存不翻倍** | 旧 MMap 回收的物理页，刚好可以供新 MMap 按需使用 |

**RocketMQ 源码中对"页"的适配**：

在 `DefaultMappedFile` 中，多处逻辑都是按页设计的：

```java
// 判断是否需要刷盘：按页计算未刷盘的页数
protected boolean isAbleToFlush(final int flushLeastPages) {
    int flush = FLUSHED_POSITION_UPDATER.get(this);
    int write = getReadPosition();
    // 核心：(已写页数 - 已刷页数) ≥ 最小刷盘页数
    return ((write / OS_PAGE_SIZE) - (flush / OS_PAGE_SIZE)) >= flushLeastPages;
}

// 提交数据：按页判断是否需要提交
protected boolean isAbleToCommit(final int commitLeastPages) {
    int commit = COMMITTED_POSITION_UPDATER.get(this);
    int write = WROTE_POSITION_UPDATER.get(this);
    // 核心：按页计算未提交页数
    return ((write / OS_PAGE_SIZE) - (commit / OS_PAGE_SIZE)) >= commitLeastPages;
}
```

这些逻辑的底层，就是因为 MMap 的内存分配/操作都是按页进行的——RocketMQ 必须按页来管控，才能精准控制内存和 IO。

### 4.3 DMA 拷贝说明

无论是传统 IO 还是 mmap，**磁盘与内存之间的数据传输都依赖 DMA（Direct Memory Access）**：

| 方式 | DMA 拷贝时机 | 用户感知 | 阻塞性 |
|------|-------------|----------|--------|
| **传统 IO 读取** | read() 调用时，磁盘→PageCache | 同步等待 | **阻塞**用户进程 |
| **传统 IO 写入** | write() 调用时或后台刷盘 | 可能阻塞 | 可能**阻塞** |
| **mmap 读取** | 首次访问缺页时，磁盘→PageCache | 透明处理 | **阻塞**但无需系统调用 |
| **mmap 写入** | OS 后台刷盘时，PageCache→磁盘 | 完全透明 | **不阻塞**用户进程 |

**mmap 的优势不在于消除 DMA 拷贝，而在于**：
1. **消除 CPU 拷贝**：无需在用户缓冲区和内核缓冲区之间拷贝数据
2. **消除上下文切换**：读写操作无需系统调用
3. **异步刷盘**：写入后立即返回，DMA 拷贝由 OS 后台完成

### 4.4 传统 IO 与 mmap 优劣势对比

| 维度 | 传统 IO (read/write) | mmap 内存映射 | 说明 |
|------|---------------------|---------------|------|
| **CPU 拷贝（读取）** | 1次：PageCache → 用户缓冲区 | **0 次** | mmap 直接访问 PageCache |
| **CPU 拷贝（写入）** | 1次：用户缓冲区 → PageCache | **0 次** | mmap 直接写入 PageCache |
| **CPU 拷贝（总计）** | 读取1次 + 写入1次 = 2次 | **0 次** | mmap 无需在用户/内核缓冲区间拷贝 |
| **DMA 拷贝（读取）** | 1次：磁盘 → PageCache | 1次：磁盘 → PageCache | 两者相同，磁盘IO必须经过DMA |
| **DMA 拷贝（写入）** | 1次：PageCache → 磁盘 | 1次：PageCache → 磁盘 | 两者相同，磁盘IO必须经过DMA |
| **DMA 拷贝（总计）** | 读取1次 + 写入1次 = 2次 | 读取1次 + 写入1次 = 2次 | 两者相同 |
| **上下文切换** | 4 次切换 | **0 次切换** | mmap 映射后读写无需系统调用 |
| **系统调用** | 每次 read/write 都需要 | **仅映射时需要** | mmap 映射后直接访问内存 |
| **内存占用** | 需要用户缓冲区 | **无需额外缓冲区** | mmap 直接操作 PageCache |
| **文件大小限制** | 无限制 | **受地址空间限制** | 32 位系统单次映射最大约 2GB；64 位系统理论上可达 TB 级别 |
| **映射开销** | 无 | **有** | mmap 初始映射需要建立页表 |
| **内存回收** | 自动 GC | **需手动管理** | MappedByteBuffer 无法被 GC 直接回收 |
| **随机访问性能** | 较差 | **优秀** | mmap 随机访问只需内存寻址 |
| **顺序访问性能** | 优秀 | 优秀 | 两者顺序访问性能相当 |
| **多进程共享** | 需要额外机制 | **天然支持** | 多进程映射同一文件可共享数据 |
| **适用场景** | 小文件、低频访问 | **大文件、高频访问** | RocketMQ 选择 mmap 处理大文件存储 |

> **📌 64 位系统地址空间说明**
>
> 64 位系统的虚拟地址空间理论上可达 2^64 字节（约 16 EB），但实际受限于：
> - **Linux x86_64**：用户空间约 128TB（内核默认配置）
> - **Windows x64**：用户模式虚拟地址空间约 8TB
> - **物理内存**：实际可用内存大小
> - **系统资源限制**：`ulimit -v`、`vm.max_map_count` 等参数
>
> RocketMQ 默认 CommitLog 单文件 1GB，在 64 位系统上完全不受地址空间限制。

```java
public void shutdown(final long intervalForcibly) {
    if (this.available) {
        this.available = false;  // 标记为不可用
        this.firstShutdownTimestamp = System.currentTimeMillis();
        this.release();  // 释放初始引用
    } else if (this.getRefCount() > 0) {
        // 强制关闭：超过 intervalForcibly 时间后强制释放
        if ((System.currentTimeMillis() - this.firstShutdownTimestamp) >= intervalForcibly) {
            this.refCount.set(-1000 - this.getRefCount());  // 强制置为负数
            this.release();
        }
    }
}
```

```java
@Override
public boolean cleanup(final long currentRef) {
    // 检查 1: 文件必须已关闭
    if (this.isAvailable()) {
        log.error("this file[REF:" + currentRef + "] " + this.fileName
                + " have not shutdown, stop unmapping.");
        return false;
    }

    // 检查 2: 避免重复清理
    if (this.isCleanupOver()) {
        log.error("this file[REF:" + currentRef + "] " + this.fileName
                + " have cleanup, do not do it again.");
        return true;
    }

    // 执行清理
    UtilAll.cleanBuffer(this.mappedByteBuffer);           // 清理当前映射
    UtilAll.cleanBuffer(this.mappedByteBufferWaitToClean); // 清理待清理映射
    this.mappedByteBufferWaitToClean = null;
    
    // 更新全局统计
    TOTAL_MAPPED_VIRTUAL_MEMORY.addAndGet(this.fileSize * (-1));
    TOTAL_MAPPED_FILES.decrementAndGet();
    
    log.info("unmap file[REF:" + currentRef + "] " + this.fileName + " OK");
    return true;
}
```

```java
    this.shutdown(intervalForcibly);  // 先关闭

        try {
            long lastModified = getLastModifiedTimestamp();
            this.fileChannel.close();  // 关闭文件通道

            boolean result = this.file.delete();  // 删除物理文件
            log.info("delete file[REF:" + this.getRefCount() + "] " + this.fileName
                    + (result ? " OK, " : " Failed, ") + "W:" + this.getWrotePosition() 
                    + " M:" + this.getFlushedPosition() + ", "
                    + UtilAll.computeElapsedTimeMilliseconds(beginTime)
                    + "," + (System.currentTimeMillis() - lastModified));
        } catch (Exception e) {
            log.warn("close file channel " + this.fileName + " Failed. ", e);
        }
        return true;
    } else {
        log.warn("destroy mapped file[REF:" + this.getRefCount() + "] " + this.fileName
                + " Failed. cleanupOver: " + this.cleanupOver);

    return false;
```

#### 4.8.5 UtilAll.cleanBuffer() 实现

`UtilAll.cleanBuffer()` 是释放 MappedByteBuffer 的关键方法：

源码位置 - [UtilAll.java](../../common/src/main/java/org/apache/rocketmq/common/UtilAll.java)：

```java
public static void cleanBuffer(final ByteBuffer buffer) {
    if (buffer == null || !buffer.isDirect() || buffer.capacity() == 0) {
        return;
    }
    invoke(invoke(viewed(buffer), "cleaner"), "clean");
}

private static Object invoke(final Object target, final String methodName, 
                             final Class<?>... args) {
    return AccessController.doPrivileged((PrivilegedAction<Object>) () -> {
        try {
            Method method = target.getClass().getMethod(methodName, args);
            method.setAccessible(true);
            return method.invoke(target);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    });
}
```

**工作原理**：
1. 获取 DirectByteBuffer 内部的 Cleaner 对象
2. 调用 Cleaner.clean() 方法
3. Cleaner 内部执行 `munmap()` 系统调用，释放映射

> **📌 重要：Java 没有公开的 unmap 方法**
>
> MappedByteBuffer 没有提供公开的 unmap() 方法。RocketMQ 通过反射调用内部 Cleaner 来实现 munmap。这是 Java NIO 的已知限制，官方建议依赖 GC 来清理，但 GC 时机不可控，因此 RocketMQ 选择主动清理。

### 4.11 三种 ByteBuffer 对比

Java NIO 提供了三种 ByteBuffer 实现，RocketMQ 选择 MappedByteBuffer 作为核心存储方案：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    三种 ByteBuffer 的 I/O 读写数据流                          │
```

| 特性 | HeapByteBuffer | DirectByteBuffer | MappedByteBuffer |
|------|----------------|------------------|------------------|
| **内存位置** | JVM 堆 | 堆外内存 | 堆外内存（映射文件） |
| **分配方式** | `ByteBuffer.allocate(size)` | `ByteBuffer.allocateDirect(size)` | `fileChannel.map(...)` |
| **分配/释放成本** | 低（JVM 管理） | 高（系统调用） | 高（系统调用 + 页表映射） |
| **内存大小限制** | 受 JVM 堆限制 | 受物理内存限制 | 受进程地址空间限制（32 位约 2GB/次；64 位可达 TB 级别） |
| **GC 管理** | ✅ 是 | ❌ 否（需手动释放） | ❌ 否 |
| **I/O 拷贝** | 需拷贝到临时 DirectBuffer | 直接使用 | 直接使用 |
| **与 PageCache 关系** | 隔离 | 隔离 | **共享** |
| **数据持久性** | 无（进程结束丢失） | 无（进程结束丢失） | **有**（映射到文件） |
| **多进程共享** | ❌ 否 | ❌ 否 | ✅ 是（映射同一文件） |
| **适用场景** | 短生命周期、小数据 | 高频 I/O、大数据 | **大文件读写（RocketMQ 选择）** |

> **📌 HeapByteBuffer 的 I/O 拷贝问题**
>
> 当使用 HeapByteBuffer 进行 I/O 操作时，JVM 必须先将数据拷贝到临时 DirectBuffer：
>
> ```
> HeapByteBuffer (JVM 堆) ──拷贝──► 临时 DirectBuffer (堆外) ──系统调用──► PageCache ──► 磁盘
> ```
>
> **原因**：JVM 堆内存可能被 GC 移动，而操作系统 I/O 需要稳定的内存地址。因此 JVM 必须先将数据拷贝到堆外内存（DirectBuffer），再通过系统调用写入 PageCache。
>
> **对比**：
> - **DirectByteBuffer**：在堆外，可直接进行系统调用，但仍需 CPU 拷贝到 PageCache
> - **MappedByteBuffer**：与 PageCache 共享物理内存，无需任何拷贝

**为什么 RocketMQ 选择 MappedByteBuffer？**

1. **零拷贝**：直接映射 PageCache，无需数据拷贝
2. **持久化**：数据映射到磁盘文件，进程崩溃不丢失
3. **多进程共享**：主从同步时可以共享同一文件映射
4. **大文件支持**：CommitLog 文件固定 1GB，适合映射

## 五、mlock 内存锁定

mlock 将进程的虚拟内存区域锁定在物理内存中，**防止被操作系统 swap 到磁盘**，保证热点数据的访问性能，常与 madvise 组合使用以优化内存访问。

### 5.1 原理概述

通过 mlock 锁定的内存区域将始终驻留物理内存，不会被操作系统换出到 Swap 分区，从而保证热点数据的访问延迟稳定。

```plain

├─────────────────────────────────────────────────────────────────────────────┤

│  │                         物理内存 (RAM)                                │  │
│  │    ┌────────────────────────────────────────────────────────────┐   │  │
│  │    │  普通内存区域（可能被 swap 换出）                             │   │  │
│  │    └────────────────────────────────────────────────────────────┘   │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                          ↕ 可能被 swap 换入/换出                             │

│  │                         Swap 分区 (磁盘)                              │  │
```

> │  │                                                                       │  │

> │                                                                             │
> │  优点: 无需编写 C 代码，只需定义接口，JNA 自动完成映射                         │
> │                                                                             │

> ```
>
> **JNA 工作原理**：
>
> | 步骤 | 说明 |
> |------|------|
> | 1. 定义接口 | 继承 `Library`，声明与 C 库函数签名匹配的方法 |
> | 2. 加载库 | `Native.loadLibrary()` 加载操作系统动态库 |
> | 3. 动态代理 | JNA 运行时生成接口的代理实现类 |
> | 4. 方法映射 | 根据方法名自动查找对应的 C 函数 |
> | 5. 类型转换 | 自动处理 Java 类型与 C 类型的转换 |
>
> **类型映射**：
>
> | Java 类型 | C 类型 | 说明 |
> |-----------|--------|------|
> | `Pointer` | `void*` | 通用指针 |
> | `NativeLong` | `long` | 平台相关的长整型 |
> | `int` | `int` | 整型 |

源码位置 - [DefaultMappedFile.java](../../store/src/main/java/org/apache/rocketmq/store/logfile/DefaultMappedFile.java)：

```java
public void mlock() {
    final long beginTime = System.currentTimeMillis();
    // 获取 MappedByteBuffer 的物理内存地址
    final long address = ((DirectBuffer) (this.mappedByteBuffer)).address();
    Pointer pointer = new Pointer(address);
    
    // 1. 锁定内存，防止被 swap 换出到磁盘
    int ret = LibC.INSTANCE.mlock(pointer, new NativeLong(this.fileSize));
    
    // 2. 建议内核预加载该区域到 PageCache
    ret = LibC.INSTANCE.madvise(pointer, new NativeLong(this.fileSize), 
                                LibC.MADV_WILLNEED);
}
```

### 5.3 系统调用详解

mlock 和 madvise 都是 Linux/Unix 操作系统提供的**系统调用**函数：

#### 5.3.1 mlock 系统调用

| 属性 | 说明 |
| --- | --- |
| **头文件** | `#include <sys/mman.h>` |
| **函数签名** | `int mlock(const void *addr, size_t len)` |
| **功能** | 将指定内存区域锁定在物理内存中，防止被 swap 到磁盘 |
| **返回值** | 成功返回 0，失败返回 -1 |
| **权限要求** | 需要 `CAP_IPC_LOCK` 权限或 root 权限 |

相关系统调用：

```c
// 锁定指定内存区域
int mlock(const void *addr, size_t len);

// 锁定进程的所有内存
int mlockall(int flags);

// 解锁内存
int munlock(const void *addr, size_t len);
int munlockall(void);
```

#### 5.3.2 madvise 系统调用

| 属性 | 说明 |
| --- | --- |
| **头文件** | `#include <sys/mman.h>` |
| **函数签名** | `int madvise(void *addr, size_t length, int advice)` |
| **功能** | 向内核提供内存区域的使用建议，让内核优化内存管理策略 |
| **返回值** | 成功返回 0，失败返回 -1 |
| **权限要求** | 无特殊权限要求 |

常用 advice 参数：

```c
// 预加载建议
MADV_WILLNEED    // 告诉内核这部分内存即将被访问，预加载到 PageCache

// 释放建议
MADV_DONTNEED    // 告诉内核这部分内存不再需要，可以释放
MADV_FREE        // 标记内存为可释放（延迟释放，访问时自动恢复）

// 访问模式建议
MADV_SEQUENTIAL  // 顺序访问模式，内核会激进预读
MADV_RANDOM      // 随机访问模式，内核减少预读
MADV_NORMAL      // 默认访问模式
```

#### 5.3.3 mlock vs madvise 对比

| 特性 | mlock | madvise |
| --- | --- | --- |
| **强制性** | 强制锁定，内核必须遵守 | 建议性，内核可以选择忽略 |
| **权限要求** | 需要 `CAP_IPC_LOCK` 或 root | 无特殊权限要求 |
| **内存效果** | 内存不会被 swap | 内存可能被 swap，但内核会优化访问 |
| **典型场景** | 关键热点数据，必须常驻内存 | 预加载、访问模式优化 |

#### 5.3.4 RocketMQ 组合策略

RocketMQ 组合使用 mlock 和 madvise 实现热点数据优化：

1. **mlock** - 确保热点 CommitLog 数据**绝对不会**被 swap
2. **madvise(MADV_WILLNEED)** - 提前触发内核预读，减少首次访问延迟

这种组合策略在消息队列场景中非常有效，因为消息存储对延迟敏感，且访问模式通常有明显的热点区域。

### 5.4 使用场景

| 场景 | 是否启用 | 原因 |
| --- | --- | --- |
| 高吞吐写入 | ✅ 启用 | 热点文件常驻内存，避免缺页中断 |
| 内存紧张 | ⚠️ 谨慎 | 锁定内存会减少可用内存 |
| 多实例部署 | ⚠️ 谨慎 | 需要合理规划锁定内存总量 |

## 六、堆外内存池 (TransientStorePool)

TransientStorePool 是 RocketMQ 提供的**堆外内存池**，用于优化异步刷盘场景的写入性能，通过减少 PageCache 锁竞争实现更高吞吐。

### 6.1 原理概述

### 6.2 核心实现

源码位置 - [TransientStorePool.java](../../store/src/main/java/org/apache/rocketmq/store/TransientStorePool.java)：

```java
public class TransientStorePool {
    private final int poolSize;                       // 池大小，默认 5
    private final int fileSize;                       // 每个缓冲区大小，默认 1GB
    private final Deque<ByteBuffer> availableBuffers; // 可用缓冲区队列
    
    public void init() {
        for (int i = 0; i < poolSize; i++) {
            // 1. 分配堆外内存
            ByteBuffer byteBuffer = ByteBuffer.allocateDirect(fileSize);
            
            // 2. 获取内存地址并锁定，防止被 swap
            final long address = ((DirectBuffer) byteBuffer).address();
            Pointer pointer = new Pointer(address);
            LibC.INSTANCE.mlock(pointer, new NativeLong(fileSize));
            
            // 3. 加入可用队列
            availableBuffers.offer(byteBuffer);
        }
    }
}
```

## 七、文件预热 (warmMappedFile)

> **核心概念**：文件预热仅针对**新创建的空文件**，通过逐页写入 0 触发缺页中断，将页面提前加载到 PageCache，避免运行时缺页延迟。常与 mlock 配合确保热点数据常驻内存。

### 7.1 原理概述

新创建的文件通过 mmap 映射后，页面并未实际加载到内存。通过逐页写入 0 触发缺页中断，让 OS 将页面提前加载到 PageCache，避免首次访问时的磁盘读取延迟。

### 7.2 RocketMQ 实现

> **重要说明**：文件预热仅在**新创建的空文件**上执行（由 AllocateMappedFileService 预分配时调用）。此时文件内容本身就是全 0，写入 0 不会破坏任何数据，目的是触发缺页中断将页面加载到 PageCache。

文件预热通过按 OS_PAGE_SIZE (4KB) 逐页写入 0，触发缺页中断将文件页面加载到 PageCache，预热完成后执行 mlock 锁定内存。

源码位置 - [DefaultMappedFile.java:528-572](../../store/src/main/java/org/apache/rocketmq/store/logfile/DefaultMappedFile.java)：

```java
public void warmMappedFile(FlushDiskType type, int pages) {
    long beginTime = System.currentTimeMillis();
    ByteBuffer byteBuffer = this.mappedByteBuffer.slice();
    int flush = 0;
    
    // 按 OS_PAGE_SIZE (4KB) 逐页写入 0，触发缺页加载到 PageCache
    for (int i = 0, j = 0; i < this.fileSize; i += OS_PAGE_SIZE, j++) {
        byteBuffer.put(i, (byte) 0);  // 写入 0 触发缺页
        
        // 同步刷盘模式：每 pages 页强制刷盘一次
        if (type == FlushDiskType.SYNC_FLUSH) {
            if ((i / OS_PAGE_SIZE) - (flush / OS_PAGE_SIZE) >= pages) {
                flush = i;
                mappedByteBuffer.force();
            }
        }
        
        // 每 1000 次让出 CPU，防止长时间占用
        if (j % 1000 == 0) {
            Thread.sleep(0);
        }
    }
    
    // 同步刷盘模式：预热完成后强制刷盘
    if (type == FlushDiskType.SYNC_FLUSH) {
        mappedByteBuffer.force();
    }
    
    // 预热完成后执行 mlock，锁定内存防止被 swap
    this.mlock();
}
```

### 7.3 配置参数

源码位置 - [MessageStoreConfig.java](../../store/src/main/java/org/apache/rocketmq/store/config/MessageStoreConfig.java)：

| --- | --- | --- |

| `flushLeastPagesWhenWarmMapedFile` | 4096 页（约 16MB） | 预热时每次刷盘的页数，每页 4KB（仅同步刷盘模式生效） |

> **📌 `flushLeastPagesWhenWarmMapedFile` 参数详解**
>
> 该参数**仅在同步刷盘模式（SYNC_FLUSH）下生效**，用于控制预热过程中每隔多少页执行一次 `force()` 刷盘操作。
>
> **执行流程**：
> ```plain
> 写入 Page 0     → 累计 1 页
> 写入 Page 1     → 累计 2 页
> ...
> 写入 Page 4095  → 累计 4096 页 → 执行 force() 刷盘
> 写入 Page 4096  → 累计 1 页（重新计数）
> ...
> ```
>
> **设计目的**：
>
> | 目的 | 说明 |
> |------|------|
> | **分批刷盘** | 避免预热完成后一次性刷盘 1GB 数据导致大延迟 |
> | **平滑 I/O 压力** | 将刷盘操作分散到预热过程中，减少 I/O 峰值 |
> | **数据安全** | 同步刷盘模式下确保数据及时落盘 |
>
> **计算示例**：
> - 默认值：4096 页
> - 每页大小：4KB（OS_PAGE_SIZE）
> - 每次刷盘数据量：4096 × 4KB = **16MB**
> - 1GB CommitLog 预热时刷盘次数：1024MB ÷ 16MB = **64 次**
>
> **异步刷盘模式（ASYNC_FLUSH）**：不执行中间刷盘，预热完成后统一由 OS 异步刷盘。

### 7.4 预热时机

文件预热在 `AllocateMappedFileService` 创建新文件时触发：

```java
    && warmMapedFileEnable) {
```

### 7.5 已存在文件不预热

**Broker 重启加载已存在文件时，不会执行预热**。

源码位置 - [MappedFileQueue.java:161-180](../../store/src/main/java/org/apache/rocketmq/store/MappedFileQueue.java)：

```java

    for (File file : files) {
        // 直接创建 MappedFile，没有调用 warmMappedFile()
        MappedFile mappedFile = new DefaultMappedFile(file.getPath(), mappedFileSize);
        mappedFile.setWrotePosition(this.mappedFileSize);
        mappedFile.setFlushedPosition(this.mappedFileSize);
        mappedFile.setCommittedPosition(this.mappedFileSize);
        this.mappedFiles.add(mappedFile);
    }
    return true;
}
```

**设计原因**：

| 场景 | 是否预热 | 原因 |
|------|----------|------|
| 新创建文件 | ✅ 是 | 新文件内容为空，预热可提前加载到 PageCache |
| 已存在文件 | ❌ 否 | 文件已有数据，预热需遍历整个文件，启动耗时长 |

不预热已存在文件的合理性：
1. **启动时间**：预热需要遍历整个文件写入 0，大文件耗时较长
2. **数据已存在**：已存在文件通常已被访问过，PageCache 可能已有缓存
3. **按需加载**：读取时触发缺页中断，按需加载到 PageCache

> **📌 缺页中断原理**
>
> 已存在文件第一次读取时会触发缺页中断，这是 mmap 内存映射的核心机制。详见 [3.2 缺页中断原理](#32-缺页中断原理)。

```java
private boolean mmapOperation() {
    // 从队列获取预分配请求
    AllocateRequest req = this.requestQueue.take();
    
    if (req.getMappedFile() == null) {
        long beginTime = System.currentTimeMillis();
        
        MappedFile mappedFile;
        // 根据配置选择是否使用堆外内存池
        if (messageStore.getMessageStoreConfig().isTransientStorePoolEnable()) {
            mappedFile = new DefaultMappedFile(req.getFilePath(), 
                req.getFileSize(), messageStore.getTransientStorePool());
        } else {
            mappedFile = new DefaultMappedFile(req.getFilePath(), req.getFileSize());
        }
        
        // 文件预热（如果启用）
        if (mappedFile.getFileSize() >= mappedFileSizeCommitLog 
            && warmMapedFileEnable) {
            mappedFile.warmMappedFile(flushDiskType, flushLeastPagesWhenWarmMapedFile);
        }
        
        req.setMappedFile(mappedFile);  // 设置结果
        req.getCountDownLatch().countDown();  // 通知等待线程
    }
    return true;
}
```

## 九、内存映射交换 (swapMap)

内存映射交换（swapMap）是 RocketMQ 的一项关键技术，用于**清理 Page Table 条目**，释放内核内存，特别适用于长期运行、磁盘数据量大的 Broker 实例。

> **📌 前置知识**：理解 swapMap 需要先理解虚拟地址与物理地址的关系，以及 mmap 多次映射同一文件的行为。详见 [三、Page Table 核心概念 - 3.8 虚拟地址与物理地址](#38-虚拟地址与物理地址)。

### 9.1 内存映射交换的必要性

在长期运行的 RocketMQ Broker 中，随着消息的不断写入和消费，会产生大量内存映射相关的资源消耗。由于 RocketMQ 使用 mmap 将磁盘文件映射到虚拟内存，当文件被访问时，内核会创建 Page Table 条目来记录虚拟地址到物理页的映射关系。

这种机制虽然提升了 I/O 性能，但也带来了长期运行的内存压力问题：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    问题：Page Table 占用内核内存                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  每个 1GB 文件被完全访问后：                                                  │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  • 页数量: 1GB / 4KB = 262,144 页                                    │   │
│  │  • Page Table 条目: 262,144 个 PTE                                   │   │
│  │  • 每个 PTE 约 8 字节                                                │   │
│  │  • Page Table 内存: 262,144 × 8 ≈ 2MB                               │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  1000 个文件累积：                                                           │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  • Page Table 内存: 1000 × 2MB = 2GB                                │   │
│  │  • 这是内核内存，无法被 swap                                          │   │
│  │  • 长期运行会持续增长                                                 │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**核心问题**：旧文件的 Page Table 条目无法被常规手段清理，原因如下：

| 尝试方案 | 问题描述 |
|----------|----------|
| **删除旧文件** | 文件可能还需要被消费者读取（消息回溯、延迟消费等场景） |
| **手动 munmap** | MappedByteBuffer 没有 public 的 munmap 方法，Java 无法直接释放 |
| **等待 GC** | MappedByteBuffer 在堆外，GC 无法回收 Page Table |

**后果**：长期运行的 Broker 内核内存占用持续增长，可能导致系统稳定性问题。

### 9.2 swapMap 解决方案

swapMap 采用**重新映射**的方式清理 Page Table，这是一种巧妙的技术手段，能够在不影响文件数据访问的前提下释放内核内存：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    swapMap 解决思路                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  传统方式（无法实现）:                                                        │
│  ┌────────────────────────────────────────────────────────────────────┐    │
│  │  mappedByteBuffer.unmap()  ← Java 没有这个方法！                    │    │
│  └────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  swapMap 方式（可行）:                                                       │
│  ┌────────────────────────────────────────────────────────────────────┐    │
│  │  1. 保存旧映射引用: oldBuffer = mappedByteBuffer                    │    │
│  │  2. 重新映射文件:   mappedByteBuffer = fileChannel.map(...)        │    │
│  │  3. 延迟释放旧映射: UtilAll.cleanBuffer(oldBuffer)  // 调用 Cleaner │    │
│  └────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  关键点：                                                                    │
│  • 虚拟地址空间不变（释放旧映射 + 创建新映射，净变化为 0）                     │
│  • Page Table 条目被清空（旧映射的 PTE 释放，新映射尚未访问）                  │
│  • 内核内存减少（Page Table 是内核内存）                                     │
│  • 文件数据不受影响，只是映射关系变化                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**swapMap 效果对比**：

| 资源类型 | swapMap 执行前 | swapMap 执行后 | 变化结果 |
|----------|----------------|----------------|----------|
| **虚拟地址空间** | 1GB | 1GB | 不变 |
| **Page Table 条目** | 262,144 个 | 0 个 | 完全清空 |
| **内核内存占用** | ~2MB | ~0 | 显著减少 |
| **Page Cache 数据** | 保留 | 保留 | 不受影响 |

> **📌 为什么新映射不立即占用 Page Table？**
>
> 关键点：**新映射不会立即创建 Page Table 条目**，只有首次访问时才会建立。
>
> ```plain
> ┌─────────────────────────────────────────────────────────────────────────────┐
> │                    swapMap 前后 Page Table 变化                              │
> ├─────────────────────────────────────────────────────────────────────────────┤
> │                                                                             │
> │  swapMap 前：                                                                │
> │  ┌──────────────────────────────────────────────────────────────────────┐  │
> │  │  旧映射 (mappedByteBuffer)                                            │  │
> │  │  • 虚拟地址: 0x7f0000000000                                           │  │
> │  │  • Page Table 条目: 262,144 个 (1GB ÷ 4KB)                           │  │
> │  │  • 内核内存占用: ~2MB                                                 │  │
> │  │  • 状态: 已访问过，Page Table 已完全建立                               │  │
> │  └──────────────────────────────────────────────────────────────────────┘  │
> │                                                                             │
> │  swapMap 后：                                                                │
> │  ┌──────────────────────────────────────────────────────────────────────┐  │
> │  │  新映射 (mappedByteBuffer)                                            │  │
> │  │  • 虚拟地址: 0x7f0000010000 (新地址)                                  │  │
> │  │  • Page Table 条目: 0 个 ← 关键！                                    │  │
> │  │  • 内核内存占用: 0                                                    │  │
> │  │  • 状态: 未访问，Page Table 未建立                                    │  │
> │  └──────────────────────────────────────────────────────────────────────┘  │
> │                                                                             │
> │  旧映射 (mappedByteBufferWaitToClean)                                       │
> │  ┌──────────────────────────────────────────────────────────────────────┐  │
> │  │  • 等待 120 秒后被 cleanSwapedMap() 释放                              │  │
> │  │  • 释放后，Page Table 条目被清理，回收 2MB 内核内存                    │  │
> │  └──────────────────────────────────────────────────────────────────────┘  │
> │                                                                             │
> └─────────────────────────────────────────────────────────────────────────────┘
> ```
>
> **mmap 与 Page Table 的关系**：
>
> | 阶段 | Page Table 状态 | 详细说明 |
> |------|----------------|------------|
> | mmap() 时 | Present = 0 | 条目存在但标记为"不在物理内存"，等待首次访问 |
> | 首次访问时 | Present = 1 | 触发 Page Fault，建立真正的内存映射 |
| swapMap 后 | 无条目 | 新映射未访问，不占用任何 Page Table 条目 |
>
> **核心收益**：对于**长期不访问的冷文件**，swapMap 可以释放其 Page Table，节省内核内存。如果文件再次被访问，Page Table 会按需重新建立。

**问题与解决方案对照表**：

| 问题类型 | 具体问题 | swapMap 解决方案 |
|----------|----------|------------------|
| 内存占用 | Page Table 占用内核内存 | 清理旧的 Page Table 条目，释放内核内存 |
| 长期运行 | 内存占用持续增长 | 对不活跃文件执行 swapMap，控制内核内存增长 |
| 资源管理 | 无法手动释放映射 | 通过重新映射 + Cleaner 机制间接释放 |
| 数据规模 | 磁盘数据量大 | 按需重建 Page Table，冷数据不占用内核内存 |

### 9.3 触发时机与策略

swapMap 由 `MappedFileQueue.swapMap()` 方法统一调度，遍历所有映射文件并检查是否满足交换条件。该机制采用了智能化的触发策略，确保在合适的时机执行内存映射交换操作。

**核心源码实现** - [MappedFileQueue.java:658-686](../../store/src/main/java/org/apache/rocketmq/store/MappedFileQueue.java)：

```java
@Override
public void swapMap(int reserveNum, long forceSwapIntervalMs, long normalSwapIntervalMs) {
    if (mappedFiles.isEmpty()) {
        return;
    }

    if (reserveNum < 3) {
        reserveNum = 3;  // 最少保留 3 个文件，确保系统稳定性
    }

    Object[] mfs = this.copyMappedFiles(0);
    if (null == mfs) {
        return;
    }

    // 从旧到新遍历，跳过最后 reserveNum 个文件（保护热点文件）
    for (int i = mfs.length - reserveNum - 1; i >= 0; i--) {
        MappedFile mappedFile = (MappedFile) mfs[i];
        
        // 条件1: 强制交换 - 超过强制间隔时间
        if (System.currentTimeMillis() - mappedFile.getRecentSwapMapTime() > forceSwapIntervalMs) {
            mappedFile.swapMap();
            continue;
        }
        
        // 条件2: 正常交换 - 超过正常间隔时间 且 有访问记录
        if (System.currentTimeMillis() - mappedFile.getRecentSwapMapTime() > normalSwapIntervalMs
                && mappedFile.getMappedByteBufferAccessCountSinceLastSwap() > 0) {
            mappedFile.swapMap();
            continue;
        }
    }
}
```

**访问计数机制详解**：

`mappedByteBufferAccessCountSinceLastSwap` 记录自上次 swapMap 以来的访问次数，用于判断文件的活跃程度：

| 访问方法 | 计数变化 | 触发场景 |
|----------|----------|----------|
| `getMappedByteBuffer()` | +1 | 获取映射缓冲区进行读写操作 |
| `sliceByteBuffer()` | +1 | 创建切片缓冲区用于特定区域访问 |
| `selectMappedBuffer()` | +1 | 选择指定范围的缓冲区进行操作 |
| `swapMap()` 执行时 | 重置为 0 | 每次执行交换后清零计数器 |

> **📌 设计意图**：正常交换条件 `accessCount > 0` 确保只处理**有访问但访问频率不高**的文件。对于完全没有访问的文件，依赖强制交换条件处理。

**swapMap 与文件删除的关系**：

swapMap 在文件存在期间执行，与文件删除是独立的两个操作：


**为什么在文件删除前执行 swapMap？**

| 场景 | 不执行 swapMap | 执行 swapMap |
|------|---------------|--------------|
| Broker 运行 30 天，累积 1000 个文件 | Page Table 占用 2GB 内核内存 | 仅保留热点文件，约 200MB |
| 文件保留策略 72 小时 | 文件未过期前，内核内存持续占用 | 历史文件及时释放 Page Table |
| 消费者回溯消费 | 无影响 | 文件仍可访问，Page Table 按需重建 |

### 9.4 核心实现机制

swapMap 的核心功能是清理 Page Table 条目，通过重新映射释放旧的 Page Table，从而有效减少内核内存占用。这一过程涉及复杂的并发控制和内存管理机制。

**核心源码实现** - [DefaultMappedFile.java:574-598](../../store/src/main/java/org/apache/rocketmq/store/logfile/DefaultMappedFile.java)：

```java
@Override
public boolean swapMap() {
    // 前置条件检查
    // 1. 引用计数必须为 1（只有自己持有，无其他线程使用）
    // 2. 没有待清理的旧映射（避免重复交换）
    if (getRefCount() == 1 && this.mappedByteBufferWaitToClean == null) {

        if (!hold()) {
            log.warn("in swapMap, hold failed, fileName: " + this.fileName);
            return false;
        }
        try {
            // 1. 保存旧映射引用，等待后续清理
            this.mappedByteBufferWaitToClean = this.mappedByteBuffer;
            
            // 2. 重新映射文件，获得新的虚拟地址
            this.mappedByteBuffer = this.fileChannel.map(
                FileChannel.MapMode.READ_WRITE, 0, fileSize);
            
            // 3. 重置访问计数和交换时间
            this.mappedByteBufferAccessCountSinceLastSwap = 0L;
            this.swapMapTime = System.currentTimeMillis();
            log.info("swap file " + this.fileName + " success.");
            return true;
        } catch (Exception e) {
            log.error("swapMap file " + this.fileName + " Failed. ", e);
        } finally {
            this.release();
        }
    } else {
        log.info("Will not swap file: " + this.fileName + ", ref=" + getRefCount());
    }
    return false;
}
```

### 9.5 清理旧映射机制

swapMap 执行后，旧的映射被安全地保存在 `mappedByteBufferWaitToClean` 中，需要等待一段时间后再进行清理，确保没有任何线程仍在访问旧映射。

**核心清理源码** - [DefaultMappedFile.java:600-620](../../store/src/main/java/org/apache/rocketmq/store/logfile/DefaultMappedFile.java)：

```java
@Override
public void cleanSwapedMap(boolean force) {
    try {
        if (this.mappedByteBufferWaitToClean == null) {
            return;
        }
        
        // 最小等待间隔 120s，确保旧映射不再被访问
        long minGapTime = 120 * 1000L;
        long gapTime = System.currentTimeMillis() - this.swapMapTime;
        
        // 非强制清理时，等待达到最小间隔
        if (!force && gapTime < minGapTime) {
            Thread.sleep(minGapTime - gapTime);
        }
        
        // 释放旧的映射内存
        UtilAll.cleanBuffer(this.mappedByteBufferWaitToClean);
        mappedByteBufferWaitToClean = null;
        log.info("cleanSwapedMap file " + this.fileName + " success.");
    } catch (Exception e) {
        log.error("cleanSwapedMap file " + this.fileName + " Failed. ", e);
    }
}
```

**安全等待时间设计**：

| 等待原因 | 详细说明 |
|----------|----------|
| **安全缓冲** | 确保所有可能持有旧映射引用的线程都有足够时间完成操作 |
| **避免崩溃** | 如果有线程仍在访问已释放的映射，会导致 SIGBUS 等严重错误 |
| **保守策略** | 120秒是基于生产环境验证的经验值，能够覆盖绝大多数场景 |

**swapMap 相关方法协作关系**：

| 方法名称 | 触发时机 | 主要作用 |
|----------|----------|----------|
| `swapMap()` | 文件进入非活跃状态时 | 重新映射到新地址，将旧映射移至待清理状态 |
| `cleanSwapedMap()` | swapMap 执行后 120 秒 | 释放旧映射内存（mappedByteBufferWaitToClean） |
| `cleanup()` | 文件完全销毁时 | 释放所有映射资源，更新全局统计 |

> **📌 cleanup() 方法详解**
>
> `cleanup()` 是 MappedFile 生命周期管理的核心方法，负责安全释放 mmap 映射的内存资源。详见 [4.8 DefaultMappedFile 内存释放机制](#48-defaultmappedfile-内存释放机制)。

#### 9.5.1 swapMap 释放内存的完整链路

swapMap 本身**不直接释放内存**，它只是"把旧 MMap 标记为待清理 + 新建新 MMap 接管读写"，真正的内存释放是由 `cleanSwapedMap()` 方法完成的。整个过程分 4 步：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    swapMap 释放内存的完整链路                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  步骤1: swapMap() 标记旧 MMap 为"待清理"（不释放内存）                        │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  • 把旧 MMap 放到待清理变量中，此时旧 MMap 仍占用内存                  │  │
│  │  • 新建新 MMap 接管读写（新 MMap 会占用新的虚拟内存）                  │  │
│  │  • 物理内存是按需分配的，不会瞬间占用双倍内存                          │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                              ↓                                              │
│  步骤2: 等待 120 秒安全窗口（避免 slice 引用导致崩溃）                       │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  • 确保所有 slice 视图都用完                                          │  │
│  │  • 防止正在使用旧映射的线程触发 SIGBUS 崩溃                            │  │

│  │  • 调用 cleaner.clean() 释放内存                                      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                              ↓                                              │
```

#### 9.5.2 UtilAll.cleanBuffer() 底层原理

`UtilAll.cleanBuffer()` 是 RocketMQ 释放 MMap 内存的"终极方法"，底层调用 JDK 的 `Cleaner` 类（兼容 JDK 8/11/17）：

**核心源码** - [UtilAll.java](../../common/src/main/java/org/apache/rocketmq/common/UtilAll.java)：

```java
public static void cleanBuffer(ByteBuffer buffer) {
    if (buffer == null || !buffer.isDirect()) {
        return;
    }
    try {
        // 1. 获取 MappedByteBuffer 的 Cleaner 对象（负责释放堆外内存）
        Method cleanerMethod = buffer.getClass().getMethod("cleaner");
        cleanerMethod.setAccessible(true);
        Object cleaner = cleanerMethod.invoke(buffer);
        if (cleaner != null) {
            // 2. 调用 cleaner.clean() 释放内存
            Method cleanMethod = cleaner.getClass().getMethod("clean");
            cleanMethod.invoke(cleaner);
        }
    } catch (Exception e) {
        log.error("clean buffer error", e);
    }
}
```

**Cleaner.clean() 的作用**：

| 操作 | 说明 |
|------|------|
| ✅ 释放虚拟内存地址 | MappedByteBuffer 占用的虚拟内存地址被释放 |
| ✅ 通知操作系统回收物理内存 | 对应的物理内存页被标记为可回收 |
| ✅ 解除文件与内存的映射关系 | 文件与内存的映射关系被解除 |

#### 9.5.3 操作系统回收物理内存

当 `clean()` 调用后，JVM 会向操作系统发送 `munmap()` 系统调用：

```c
// 底层 Linux 系统调用（JDK 内部实现）
munmap(addr, length);
```

**操作系统处理流程**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 标记虚拟内存为"未使用" | 把这块虚拟内存标记为"未使用" |
| 2 | 回收物理内存 | 如果没有其他进程引用，回收对应的物理内存 |
| 3 | 内存回归空闲池 | 物理内存会回到系统的"空闲内存池"，供其他进程使用 |

#### 9.5.4 为什么必须用 Cleaner 而不是 GC？

| 对比项 | JVM GC | Cleaner.clean() |
|--------|--------|-----------------|
| **管理范围** | 只管理堆内内存 | 可以管理堆外内存 |
| **触发时机** | 不确定，依赖 GC 周期 | 立即执行，可控 |
| **对 MMap 的效果** | ❌ 无法回收 MMap 的堆外内存 | ✅ 触发 munmap() 系统调用 |
| **适用场景** | 普通 Java 对象 | DirectByteBuffer、MappedByteBuffer |

**核心原因**：MMap 是堆外内存，JVM GC 只管理堆内内存，不会主动回收堆外的 MMap。只有调用 `Cleaner.clean()`，才能主动触发 `munmap()` 系统调用，释放内存。

#### 9.5.5 为什么不能直接释放 MMap 内存？

**技术上可以直接释放**，但在 RocketMQ 生产场景中**绝对不能这么做**——直接释放必出问题，甚至导致 Broker 崩溃。

**问题1：正在使用 slice 视图的线程会触发 SIGBUS 崩溃**

RocketMQ 读消息时，一定会通过 `mappedByteBuffer.slice()` 创建视图：

```java
// 读消息核心代码
ByteBuffer byteBuffer = this.mappedByteBuffer.slice();
byteBuffer.position(pos);
// 返回给上层线程（消费、复制、拉取）
return new SelectMappedBufferResult(fileFromOffset + pos, byteBuffer, size, this);
```

| 问题 | 说明 |
|------|------|
| slice 视图共享底层物理内存地址 | 如果此时直接释放 MMap → 底层物理内存被回收 |
| 线程访问 slice 时 | 操作系统会发送 `SIGBUS` 信号 |
| JVM 收到 SIGBUS 后 | **直接崩溃**（无法捕获、无法恢复），Broker 当场宕机 |

**问题2：读写线程会遇到"空映射"，业务直接中断**

| 问题 | 说明 |
|------|------|
| 直接释放后 | `mappedByteBuffer` 变成"无效映射" |
| 后续读写线程调用 | `mappedByteBuffer.put()`/`get()` 时抛出异常 |
| 业务影响 | 消息生产/消费全部中断，业务报错 |

**唯一安全直接释放的场景**：Broker 停机前的最终清理（`destroy()` 方法中）：

```java
@Override
public boolean destroy(final long intervalForcibly) {
    this.shutdown(intervalForcibly); // 等待所有线程退出
    if (this.isCleanupOver()) {
        // 此时无任何线程使用，可直接释放
        UtilAll.cleanBuffer(this.mappedByteBuffer);
        this.fileChannel.close();
        this.file.delete();
        return true;
    }
    return false;
}
```

**swapMap 的价值**：不是"不能直接释放"，而是"通过双 MMap 切换 + 延迟等待"，把"直接释放"的风险降到最低。

### 9.9 MappedByteBuffer 与 DirectByteBuffer 区别

理解 swapMap 释放的是什么内存，需要先区分两种"堆外内存"：

```plain
┌─────────────────────────────────────────────────────────────────────────────┐
│                    两种"堆外内存"的本质区别                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  DirectByteBuffer（堆外直接内存）:                                           │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  ByteBuffer.allocateDirect(1GB)                                     │   │
│  │  • 占用：物理内存（受 -XX:MaxDirectMemorySize 限制）                 │   │
│  │  • 管理：JVM 通过 Cleaner 释放                                       │   │
│  │  • 用途：TransientStorePool 使用此方式                               │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  MappedByteBuffer（内存映射）:                                               │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  FileChannel.map(MapMode.READ_WRITE, 0, 1GB)                        │   │
│  │  • 占用：虚拟地址空间（不受 -XX:MaxDirectMemorySize 限制）❗         │   │
│  │  • 管理：需要 munmap 系统调用释放                                    │   │
│  │  • 用途：CommitLog/ConsumeQueue 使用此方式                           │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**关键区别对比**：

| 特性 | DirectByteBuffer | MappedByteBuffer |
|------|------------------|------------------|
| **内存类型** | 堆外直接内存 | 虚拟地址空间映射 |
| **受 MaxDirectMemorySize 限制** | ✅ 是 | ❌ 否 |
| **占用物理内存** | ✅ 立即占用 | ❌ 按需加载（缺页时） |
| **释放方式** | Cleaner.clean() | munmap 系统调用 |
| **RocketMQ 使用场景** | TransientStorePool | CommitLog/ConsumeQueue |

**swapMap 释放的是什么内存**：

| 释放对象 | 是否释放 | 说明 |
|----------|----------|------|
| **PageCache 物理内存** | ❌ 否 | 文件数据仍在 PageCache 中，可被 OS 换出 |
| **虚拟地址空间** | ✅ 是 | 释放了旧的虚拟地址范围 |
| **Page Table 条目** | ✅ 是 | 清理了旧的页表条目，释放内核内存 |
| **堆外直接内存** | ❌ 无关 | MappedByteBuffer 不占用堆外直接内存 |

> **📌 重要：swapMap 释放的是内核内存**
>
> swapMap 的核心价值是释放 **Page Table 条目（内核内存）**，而不是释放"堆外直接内存"或 PageCache 物理内存。Page Table 存储在内核内存中，无法被 swap 换出，长期运行会持续累积。swapMap 通过重新映射清理旧条目，解决内核内存增长问题。

**验证方法**：

```java
// 设置 -XX:MaxDirectMemorySize=1g

// 映射 10GB 文件，不会 OOM（不受 MaxDirectMemorySize 限制）
MappedByteBuffer mmap = FileChannel.open(path, StandardOpenOption.READ)
    .map(FileChannel.MapMode.READ_ONLY, 0, 10L * 1024 * 1024 * 1024);

// 但分配 2GB DirectByteBuffer 会 OOM
ByteBuffer direct = ByteBuffer.allocateDirect(2L * 1024 * 1024 * 1024); // OOM!
```

### 10.7 核心优化总结

| 优化手段 | 核心作用 | 关键技术 |
| --- | --- | --- |
| **mmap 内存映射** | 零拷贝读写 | FileChannel.map() |
| **mlock 内存锁定** | 防止热点数据被 swap | mlock + madvise |
| **堆外内存池** | 减少锁竞争，提升写入性能 | TransientStorePool |
| **文件预热** | 提前加载到 PageCache | warmMappedFile |
| **文件预分配** | 避免文件创建阻塞写入 | AllocateMappedFileService |
| **内存映射交换** | 释放不活跃内存 | swapMap |

这些优化手段相互配合，共同支撑 RocketMQ 的高吞吐、低延迟存储能力。在实际应用中，需要根据业务场景（数据安全性 vs 吞吐量）选择合适的配置组合。
