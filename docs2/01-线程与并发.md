# 线程与并发

> **关联文档**：Reactor模式的详细实现原理请参阅 [04-IO多路复用.md](04-IO多路复用.md)，线程等待唤醒的应用场景请参阅 [06-中断与信号.md](06-中断与信号.md)。

## 1. 概述

线程是CPU调度的基本单位，并发编程是高性能分布式系统的核心技术。Linux内核通过`task_struct`结构体统一管理进程和线程，线程本质是共享地址空间的轻量级进程(LWP)。RocketMQ作为高吞吐量的消息中间件，在并发编程方面有丰富的实践，包括：

- **线程生命周期管理**：通过ServiceThread统一管理后台服务线程
- **高效同步机制**：基于futex和CAS实现轻量级同步
- **灵活锁策略**：自旋锁、可重入锁、分段锁按场景选择
- **线程池监控**：ThreadPoolMonitor实现线程池状态监控和告警
- **Reactor网络模型**：三级线程组处理高并发网络请求

本文将从操作系统原理出发，深入分析RocketMQ的并发编程实践。

## 2. 进程与线程基础

### 2.1 进程与线程概念

#### 进程定义与特征

**进程(Process)** 是操作系统资源分配的基本单位，是程序在执行过程中的一个实例。每个进程拥有独立的地址空间和系统资源。

**进程特征**：

| 特征 | 说明 |
|------|------|
| 独立地址空间 | 每个进程拥有独立的虚拟地址空间，互不干扰 |
| 独立资源 | 文件描述符表、信号处理、工作目录等资源独立 |
| 隔离性 | 进程间通信需要通过IPC机制（管道、共享内存、套接字等） |
| 创建开销 | fork()创建进程需要复制父进程资源，开销较大 |

#### 线程定义与特征

**线程(Thread)** 是CPU调度的基本单位，是进程内的执行流。同一进程内的多个线程共享进程资源，但拥有独立的执行栈和寄存器状态。

**线程特征**：

| 特征 | 说明 |
|------|------|
| 共享地址空间 | 同一进程内的线程共享虚拟地址空间 |
| 共享资源 | 共享文件描述符、信号处理、堆内存等 |
| 独立执行流 | 每个线程拥有独立的栈、程序计数器、寄存器状态 |
| 创建开销 | pthread_create()创建线程开销远小于进程创建 |

#### 进程与线程对比

| 对比维度 | 进程 | 线程 |
|---------|------|------|
| 资源分配 | 独立地址空间和资源 | 共享进程资源 |
| 调度单位 | 不是调度单位 | CPU调度的基本单位 |
| 通信方式 | IPC（管道、共享内存、套接字） | 共享内存、锁、条件变量 |
| 创建开销 | 大（需复制资源） | 小（仅分配栈和寄存器） |
| 上下文切换 | 大（需切换页表） | 小（仅切换寄存器和栈） |
| 隔离性 | 高（地址空间隔离） | 低（共享地址空间） |
| 健壮性 | 高（一个进程崩溃不影响其他进程） | 低（一个线程崩溃可能导致整个进程退出） |

#### 轻量级进程(LWP)

Linux采用"统一进程/线程模型"，线程在内核中被称为**轻量级进程(LWP，Light Weight Process)**，与进程使用相同的数据结构`task_struct`描述，区别在于资源共享粒度。

**设计思想**：
- 进程拥有独立的地址空间、文件描述符表、信号处理等资源
- 线程共享同一进程的资源，仅拥有独立的栈和寄存器状态
- 通过`clone()`系统调用的flags参数控制资源共享粒度

**clone()系统调用flags参数**：

| flags参数 | 说明 | 用途 |
|----------|------|------|
| `CLONE_VM` | 共享地址空间 | 创建线程 |
| `CLONE_FS` | 共享文件系统信息 | 共享根目录、工作目录 |
| `CLONE_FILES` | 共享文件描述符表 | 共享打开的文件 |
| `CLONE_SIGHAND` | 共享信号处理 | 共享信号处理函数 |
| `CLONE_THREAD` | 加入同一线程组 | 共享tgid |

### 2.2 内核数据结构

`task_struct`是Linux内核中最核心的数据结构，定义在`include/linux/sched.h`：

```c
struct task_struct {
    volatile long state;        // 进程状态：TASK_RUNNING等
    void *stack;                // 内核栈指针
    struct mm_struct *mm;       // 用户空间内存描述符
    struct mm_struct *active_mm;// 内核线程借用的内存描述符
    
    pid_t pid;                  // 进程/线程唯一标识符
    pid_t tgid;                 // 线程组ID（主线程pid）
    struct task_struct *parent; // 父进程指针
    struct list_head children;  // 子进程链表
    struct list_head sibling;   // 兄弟进程链表
    
    struct fs_struct *fs;       // 文件系统信息（根目录、工作目录）
    struct files_struct *files; // 打开文件表
    struct nsproxy *nsproxy;    // 命名空间代理
    
    struct signal_struct *signal;    // 信号处理
    struct sighand_struct *sighand;  // 信号处理函数表
    sigset_t blocked;                 // 阻塞信号集
    
    int prio, static_prio, normal_prio; // 调度优先级
    unsigned int rt_priority;           // 实时优先级
    const struct sched_class *sched_class; // 调度类
    struct sched_entity se;             // CFS调度实体
    struct sched_rt_entity rt;          // 实时调度实体
    
    cputime_t utime, stime;            // 用户态/内核态CPU时间
    unsigned long nvcsw, nivcsw;       // 自愿/非自愿上下文切换次数
    
    char comm[TASK_COMM_LEN];          // 进程名称（最长16字节）
};
```

**task_struct关键字段详解**：

| 字段 | 类型 | 说明 | 用途 |
|------|------|------|------|
| `state` | volatile long | 进程状态 | 调度器判断进程是否可运行 |
| `pid` | pid_t | 进程/线程ID | 全局唯一标识符 |
| `tgid` | pid_t | 线程组ID | 同一线程组的线程共享tgid |
| `mm` | mm_struct* | 内存描述符 | 管理进程地址空间 |
| `files` | files_struct* | 打开文件表 | 管理文件描述符 |
| `fs` | fs_struct* | 文件系统信息 | 根目录、工作目录 |
| `prio` | int | 动态优先级 | 调度器使用 |
| `se` | sched_entity | CFS调度实体 | 红黑树节点，包含vruntime |
| `utime/stime` | cputime_t | CPU时间 | 用户态/内核态运行时间 |
| `nvcsw/nivcsw` | unsigned long | 上下文切换次数 | 性能分析指标 |

#### 系统调用接口

| 系统调用 | 参数 | 返回值 | 说明 |
|----------|------|--------|------|
| `getpid()` | 无 | pid_t | 返回进程ID（tgid） |
| `gettid()` | 无 | pid_t | 返回线程ID（pid） |
| `clone()` | flags, stack, ... | pid_t | 创建线程/进程，flags控制资源共享 |
| `fork()` | 无 | pid_t | 创建进程，复制父进程资源 |
| `execve()` | filename, argv, envp | int | 加载新程序 |

#### 内核参数

| 参数路径 | 默认值 | 说明 |
|----------|--------|------|
| `/proc/sys/kernel/pid_max` | 32768 | 最大PID值 |
| `/proc/sys/kernel/threads-max` | 依赖内存 | 系统最大线程数 |
| `/proc/sys/vm/max_map_count` | 65530 | 最大内存映射数量 |

### 2.3 进程状态与转换

**Linux内核进程/线程状态定义**（`include/linux/sched.h`）：

| 状态 | 值 | 说明 | 触发条件 |
|------|-----|------|---------|
| `TASK_RUNNING` | 0 | 运行态，正在运行或等待CPU调度 | 获得CPU时间片 |
| `TASK_INTERRUPTIBLE` | 1 | 可中断睡眠，等待事件，可被信号唤醒 | 等待I/O、锁、信号量 |
| `TASK_UNINTERRUPTIBLE` | 2 | 不可中断睡眠，只能被事件唤醒 | 等待磁盘I/O完成 |
| `TASK_ZOMBIE` | 4 | 僵尸态，进程已终止但父进程未回收 | 进程exit()后 |
| `TASK_STOPPED` | 8 | 停止态，被信号暂停 | SIGSTOP、SIGTSTP信号 |
| `TASK_TRACED` | 16 | 跟踪态，被调试器跟踪 | ptrace()系统调用 |

**两种核心睡眠状态对比**：

| 对比维度 | TASK_INTERRUPTIBLE | TASK_UNINTERRUPTIBLE |
|---------|-------------------|---------------------|
| 状态值 | 1 | 2 |
| 唤醒方式 | 事件发生或收到信号 | 仅事件发生 |
| 信号响应 | ✅ 响应所有信号 | ❌ 不响应任何信号 |
| top显示 | S (Sleeping) | D (Disk Sleep) |
| 典型场景 | 网络I/O、锁等待、定时等待 | 磁盘I/O、内存换页 |

**状态转换关系**：

```mermaid
stateDiagram-v2
    [*] --> TASK_RUNNING: 创建进程
    TASK_RUNNING --> TASK_RUNNING: 获得CPU时间片
    TASK_RUNNING --> TASK_INTERRUPTIBLE: 等待事件(可中断)
    TASK_RUNNING --> TASK_UNINTERRUPTIBLE: 等待I/O(不可中断)
    TASK_RUNNING --> TASK_STOPPED: SIGSTOP信号
    TASK_RUNNING --> TASK_TRACED: ptrace()
    TASK_INTERRUPTIBLE --> TASK_RUNNING: 事件就绪/信号
    TASK_UNINTERRUPTIBLE --> TASK_RUNNING: I/O完成
    TASK_STOPPED --> TASK_RUNNING: SIGCONT信号
    TASK_TRACED --> TASK_RUNNING: 调试器继续
    TASK_RUNNING --> TASK_ZOMBIE: exit()
    TASK_ZOMBIE --> [*]: 父进程wait()
```

**图表核心结论**：Linux线程以TASK_RUNNING为核心枢纽，在运行、等待、停止、终止四种状态间流转，其中TASK_INTERRUPTIBLE和TASK_UNINTERRUPTIBLE是两种关键的睡眠状态。

**关键概念**：

- **TASK_RUNNING**：唯一可被CPU执行的状态，包含"正在运行"和"就绪等待调度"两种情况
- **TASK_INTERRUPTIBLE vs TASK_UNINTERRUPTIBLE**：前者可被信号唤醒（如网络I/O），后者只能等待事件完成（如磁盘I/O），避免关键操作被中断
- **TASK_ZOMBIE**：线程已终止但资源未回收，父进程需调用wait()避免僵尸进程累积

### 2.4 进程调度原理

#### CFS调度器原理

Linux使用**CFS(Completely Fair Scheduler，完全公平调度器)**作为默认调度器，核心思想是"公平分配CPU时间"。每个进程维护一个`vruntime`（虚拟运行时间），调度器优先选择`vruntime`最小的进程运行。

**设计思想**：
- 红黑树维护就绪队列，按`vruntime`排序
- `vruntime`小的进程在树左侧，优先被调度
- 运行时间与进程优先级成反比：优先级越高，`vruntime`增长越慢
- 支持实时调度类(SCHED_FIFO/SCHED_RR)和普通调度类(SCHED_NORMAL)

#### 内核数据结构

```c
// CFS调度器核心数据结构
struct cfs_rq {
    struct rb_root tasks_timeline;     // 红黑树根节点
    struct rb_node *rb_leftmost;       // 最左节点（vruntime最小）
    unsigned int nr_running;           // 就绪进程数
    u64 min_vruntime;                  // 最小vruntime基准
    
    struct sched_entity *curr;         // 当前运行的调度实体
    struct sched_entity *next;         // 下一个待运行实体
};

// 调度实体（嵌入在task_struct中）
struct sched_entity {
    struct rb_node run_node;           // 红黑树节点
    u64 vruntime;                      // 虚拟运行时间
    u64 sum_exec_runtime;              // 累计执行时间
    u64 prev_sum_exec_runtime;         // 上次累计执行时间
    struct cfs_rq *cfs_rq;             // 所属CFS队列
};
```

**调度类层次**：

| 调度类 | 策略 | 优先级范围 | 说明 |
|--------|------|-----------|------|

### 2.5 上下文切换

#### 切换原理

**上下文切换**是操作系统实现多任务的核心机制，包括保存旧进程状态、切换内核栈和页表、加载新进程状态。每次切换约消耗1-10微秒。

**切换内容**：
- **CPU寄存器**：通用寄存器、程序计数器(PC)、栈指针(SP)
- **内核栈**：每个进程有独立的内核栈（8KB或16KB）
- **页表基址**：CR3寄存器，切换地址空间
- **浮点/向量寄存器**：延迟保存(Lazy FPU)

#### 处理流程

```mermaid

        C2 --> C3["保存当前进程PCB<br/>switch_to宏"]
        C3 --> C4["切换内核栈<br/>ESP指向新进程栈"]

    end

```

**图表核心结论**：上下文切换涉及寄存器保存、内核栈切换、页表切换三个核心步骤，其中页表切换和TLB刷新开销最大。

**switch_to宏核心逻辑**：

```c
// arch/x86/include/asm/switch_to.h
#define switch_to(prev, next, last)               \
do {                                              \
    ((last) = __switch_to((prev), (next)));       \
} while (0)

// __switch_to汇编实现
// 1. 保存当前进程寄存器
// 2. 切换内核栈
// 3. 加载新进程寄存器
```

#### 性能特征

| 操作 | 开销 | 说明 |
|------|------|------|
| 寄存器保存/恢复 | ~100ns | 通用寄存器 |
| 内核栈切换 | ~200ns | ESP指针更新 |
| 页表切换(CR3) | ~500ns | 写入新进程PGD |
| TLB刷新 | ~1-5μs | 进程切换时可能需要 |
| 总开销 | **1-10μs** | 取决于CPU架构和缓存状态 |

#### 调试方法

### 2.6 Java线程模型

#### Java线程与Linux线程映射

Java线程在Linux系统中映射为轻量级进程(LWP)，JVM通过pthread库创建线程：

| Java状态 | Linux状态 | 说明 |
|---------|----------|------|
| RUNNABLE | TASK_RUNNING | 可运行状态 |
| BLOCKED | TASK_INTERRUPTIBLE | 等待monitor锁 |
| WAITING | TASK_INTERRUPTIBLE | 无限等待 |
| TIMED_WAITING | TASK_INTERRUPTIBLE | 计时等待 |
| TERMINATED | TASK_ZOMBIE | 终止状态 |

#### Java线程状态转换

```mermaid
stateDiagram-v2
    [*] --> NEW: 线程创建
    NEW --> RUNNABLE: start()
    RUNNABLE --> BLOCKED: 等待锁
    RUNNABLE --> WAITING: wait()/join()/park()
    RUNNABLE --> TIMED_WAITING: sleep(timeout)/wait(timeout)
    BLOCKED --> RUNNABLE: 获取锁
    WAITING --> RUNNABLE: notify()/unpark()
    TIMED_WAITING --> RUNNABLE: 超时/notify()
    RUNNABLE --> TERMINATED: run()结束
    TERMINATED --> [*]
```

**图表核心结论**：Java线程以RUNNABLE为唯一活跃状态，通过synchronized锁、Object.wait()、Thread.sleep()等方法在6种状态间转换，所有等待状态最终都回归RUNNABLE才能继续执行。

**关键概念**：

- **RUNNABLE**：Java中唯一"活跃"状态，对应Linux的TASK_RUNNING，包含"正在执行"和"等待CPU调度"
- **BLOCKED vs WAITING**：BLOCKED是等待synchronized锁，WAITING是主动等待（如Object.wait()）
- **WAITING vs TIMED_WAITING**：前者无限等待需显式唤醒，后者有超时机制

#### 守护线程

**守护线程(Daemon Thread)** 是为其他线程提供服务的后台线程，JVM退出时不等待守护线程完成：

| 线程类型 | JVM退出行为 | 典型用途 |
|---------|------------|---------|
| 用户线程 | 等待所有用户线程结束 | 业务逻辑执行 |
| 守护线程 | 不等待，直接退出 | GC(Garbage Collection，垃圾回收)、监控、心跳 |

### 3.2 CAS原子操作

#### 3.2.1 CAS原理

**CAS(Compare-And-Swap，比较并交换)** 是原子操作的基础：

```c
// CAS 伪代码
bool CAS(int *addr, int expected, int new_value) {
    if (*addr == expected) {
        *addr = new_value;
        return true;
    }
    return false;
}

// x86 汇编
lock cmpxchg [dest], source
```

**CAS与lock前缀**：

| 层面 | 名称 | 说明 |
|------|------|------|
| 概念层 | CAS | Compare-And-Swap，原子操作语义 |
| 实现层 | `lock cmpxchg` | x86架构的具体指令 |

> `lock`是前缀不是独立指令，修饰后续指令保证原子性。不同架构实现不同：x86用`lock cmpxchg`，ARM用`LDXR/STXR`。

**CAS操作流程**：

```mermaid
flowchart TD
    Start["CAS操作开始"] --> ReadAddr["读取内存地址addr的值"]
    ReadAddr --> Compare{比较<br/>*addr == expected?}
    
    Compare -->|"相等"| SetNew["原子写入<br/>*addr = new_value"]
    Compare -->|"不相等"| ReturnFalse["返回false<br/>操作失败"]
    
    SetNew --> ReturnTrue["返回true<br/>操作成功"]
    
    %% 样式定义
    style Start fill:#e8f5e9,stroke:#4caf50,stroke-width:2px
    style Compare fill:#fff3e0,stroke:#ff9800,stroke-width:2px
    style SetNew fill:#e3f2fd,stroke:#2196f3,stroke-width:2px
    style ReturnTrue fill:#e8f5e9,stroke:#4caf50,stroke-width:2px
    style ReturnFalse fill:#ffebee,stroke:#f44336,stroke-width:2px
```

**图表核心结论**：CAS是原子性的比较并交换操作，整个操作在硬件层面不可分割，确保多线程环境下的数据一致性，是Java并发包的基础。

**CAS操作步骤说明**：

| 步骤 | 操作 | 类型 | 说明 |
|------|------|------|------|
| 1 | 读取内存值 | 原子操作 | 从内存地址addr读取当前值 |
| 2 | 比较期望值 | 原子操作 | 比较当前值与期望值expected |
| 3 | 条件更新 | 原子操作 | 相等时写入新值new_value，否则失败 |
| 4 | 返回结果 | 原子操作 | 返回操作成功或失败标志 |

#### 3.2.2 ABA问题

**ABA问题场景**：


| 单变量限制 | 只能操作一个变量 | 使用锁或AtomicReference |

### 3.3 futex机制

#### 3.3.1 设计思想

**futex(Fast Userspace Mutex，快速用户空间互斥锁)** 是Linux实现高效同步的核心机制。

**核心思想**：
- 无竞争时：完全在用户态完成，避免系统调用开销
- 有竞争时：通过内核等待队列阻塞线程

**锁的层次演进**：
```
硬件层：lock前缀 → 原子性保证（无锁对象）
    ↓
内核层：futex → 锁对象 + 等待队列（完整锁语义）
    ↓
应用层：ReentrantLock → 可重入、公平性等高级特性
```

#### 3.3.2 内核数据结构

```c
// futex等待队列节点
struct futex_q {
    struct plist_node list;          // 优先级链表节点
    struct task_struct *task;        // 等待的进程
    spinlock_t *lock_ptr;            // 自旋锁指针
    union futex_key key;             // futex标识键
    u32 *uaddr;                      // 用户态地址
};

// futex哈希桶
struct futex_hash_bucket {
    spinlock_t lock;                 // 保护链表的自旋锁
    struct plist_head chain;         // 等待队列链表
};
```

#### 3.3.4 系统调用接口

```c
long sys_futex(u32 *uaddr, int futex_op, u32 val,
               const struct timespec *timeout,
               u32 *uaddr2, u32 val3);
```

| 操作码 | 参数 | 说明 |
|--------|------|------|
| `FUTEX_WAIT` | uaddr, val, timeout | 等待*uaddr == val，否则阻塞 |
| `FUTEX_WAKE` | uaddr, nr_wake | 唤醒nr_wake个等待线程 |
| `FUTEX_REQUEUE` | uaddr, nr_wake, uaddr2 | 唤醒并移动到另一个futex |

#### 3.3.5 FUTEX操作详解

**FUTEX_WAKE vs FUTEX_REQUEUE**：

| 操作 | 效果 | Java对应 |
|------|------|---------|
| `FUTEX_WAKE` | 直接唤醒，线程立即竞争锁 | `unlock()` |
| `FUTEX_REQUEUE` | 唤醒+移动队列，避免惊群 | `signal()` |

**场景1：无Condition（纯锁竞争）**

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();    // CAS竞争，失败则 FUTEX_WAIT
lock.unlock();  // FUTEX_WAKE(1)
```

```
执行流程：
  T1: lock() → CAS成功 → 获取锁
  T2: lock() → CAS失败 → FUTEX_WAIT → 进入锁等待队列
  T3: lock() → CAS失败 → FUTEX_WAIT → 进入锁等待队列

  锁等待队列: [T2, T3]

  T1: unlock() → FUTEX_WAKE(1) → T2唤醒 → 竞争锁成功
```

**场景2：有Condition（条件等待）**

```java
ReentrantLock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();

// 消费者
lock.lock();
while (queue.isEmpty()) {
    notEmpty.await();  // FUTEX_WAIT，进入Condition队列
}
lock.unlock();

// 生产者
lock.lock();
queue.add(item);
notEmpty.signal();     // FUTEX_REQUEUE，移动到锁队列
lock.unlock();         // FUTEX_WAKE，唤醒锁队列
```

```
执行流程：
  C1, C2, C3: await() → FUTEX_WAIT → 进入Condition队列

  Condition队列: [C1, C2, C3]
  锁等待队列: []

  P1: signal() → FUTEX_REQUEUE(1, lock_futex)
      C1 唤醒 → 竞争锁
      C2, C3 移动到锁等待队列

  Condition队列: []
  锁等待队列: [C2, C3]
  C1: RUNNABLE，竞争锁
```

**Java与futex对应关系**：

| Java操作 | futex操作 | 说明 |
|---------|-----------|------|
| `lock.lock()` | CAS + `FUTEX_WAIT` | 竞争失败则阻塞 |
| `lock.unlock()` | `FUTEX_WAKE(1)` | 唤醒锁等待队列 |
| `condition.await()` | `FUTEX_WAIT` | 进入Condition队列 |
| `condition.signal()` | `FUTEX_REQUEUE(1)` | 唤醒1个，移动其余 |
| `condition.signalAll()` | `FUTEX_REQUEUE(ALL)` | 全部唤醒 |

**signal() vs signalAll()**：

| 方法 | 唤醒数 | 移动数 | 开销 | 适用场景 |
|------|--------|--------|------|---------|
| `signal()` | 1 | N-1 | 小 | 只需唤醒1个线程 |
| `signalAll()` | N | 0 | 大 | 所有线程需重新检查条件 |

### 3.4 自旋锁

#### 3.4.1 自旋等待原理

**自旋锁(Spinlock)**是一种忙等待锁：

**图表核心结论**：自旋锁通过CAS指令在用户态忙等待获取锁，无上下文切换开销，但竞争激烈时CPU空转严重，适用于锁持有时间极短的场景。

**适用场景**：

| 场景 | 是否适合 | 原因 |
|------|---------|------|
| 锁持有时间短 | ✅ 适合 | 等待时间短，上下文切换开销更大 |
| 锁竞争少 | ✅ 适合 | 很少需要自旋 |
| 锁持有时间长 | ❌ 不适合 | CPU空转浪费严重 |
| 锁竞争激烈 | ❌ 不适合 | 大量线程自旋，CPU占用高 |

#### 3.4.2 RocketMQ PutMessageSpinLock实现

[PutMessageSpinLock.java](../store/src/main/java/org/apache/rocketmq/store/PutMessageSpinLock.java) 实现自旋锁：

```java
/**
 * Spin lock Implementation to put message, suggest using this with low race conditions
 * 自旋锁实现，建议在低竞争场景下使用
 */
public class PutMessageSpinLock implements PutMessageLock {
    // true: Can lock（可获取锁）, false: in lock（锁被占用）
    private AtomicBoolean putMessageSpinLock = new AtomicBoolean(true);  // 默认值：true（可获取）

    @Override
    public void lock() {
        boolean flag;
        do {
            // CAS: 期望值为true（可获取），更新为false（已锁定）
            flag = this.putMessageSpinLock.compareAndSet(true, false);
        } while (!flag);  // 自旋等待，直到获取锁成功
    }

    @Override
    public void unlock() {
        // CAS: 期望值为false（已锁定），更新为true（可获取）
        this.putMessageSpinLock.compareAndSet(false, true);
    }
}
```

**自旋锁状态说明**：

| 状态值 | 含义 | 说明 |
|--------|------|------|
| `true` | 可获取锁 | 锁未被占用，可尝试获取 |
| `false` | 锁被占用 | 其他线程持有锁，需等待 |

**AQS工作原理说明**：

| 组件 | 说明 |
|------|------|
| CLH队列 | Craig, Landin, and Hagersten队列，双向链表 |

| Head节点 | 虚拟节点，不存储线程信息 |
| Tail节点 | 指向队列最后一个等待节点 |

**公平锁 vs 非公平锁**：

| 类型 | 说明 | 特点 |
|------|------|------|
| 公平锁 | 按请求顺序获取 | 公平，但吞吐量低 |
| 非公平锁 | 允许插队 | 吞吐量高，但可能饥饿 |

#### 3.5.3 Condition队列机制

**Condition队列与锁等待队列**是AQS中两种不同的等待队列：

**队列结构**：

```
┌─────────────────────────────────────────────────────────────┐
│                    ReentrantLock                            │
├─────────────────────────────────────────────────────────────┤
│  锁等待队列（AQS CLH队列）                                    │
│  [T4] → [T5] → [T6]     等待获取锁                          │
│  入队：lock()竞争失败  出队：unlock()唤醒                    │
│                                                             │
│  Condition队列（notEmpty）                                   │
│  [C1] → [C2] → [C3]     等待"非空"条件                      │
│  入队：await()释放锁   出队：signal()移动到锁队列            │
│                                                             │
│  Condition队列（notFull）                                    │
│  [P1] → [P2]            等待"非满"条件                      │
└─────────────────────────────────────────────────────────────┘
```

**核心区别**：

| 对比项 | 锁等待队列 | Condition队列 |
|--------|-----------|--------------|
| 等待什么 | 等待获取锁 | 等待条件成立 |
| 入队时机 | `lock()`竞争失败 | `await()`主动等待 |
| 出队时机 | `unlock()`唤醒 | `signal()`通知 |
| 是否释放锁 | 否 | 是（await释放锁） |
| 队列数量 | 1个/锁 | N个/Condition |

**线程流转**：

```
锁等待队列流转：
  T1: lock()失败 → 进入锁等待队列 → BLOCKED
  Owner: unlock() → FUTEX_WAKE → T1唤醒 → 获取锁

Condition队列流转：
  C1: await() → 释放锁 + 进入Condition队列 → BLOCKED
  P1: signal() → FUTEX_REQUEUE → C1移动到锁等待队列
  P1: unlock() → C1唤醒 → 获取锁 → 检查条件
```

**signal() vs signalAll()**：

| 方法 | 唤醒数 | 移动数 | 开销 | 适用场景 |
|------|--------|--------|------|---------|
| `signal()` | 1 | N-1 | 小 | 只需唤醒1个线程 |
| `signalAll()` | N | 0 | 大 | 所有线程需重新检查条件 |

| 模式 | 锁数量 | 并发度 | 适用场景 |
|------|--------|--------|---------|

**关键概念**：

- **Hash映射**：根据key的hash值分配到对应的锁段
- **锁粒度**：分段数越多，锁粒度越细，并发度越高
- **一致性保证**：相同key的操作映射到同一锁段，保证顺序性
- **典型应用**：ConcurrentHashMap（16段）、RocketMQ TopicQueueLock（32段）

#### 3.6.3 RocketMQ TopicQueueLock实现

[TopicQueueLock.java](../store/src/main/java/org/apache/rocketmq/store/TopicQueueLock.java) 实现分段锁：

```java
public class TopicQueueLock {
    private final int size;  // 分段数量，默认值：32
    private final List<Lock> lockList;  // 锁列表

    public TopicQueueLock() {
        this.size = 32;  // 32个分段
        this.lockList = new ArrayList<>(32);
        for (int i = 0; i < this.size; i++) {
            this.lockList.add(new ReentrantLock());  // 每段一个可重入锁
        }
    }

    /**
     * 根据 topicQueueKey 获取对应的锁并加锁
     * @param topicQueueKey 格式：topic-queueId
     */
    public void lock(String topicQueueKey) {
        // 使用 hashCode & 0x7fffffff 确保非负，再取模
        Lock lock = this.lockList.get((topicQueueKey.hashCode() & 0x7fffffff) % this.size);
        lock.lock();
    }

    /**
     * 根据 topicQueueKey 释放对应的锁
     */
    public void unlock(String topicQueueKey) {
        Lock lock = this.lockList.get((topicQueueKey.hashCode() & 0x7fffffff) % this.size);
        lock.unlock();
    }
}
```

**设计要点**：

| 要点 | 说明 |
|------|------|
| 分段数 | 32个分段，平衡并发度和内存开销 |
| Hash算法 | `hashCode & 0x7fffffff` 确保非负，避免负数取模异常 |
| 锁类型 | ReentrantLock（非公平），支持可重入 |
| 一致性保证 | 相同 topicQueueKey 映射到同一锁段，保证顺序性 |

### 3.7 锁机制对比与选择

**自旋锁 vs 可重入锁 vs 分段锁**：

| 对比维度 | 自旋锁 | 可重入锁 | 分段锁 |
|---------|--------|---------|--------|
| 实现原理 | CAS忙等待 | AQS + CLH队列 | 多段ReentrantLock |
| 等待方式 | CPU空转 | 线程阻塞 | 线程阻塞 |
| 上下文切换 | 无 | 有 | 有 |
| 适用场景 | 锁持有时间极短 | 锁持有时间较长 | 高并发写操作 |
| CPU开销 | 高竞争时高 | 中等 | 低 |
| 公平性 | 无 | 可配置 | 可配置 |
| RocketMQ实现 | PutMessageSpinLock | PutMessageReentrantLock | TopicQueueLock |

**锁选择建议**：

| 场景 | 推荐锁类型 | 原因 |
|------|----------|------|
| 低竞争、短持有 | 自旋锁 | 避免上下文切换开销 |
| 高竞争、长持有 | 可重入锁 | 避免CPU空转 |
| 多Key并发写入 | 分段锁 | 降低锁竞争粒度 |
| 单Key顺序操作 | 可重入锁 | 简单可靠 |

**futex快速路径 vs 慢速路径**：

| 路径 | 延迟 | CPU开销 | 适用场景 |
|------|------|---------|---------|
| 快速路径（无竞争） | ~50ns | 低 | 大多数情况 |
| 慢速路径（有竞争） | ~5μs | 中等 | 锁竞争时 |

**CAS vs 锁**：

| 对比维度 | CAS | 锁 |
|---------|-----|-----|
| 操作粒度 | 单变量 | 代码块 |
| 开销 | 低（用户态） | 高（可能内核态） |
| 适用场景 | 简单原子操作 | 复杂临界区 |
| ABA问题 | 存在 | 不存在 |
| 公平性 | 无 | 可配置 |

| `keepAliveTime` | 空闲线程存活时间 | 60,000ms = 60s | 临时线程超时回收 |
| `workQueue` | 任务队列 | LinkedBlockingQueue | 有界/无界，影响背压 |

## 5. Reactor模式

> **扩展阅读**：Reactor模式的详细实现原理、epoll机制、Netty配置等内容，请参阅 [04-IO多路复用.md](04-IO多路复用.md)。

### 5.1 Reactor模式原理

**Reactor模式**基于I/O多路复用，用少量线程处理大量连接，是RocketMQ高并发网络处理的核心架构。

**三级线程组架构**：

| 线程组 | 线程数 | 职责 | 系统调用 |
|--------|--------|------|---------|
| Boss Group | 1 | Accept连接 | `accept()`、`epoll_ctl()` |
| Selector Group | serverSelectorThreads（默认值：3） | I/O读写 | `epoll_wait()`、`read()`、`write()` |
| Worker Group | serverWorkerThreads（默认值：8） | 业务处理 | 无I/O系统调用 |

**图表核心结论**：Reactor模式通过三级线程组实现I/O与业务分离，Boss Group负责连接建立，Selector Group负责I/O读写，Worker Group负责业务处理，实现高并发、低延迟的网络处理。

**关键设计原则**：

- **Boss Group**：单线程负责Accept连接，避免多线程竞争
- **Selector Group**：N线程处理I/O读写，基于epoll多路复用
- **Worker Group**：M线程执行业务逻辑，与I/O线程分离避免阻塞
- **I/O多路复用**：一个线程同时监控多个连接，减少线程数量

### 5.3 线程模型对比

**单线程 vs 多线程 vs Reactor**：

### 6.1 ServiceThread服务线程

RocketMQ所有后台服务线程继承自 [ServiceThread.java](../common/src/main/java/org/apache/rocketmq/common/ServiceThread.java)：

```java
public abstract class ServiceThread implements Runnable {
    private static final long JOIN_TIME = 90 * 1000;  // 等待线程结束超时，默认值：90,000ms = 90s
    
    protected Thread thread;                           // 线程对象
    protected final CountDownLatch2 waitPoint = new CountDownLatch2(1);  // 等待点，初始计数：1
    protected volatile AtomicBoolean hasNotified = new AtomicBoolean(false);  // 唤醒标志，默认值：false
    protected volatile boolean stopped = false;        // 停止标志，默认值：false
    protected boolean isDaemon = false;                // 是否守护线程，默认值：false
    
    private final AtomicBoolean started = new AtomicBoolean(false);  // 启动标志，默认值：false

    public void start() {
        log.info("Try to start service thread:{} started:{} lastThread:{}", 
            getServiceName(), started.get(), thread);
        if (!started.compareAndSet(false, true)) {
            return;  // CAS保证单次启动，已启动则直接返回
        }
        stopped = false;
        this.thread = new Thread(this, getServiceName());
        this.thread.setDaemon(isDaemon);
        this.thread.start();
    }

    public void shutdown(final boolean interrupt) {
        log.info("Try to shutdown service thread:{} started:{} lastThread:{}", 
            getServiceName(), started.get(), thread);
        if (!started.compareAndSet(true, false)) {
            return;  // CAS保证单次关闭，已关闭则直接返回
        }
        this.stopped = true;
        log.info("shutdown thread " + this.getServiceName() + " interrupt " + interrupt);

        // 唤醒等待中的线程，确保shutdown不会被阻塞
        if (hasNotified.compareAndSet(false, true)) {
            waitPoint.countDown();
        }

        try {
            if (interrupt) {
                this.thread.interrupt();  // 可选：中断线程
            }

            long beginTime = System.currentTimeMillis();
            if (!this.thread.isDaemon()) {
                this.thread.join(this.getJoinTime());  // 等待线程结束，最多等待90s
            }
            long elapsedTime = System.currentTimeMillis() - beginTime;
            log.info("join thread " + this.getServiceName() + " elapsed time(ms) " + elapsedTime);
        } catch (InterruptedException e) {
            log.error("Interrupted", e);
        }
    }

    public void shutdown() {
        this.shutdown(false);  // 默认不中断线程
    }

    public long getJoinTime() {
        return JOIN_TIME;  // 返回等待超时时间：90,000ms = 90s
    }

    public void wakeup() {
        if (hasNotified.compareAndSet(false, true)) {
            waitPoint.countDown();  // 唤醒等待中的线程
        }
    }

    protected void waitForRunning(long interval) {
        // 路径1：已被唤醒，直接执行onWaitEnd()
        if (hasNotified.compareAndSet(true, false)) {
            this.onWaitEnd();
            return;
        }

        // 路径2：未被唤醒，进入等待状态
        waitPoint.reset();  // 重置CountDownLatch2

        try {
            waitPoint.await(interval, TimeUnit.MILLISECONDS);  // 等待指定时间或被唤醒
        } catch (InterruptedException e) {
            log.error("Interrupted", e);
        } finally {
            hasNotified.set(false);  // 重置唤醒标志
            this.onWaitEnd();  // 等待结束后执行回调
        }
    }

    protected void onWaitEnd() {
        // 空实现，子类可覆盖以执行等待结束后的逻辑
    }

    public boolean isStopped() {
        return stopped;
    }

    public boolean isDaemon() {
        return isDaemon;
    }

    public void setDaemon(boolean daemon) {
        isDaemon = daemon;
    }

    public abstract String getServiceName();  // 子类必须实现，返回服务名称
}
```

**设计要点**：

| 要点 | 操作系统原理 | RocketMQ实现 |
|------|-------------|-------------|
| 单次启动 | 线程只能启动一次 | CAS保证`started`只从false变true一次 |
| 优雅关闭 | 等待线程执行完毕 | `join()`等待线程结束，默认90,000ms = 90s超时 |
| 守护线程 | JVM退出时不等待守护线程 | `setDaemon()`控制是否为守护线程，默认值：false |
| 唤醒机制 | 避免信号丢失 | `hasNotified`标志位记录唤醒信号，`waitPoint`实现等待/唤醒 |

### 6.2 CountDownLatch2等待唤醒

RocketMQ使用 [CountDownLatch2.java](../common/src/main/java/org/apache/rocketmq/common/CountDownLatch2.java) 实现可重置的等待/唤醒机制：

```java
public class CountDownLatch2 {
    private final Sync sync;  // 基于 AQS 的同步器
    
    public CountDownLatch2(int count) {
        if (count < 0)
            throw new IllegalArgumentException("count < 0");
        this.sync = new Sync(count);
    }
    
    public void await() throws InterruptedException {
        sync.acquireSharedInterruptibly(1);
    }
    
    public boolean await(long timeout, TimeUnit unit) throws InterruptedException {
        return sync.tryAcquireSharedNanos(1, unit.toNanos(timeout));
    }
    
    public void countDown() { 
        sync.releaseShared(1); 
    }
    
    public void reset() { 
        sync.reset();  
    }
    
    private static final class Sync extends AbstractQueuedSynchronizer {
        private final int startCount;  // 初始计数值，用于reset()
        
        Sync(int count) {
            this.startCount = count;
            setState(count);  // AQS state 表示当前计数
        }
        
        @Override
        protected int tryAcquireShared(int acquires) {
            return (getState() == 0) ? 1 : -1;  // 计数为0时返回1（成功），否则返回-1（等待）
        }
        
        @Override
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int c = getState();
                if (c == 0)
                    return false;  // 已经是0，无需再减
                int nextc = c - 1;
                if (compareAndSetState(c, nextc))
                    return nextc == 0;  // 减到0时返回true，触发唤醒
            }
        }
        
        protected void reset() {
            setState(startCount);  // 重置到初始计数值
        }
    }
}
```

**CountDownLatch vs CountDownLatch2 对比**：

| 特性 | CountDownLatch | CountDownLatch2 |
|------|---------------|-----------------|
| 可重置 | ❌ 一次性使用 | ✅ 支持reset()重复使用 |
| 计数方式 | 只能减 | 只能减，但可重置 |
| 适用场景 | 一次性事件 | 周期性等待/唤醒 |

**CountDownLatch2 方法说明**：

| 方法 | 返回类型 | 说明 |
|------|---------|------|
| `await()` | void | 阻塞等待计数器归零，可被中断 |
| `await(long timeout, TimeUnit unit)` | boolean | 超时等待，返回true表示计数归零，false表示超时 |
| `countDown()` | void | 计数减1，归零时唤醒所有等待线程 |
| `reset()` | void | 重置计数器到初始值，可重复使用 |
| `getCount()` | long | 返回当前计数值，用于调试和测试 |
| `toString()` | String | 返回标识字符串，格式：`ClassName[Count = N]` |

**关键设计**：

| 问题 | 操作系统原理 | RocketMQ解决方案 |
|------|-------------|-----------------|
| 虚假唤醒 | wait可能无故返回 | 循环检查`hasNotified`标志 |
| 信号丢失 | wakeup在wait之前调用 | `hasNotified`标志位记录唤醒信号 |
| 可重用性 | CountDownLatch只能用一次 | `reset()`方法重置计数器 |

```java
        return Integer.MAX_VALUE;  // 无流控限制
    }

    public void addByteCountTransferred(long count) {
        this.transferredByte.addAndGet(count);  // 原子增加传输字节数
    }

    public long getTransferredByteInSecond() {
        return this.transferredByteInSecond;  // 返回每秒传输字节数
    }

    @Override
    public String getServiceName() {
        return FlowMonitor.class.getSimpleName();  // 返回 "FlowMonitor"
    }

    protected boolean isFlowControlEnable() {
        return this.messageStoreConfig.isHaFlowControlEnable();  // 是否启用HA流控
```

```java
        this.stopped = true;
    }
```

#### 6.5.2 ReferenceResource引用计数

[ReferenceResource.java](../store/src/main/java/org/apache/rocketmq/store/ReferenceResource.java) 使用AtomicLong实现引用计数：

```java
public abstract class ReferenceResource {
    protected final AtomicLong refCount = new AtomicLong(1);  // 初始引用计数，默认值：1
    protected volatile boolean available = true;              // 是否可用，默认值：true
    protected volatile boolean cleanupOver = false;           // 是否清理完成，默认值：false
    private volatile long firstShutdownTimestamp = 0;         // 首次关闭时间戳，默认值：0

    /**
     * 持有资源，增加引用计数
     */
    public synchronized boolean hold() {
        if (this.isAvailable()) {
            if (this.refCount.getAndIncrement() > 0) {
                return true;  // 引用计数 > 0，持有成功
            } else {
                this.refCount.getAndDecrement();  // 回滚
            }
        }
        return false;
    }

    /**
     * 检查资源是否可用
     */
    public boolean isAvailable() {
        return this.available;
    }

    /**
     * 关闭资源，支持强制关闭
     * @param intervalForcibly 强制关闭等待间隔，单位：ms
     */
    public void shutdown(final long intervalForcibly) {
        if (this.available) {
            this.available = false;
            this.firstShutdownTimestamp = System.currentTimeMillis();
            this.release();
        } else if (this.getRefCount() > 0) {
            // 超时后强制关闭
            if ((System.currentTimeMillis() - this.firstShutdownTimestamp) >= intervalForcibly) {
                this.refCount.set(-1000 - this.getRefCount());  // 设置为负数触发强制清理
                this.release();
            }
        }
    }

    /**
     * 释放资源，减少引用计数
     */
    public void release() {
        long value = this.refCount.decrementAndGet();
        if (value > 0)
            return;  // 还有引用，不清理

        synchronized (this) {
            this.cleanupOver = this.cleanup(value);  // 引用计数 <= 0，执行清理
        }
    }

    /**
     * 获取当前引用计数
     */
    public long getRefCount() {
        return this.refCount.get();
    }

    /**
     * 抽象方法，子类实现具体清理逻辑
     */
    public abstract boolean cleanup(final long currentRef);

    /**
     * 检查是否清理完成
     */
    public boolean isCleanupOver() {
        return this.refCount.get() <= 0 && this.cleanupOver;
    }
}
```

### 6.6 最佳实践总结

**线程池配置**：

- 核心线程数 = CPU核心数 * (1 + 等待时间/计算时间)
- 最大线程数根据业务峰值设置
- 使用有界队列防止OOM
- 选择合适的拒绝策略

**锁选择**：

- 优先考虑无锁设计（CAS、原子类）
- 短持有时间用自旋锁
- 长持有时间用可重入锁
- 高并发写用分段锁

**线程命名**：

- 使用有意义的线程名称
- 便于问题排查和监控
- 格式：`业务模块-功能-序号`
