## 1. TCP/IP协议栈原理

### 1.1 协议栈分层架构

#### 操作系统原理

**TCP/IP协议栈**是Linux内核网络子系统的核心，采用分层架构实现网络通信。数据从应用层向下经过各层协议处理，最终通过网卡发送；接收时反向处理。

**设计思想**：
- 分层解耦，每层专注特定功能
- 协议无关性，支持多种协议共存
- 零拷贝优化，减少数据拷贝次数
- 异步处理，中断与软中断分离

#### 内核数据结构

```c
// socket结构体（include/linux/net.h）
struct socket {
    socket_state state;             // socket状态
    short type;                     // socket类型（SOCK_STREAM等）
    unsigned long flags;            // 标志位
    struct file *file;              // 关联的file结构
    struct sock *sk;                // 内核sock结构
    const struct proto_ops *ops;    // 协议操作函数
    struct socket_wq wq;            // 等待队列
};

// sock结构体（include/net/sock.h）
struct sock {
    struct sock_common __sk_common; // 公共字段
#define sk_state __sk_common.skc_state  // socket状态
#define sk_family __sk_common.skc_family // 协议族
#define sk_protocol __sk_common.skc_protocol // 协议
    struct proto *sk_prot;          // 协议处理函数
    struct net *sk_net;             // 网络命名空间
    
    struct dst_entry *sk_dst_cache; // 路由缓存
    atomic_t sk_refcnt;             // 引用计数
    
    struct sk_buff_head sk_receive_queue;  // 接收队列
    struct sk_buff_head sk_write_queue;    // 发送队列
    
    int sk_rcvbuf;                  // 接收缓冲区大小
    int sk_sndbuf;                  // 发送缓冲区大小
    
    unsigned long sk_flags;         // 标志位
    unsigned long sk_pacing_rate;   // 发送速率
    unsigned long sk_max_pacing_rate; // 最大发送速率
};

// sk_buff网络缓冲区（include/linux/skbuff.h）
struct sk_buff {
    union {
        struct {
            struct sk_buff *next, *prev; // 链表指针
            struct net_device *dev;      // 网络设备
        };
        struct rb_node rbnode;
    };
    
    struct sock *sk;                // 所属socket
    union {
        ktime_t tstamp;             // 时间戳
        u64 netmem_data;
    };
    
    char cb[48];                    // 控制块（各层私有数据）
    
    unsigned int len,               // 数据总长度
                 data_len;          // 分页数据长度
    __u16 mac_len,                  // MAC头长度
          hdr_len;                   // 头部克隆长度
    
    __u32 priority;                 // 优先级
    
    __be16 protocol;                // 协议类型
    __u16 transport_header;         // 传输层头偏移
    __u16 network_header;           // 网络层头偏移
    __u16 mac_header;               // MAC头偏移
    
    sk_buff_data_t tail;            // 数据尾指针
    sk_buff_data_t end;             // 缓冲区尾指针
    unsigned char *head,            // 缓冲区头指针
                  *data;             // 数据头指针
    unsigned int truesize;          // 实际分配大小
    atomic_t users;                 // 用户计数
};
```

**sk_buff数据结构说明**：

| 字段 | 说明 | 用途 |
|------|------|------|
| `head/tail/data/end` | 数据指针 | 管理数据缓冲区，支持头部/尾部添加 |
| `transport_header` | 传输层头偏移 | TCP/UDP头部位置 |
| `network_header` | 网络层头偏移 | IP头部位置 |
| `mac_header` | MAC头偏移 | 以太网帧头位置 |
| `len/data_len` | 数据长度 | 支持分页存储 |
| `sk` | 所属socket | 关联到socket |

## 2. TCP参数优化

### 2.1 操作系统原理

**TCP参数**影响网络性能和可靠性：

| 参数 | 说明 | 内核路径 | 单位 |
|------|------|---------|------|
| SO_BACKLOG | 连接等待队列长度 | `/proc/sys/net/core/somaxconn` | 个 |
| SO_REUSEADDR | 允许重用端口 | 内核socket选项 | - |
| TCP_NODELAY | 禁用Nagle算法 | `/proc/sys/net/ipv4/tcp_low_latency` | - |
| SO_KEEPALIVE | TCP保活探测 | `/proc/sys/net/ipv4/tcp_keepalive_*` | - |
| SO_SNDBUF/SO_RCVBUF | 收发缓冲区大小 | `/proc/sys/net/ipv4/tcp_rmem/wmem` | B |

**Nagle算法**：将小包合并发送，减少网络负载，但增加延迟。

**问题背景**：在低延迟场景下（如RPC调用），Nagle算法会导致消息延迟累积，影响响应速度。禁用Nagle算法（TCP_NODELAY=true）可确保数据立即发送。

### 2.2 RocketMQ实现

[NettyRemotingServer.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingServer.java) 配置TCP参数：

```java
serverBootstrap.group(this.eventLoopGroupBoss, this.eventLoopGroupSelector)
    .channel(useEpoll() ? EpollServerSocketChannel.class : NioServerSocketChannel.class)
    .option(ChannelOption.SO_BACKLOG, 1024)                    // 连接等待队列长度：1024个连接
    .option(ChannelOption.SO_REUSEADDR, true)                  // 允许重用端口
    .childOption(ChannelOption.SO_KEEPALIVE, false)            // 禁用TCP Keepalive，使用应用层心跳
    .childOption(ChannelOption.TCP_NODELAY, true);             // 禁用Nagle算法，降低延迟
```

**参数选择原因**：

| 参数 | 设置 | 原因 |
|------|------|------|
| SO_BACKLOG | 1024 | 支持高并发连接，与内核`/proc/sys/net/core/somaxconn`配合使用 |
| TCP_NODELAY | true | 禁用Nagle算法，降低消息延迟，适合RPC场景 |
| SO_KEEPALIVE | false | 使用应用层心跳替代，检测更及时、可控性更强 |

**扩展TCP参数配置**：

[NettyRemotingServer.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingServer.java#L274-L293) 支持自定义缓冲区配置：

```java
private void addCustomConfig(ServerBootstrap childHandler) {
    // 发送缓冲区大小配置
    if (nettyServerConfig.getServerSocketSndBufSize() > 0) {
        childHandler.childOption(ChannelOption.SO_SNDBUF, 
            nettyServerConfig.getServerSocketSndBufSize());
    }
    // 接收缓冲区大小配置
    if (nettyServerConfig.getServerSocketRcvBufSize() > 0) {
        childHandler.childOption(ChannelOption.SO_RCVBUF, 
            nettyServerConfig.getServerSocketRcvBufSize());
    }
    // 写缓冲区水位线配置（流控）
    if (nettyServerConfig.getWriteBufferLowWaterMark() > 0 
        && nettyServerConfig.getWriteBufferHighWaterMark() > 0) {
        childHandler.childOption(ChannelOption.WRITE_BUFFER_WATER_MARK, 
            new WriteBufferWaterMark(
                nettyServerConfig.getWriteBufferLowWaterMark(),   // 低水位线
                nettyServerConfig.getWriteBufferHighWaterMark())); // 高水位线
    }
    // 内存池化配置
    if (nettyServerConfig.isServerPooledByteBufAllocatorEnable()) {
        childHandler.childOption(ChannelOption.ALLOCATOR, PooledByteBufAllocator.DEFAULT);
    }
}
```

**WRITE_BUFFER_WATER_MARK 说明**：

| 参数 | 说明 | 触发条件 |
|------|------|----------|
| Low Water Mark | 低水位线 | 缓冲区低于此值时，channel变为可写状态 |
| High Water Mark | 高水位线 | 缓冲区高于此值时，channel变为不可写状态 |

## 3. 连接建立流程

### 3.1 操作系统原理

**TCP三次握手**建立连接：

```mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    participant SQ as 半连接队列(SYN队列)
    participant AQ as 全连接队列(Accept队列)

    C->>S: SYN (seq=x)
    Note right of S: SYN-RCVD状态<br/>加入半连接队列
    S->>C: SYN+ACK (seq=y, ack=x+1)
    Note left of C: ESTABLISHED状态
    C->>S: ACK (ack=y+1)
    Note right of S: ESTABLISHED状态<br/>移至全连接队列
```

**核心结论**：TCP通过三次握手建立可靠连接，服务端使用两个队列（半连接队列和全连接队列）管理连接状态，确保高并发场景下的连接稳定性。

**关键概念**：
- **半连接队列(SYN队列)**：存放处于SYN-RCVD状态的连接，等待客户端ACK确认
- **全连接队列(Accept队列)**：存放已完成三次握手的ESTABLISHED连接，等待应用层accept()
- **SYN Flood攻击**：攻击者发送大量SYN但不回复ACK，导致半连接队列溢出

**关键队列**：

| 队列 | 说明 | 内核参数 | 单位 |
|------|------|---------|------|
| 半连接队列(SYN队列) | 存放SYN-RCVD状态的连接 | `/proc/sys/net/ipv4/tcp_max_syn_backlog` | 个 |
| 全连接队列(Accept队列) | 存放ESTABLISHED状态的连接 | `/proc/sys/net/core/somaxconn` | 个 |

**相关内核参数**：

| 参数 | 说明 |
|------|------|
| `/proc/sys/net/ipv4/tcp_max_syn_backlog` | 半连接队列长度 |
| `/proc/sys/net/core/somaxconn` | 全连接队列长度 |
| `/proc/sys/net/ipv4/tcp_syncookies` | SYN Cookie防护 |

### 3.2 RocketMQ服务端实现

```java

    @Override
    public void initChannel(SocketChannel ch) {
        ch.pipeline()
            // 握手处理器（处理TLS检测）
            .addLast(defaultEventExecutorGroup, HANDSHAKE_HANDLER_NAME, handshakeHandler)
            .addLast(defaultEventExecutorGroup,

                new IdleStateHandler(0, 0,                  // 空闲检测：读写均不超时
                    nettyServerConfig.getServerChannelMaxIdleTimeSeconds()), // 默认值：120s
                connectionManageHandler,                     // 连接管理Handler
                serverHandler                                // 业务处理Handler
            );
    }
});
```

```java
static class ChannelWrapper {
    private final ChannelFuture channelFuture;
    // 最后响应时间，用于检测不活跃连接
    // 仅受同步或异步请求影响，单向请求不更新此时间
    private long lastResponseTime;

    public ChannelWrapper(ChannelFuture channelFuture) {
        this.channelFuture = channelFuture;
        this.lastResponseTime = System.currentTimeMillis();  // 初始化为创建时间
    }

    public boolean isOK() {
        // Channel存在且处于活跃状态
        return this.channelFuture.channel() != null 
            && this.channelFuture.channel().isActive();
    }

    public boolean isWritable() {
        // Channel是否可写（用于流控）
        return this.channelFuture.channel().isWritable();
    }

    public void updateLastResponseTime() {
        this.lastResponseTime = System.currentTimeMillis();  // 更新最后响应时间
    }
}
```

## 4. 空闲连接检测

### 4.1 操作系统原理

**空闲连接检测**防止资源泄漏：

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| TCP Keepalive | 内核定时发送探测包 | 简单，但间隔长（默认2小时） |
| 应用层心跳 | 应用自定义心跳协议 | 灵活，可快速检测 |

**TCP Keepalive参数**：

```bash
/proc/sys/net/ipv4/tcp_keepalive_time   # 首次探测时间，默认值：7200s (2小时)
/proc/sys/net/ipv4/tcp_keepalive_intvl  # 探测间隔，默认值：75s
/proc/sys/net/ipv4/tcp_keepalive_probes # 探测次数，默认值：9次
```

**参数详细说明**：

| 参数 | 默认值 | 单位 | 说明 |
|------|-------|------|------|
| tcp_keepalive_time | 7200 | s | 连接空闲多久后开始发送保活探测包 |
| tcp_keepalive_intvl | 75 | s | 保活探测包的发送间隔 |
| tcp_keepalive_probes | 9 | 次 | 探测失败多少次后认为连接断开 |

**问题背景**：TCP Keepalive 默认2小时才触发首次探测，对于需要快速检测连接断开的场景不适用。RocketMQ 使用应用层心跳机制，可在秒级检测到连接异常。

```java
protected void scanChannelTablesOfNameServer() {
    for (String addr : this.channelTables.keySet()) {
        ChannelWrapper channelWrapper = this.channelTables.get(addr);
        if (channelWrapper == null) {
            continue;
        }
        // 检测超过channelNotActiveInterval未响应的连接
        if ((System.currentTimeMillis() - channelWrapper.getLastResponseTime()) 
            > this.nettyClientConfig.getChannelNotActiveInterval()) {  // 默认值：60000ms (60s)
            log.warn("[SCAN] No response after {} from name server {}, so close it!", 
                channelWrapper.getLastResponseTime(), addr);
            closeChannel(addr, channelWrapper.getChannel());
        }
    }
}
```

### 5.1 Channel生命周期

**Channel生命周期**：连接建立 -> 数据传输 -> 连接关闭

**Channel生命周期状态图**：

### 5.3 NettyEventExecutor事件处理

[NettyRemotingAbstract.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingAbstract.java#L557-L610) 实现事件处理：

```java
class NettyEventExecutor extends ServiceThread {
    // 事件队列，最大容量10000个事件
    private final LinkedBlockingQueue<NettyEvent> eventQueue = new LinkedBlockingQueue<>();

    public void putNettyEvent(final NettyEvent event) {
        int currentSize = this.eventQueue.size();
        int maxSize = 10000;  // 最大事件数量：10000个
        if (currentSize <= maxSize) {
            this.eventQueue.add(event);
        } else {
            // 队列已满，丢弃事件并打印警告日志
            log.warn("event queue size [{}] over the limit [{}], so drop this event {}", 
                currentSize, maxSize, event.toString());
        }
    }

    @Override
    public void run() {
        log.info(this.getServiceName() + " service started");

        final ChannelEventListener listener = NettyRemotingAbstract.this.getChannelEventListener();

        while (!this.isStopped()) {
            try {
                // 每3秒轮询一次事件队列
                NettyEvent event = this.eventQueue.poll(3000, TimeUnit.MILLISECONDS);
                if (event != null && listener != null) {
                    switch (event.getType()) {
                        case IDLE:
                            listener.onChannelIdle(event.getRemoteAddr(), event.getChannel());
                            break;
                        case CLOSE:
                            listener.onChannelClose(event.getRemoteAddr(), event.getChannel());
                            break;
                        case CONNECT:
                            listener.onChannelConnect(event.getRemoteAddr(), event.getChannel());
                            break;
                        case EXCEPTION:
                            listener.onChannelException(event.getRemoteAddr(), event.getChannel());
                            break;
                        default:
                            break;
                    }
                }
            } catch (Exception e) {
                log.warn(this.getServiceName() + " service has exception. ", e);
            }
        }

        log.info(this.getServiceName() + " service end");
    }
}
```

### 6.2 同步请求实现

**同步请求超时机制**：同步请求需要等待响应，超时机制防止无限等待：

```mermaid
sequenceDiagram
    participant C as 客户端
    participant T as 超时计时器
    participant S as 服务端
    
    C->>T: 启动超时计时
    C->>S: 发送请求
    Note over C,T: 等待响应中...
    
    alt 正常响应
        S->>C: 返回响应
        C->>T: 取消计时
        Note over C: 处理响应
    else 超时未响应
        T->>C: 超时触发
        C->>C: 抛出TimeoutException
        Note over C: 清理资源
    end
```

**核心结论**：同步请求通过超时机制避免无限等待，确保系统资源及时释放，防止线程阻塞导致系统性能下降。

[NettyRemotingAbstract.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingAbstract.java#L407-L444) 实现同步请求：

```java
public RemotingCommand invokeSyncImpl(final Channel channel, final RemotingCommand request,
    final long timeoutMillis)
    throws InterruptedException, RemotingSendRequestException, RemotingTimeoutException {
    // 获取请求ID（opaque用于匹配请求和响应）
    final int opaque = request.getOpaque();

    try {
        // 创建响应Future，用于等待响应
        final ResponseFuture responseFuture = new ResponseFuture(
            channel, opaque, timeoutMillis, null, null);
        // 存入响应表，等待响应时根据opaque查找
        this.responseTable.put(opaque, responseFuture);
        final SocketAddress addr = channel.remoteAddress();
        
        // 发送请求，添加监听器处理发送结果
        channel.writeAndFlush(request).addListener((ChannelFutureListener) f -> {
            if (f.isSuccess()) {
                // 发送成功，设置标志位
                responseFuture.setSendRequestOK(true);
                return;
            }
            // 发送失败，清理资源
            responseFuture.setSendRequestOK(false);
            responseTable.remove(opaque);
            responseFuture.setCause(f.cause());
            responseFuture.putResponse(null);
            log.warn("Failed to write a request command to {}, caused by underlying I/O operation failure", addr);
        });

        // 阻塞等待响应
        RemotingCommand responseCommand = responseFuture.waitResponse(timeoutMillis);
        if (null == responseCommand) {
            if (responseFuture.isSendRequestOK()) {
                // 发送成功但超时未收到响应
                throw new RemotingTimeoutException(
                    RemotingHelper.parseSocketAddressAddr(addr), timeoutMillis,
                    responseFuture.getCause());
            } else {
                // 发送失败
                throw new RemotingSendRequestException(
                    RemotingHelper.parseSocketAddressAddr(addr), responseFuture.getCause());
            }
        }

        return responseCommand;
    } finally {
        // 清理响应表
        this.responseTable.remove(opaque);
    }
}
```

**核心结论**：同步请求通过ResponseFuture和CountDownLatch实现阻塞等待，opaque标识符用于匹配请求和响应，确保响应正确返回给调用方。

**关键概念**：
- **opaque**：请求唯一标识符，用于匹配请求和响应，每次请求自增
- **ResponseFuture**：封装响应等待逻辑，包含CountDownLatch用于同步阻塞
- **responseTable**：ConcurrentHashMap，初始容量256，存储opaque到ResponseFuture的映射

**分步详解**：

| 步骤 | 操作 | 类型 | 说明 |
|------|------|------|------|
| 1 | 创建Future | 初始化 | 创建ResponseFuture对象，设置超时时间 |
| 2 | 存入响应表 | 注册 | 将opaque和Future存入responseTable |
| 3 | 发送请求 | 网络 | 异步发送请求到Channel |
| 4 | 等待响应 | 阻塞 | CountDownLatch.await()阻塞当前线程 |
| 5 | 处理响应 | 回调 | 收到响应后唤醒等待线程 |
| 6 | 清理资源 | 释放 | 从responseTable移除Future |

### 6.3 异步请求实现

[NettyRemotingAbstract.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingAbstract.java#L446-L490) 实现异步请求：

```java
public void invokeAsyncImpl(final Channel channel, final RemotingCommand request, 
    final long timeoutMillis, final InvokeCallback invokeCallback)
    throws InterruptedException, RemotingTooMuchRequestException, RemotingTimeoutException, 
           RemotingSendRequestException {
    long beginStartTime = System.currentTimeMillis();
    final int opaque = request.getOpaque();
    
    // 尝试获取异步信号量（限流保护）
    boolean acquired = this.semaphoreAsync.tryAcquire(timeoutMillis, TimeUnit.MILLISECONDS);
    if (acquired) {
        // 信号量释放器（确保只释放一次）
        final SemaphoreReleaseOnlyOnce once = new SemaphoreReleaseOnlyOnce(this.semaphoreAsync);
        long costTime = System.currentTimeMillis() - beginStartTime;
        if (timeoutMillis < costTime) {
            once.release();
            throw new RemotingTimeoutException("invokeAsyncImpl call timeout");
        }

        // 创建响应Future
        final ResponseFuture responseFuture = new ResponseFuture(
            channel, opaque, timeoutMillis - costTime, invokeCallback, once);
        this.responseTable.put(opaque, responseFuture);
        try {
            channel.writeAndFlush(request).addListener((ChannelFutureListener) f -> {
                if (f.isSuccess()) {
                    responseFuture.setSendRequestOK(true);
                    return;
                }
                // 发送失败，触发回调
                requestFail(opaque);
                log.warn("send a request command to channel <{}> failed.", 
                    RemotingHelper.parseChannelRemoteAddr(channel));
            });
        } catch (Exception e) {
            responseFuture.release();
            log.warn("send a request command to channel <" + 
                RemotingHelper.parseChannelRemoteAddr(channel) + "> Exception", e);
            throw new RemotingSendRequestException(
                RemotingHelper.parseChannelRemoteAddr(channel), e);
        }
    } else {
        // 获取信号量失败（请求过多）
        if (timeoutMillis <= 0) {
            throw new RemotingTooMuchRequestException("invokeAsyncImpl invoke too fast");
        } else {
            String info = String.format(
                "invokeAsyncImpl tryAcquire semaphore timeout, %dms, waiting thread nums: %d semaphoreAsyncValue: %d",
                timeoutMillis, this.semaphoreAsync.getQueueLength(), 
                this.semaphoreAsync.availablePermits());
            log.warn(info);
            throw new RemotingTimeoutException(info);
        }
    }
}
```

- 信号量获取失败会导致请求被拒绝，需要合理设置信号量大小

```java
public void scanResponseTable() {
    final List<ResponseFuture> rfList = new LinkedList<>();
    Iterator<Entry<Integer, ResponseFuture>> it = this.responseTable.entrySet().iterator();
    while (it.hasNext()) {
        Entry<Integer, ResponseFuture> next = it.next();
        ResponseFuture rep = next.getValue();

        // 判断是否超时（超时时间 + 1秒容错）
        if ((rep.getBeginTimestamp() + rep.getTimeoutMillis() + 1000) <= System.currentTimeMillis()) {
            rep.release();      // 释放信号量
            it.remove();        // 从响应表中移除
            rfList.add(rep);
            log.warn("remove timeout request, " + rep);
        }
    }

    // 执行超时回调
    for (ResponseFuture rf : rfList) {
        try {
            executeInvokeCallback(rf);
        } catch (Throwable e) {
            log.warn("scanResponseTable, operationComplete Exception", e);
        }
    }
}
```

#### 7.5.4 SemaphoreReleaseOnlyOnce详解

[SemaphoreReleaseOnlyOnce.java](../remoting/src/main/java/org/apache/rocketmq/remoting/common/SemaphoreReleaseOnlyOnce.java) 确保信号量只释放一次：

```java
public class SemaphoreReleaseOnlyOnce {
    private final AtomicBoolean released = new AtomicBoolean(false);  // 释放标志，初始为false
    private final Semaphore semaphore;  // 关联的信号量

    public SemaphoreReleaseOnlyOnce(Semaphore semaphore) {
        this.semaphore = semaphore;
    }

    public void release() {
        if (this.semaphore != null) {
            // 使用CAS确保只释放一次，避免信号量计数错误
            if (this.released.compareAndSet(false, true)) {
                this.semaphore.release();
            }
        }
    }
}
```

**问题背景**：在异步请求处理中，可能存在多个地方触发信号量释放（如正常响应、超时扫描、请求失败等），如果多次释放信号量会导致信号量计数错误，进而影响限流功能。

**解决方案**：使用原子布尔值确保信号量只释放一次，即使多次调用release()方法，也只会真正释放一次信号量。

**使用示例**：

```java
// 创建信号量释放器
final SemaphoreReleaseOnlyOnce once = new SemaphoreReleaseOnlyOnce(semaphoreAsync);

// 在响应处理时释放
once.release();  // 第一次调用，信号量释放成功

// 在超时扫描时释放
once.release();  // 第二次调用，不会重复释放信号量
```

## 8. RPC Hook机制

### 8.1 Hook接口

[RPCHook.java](../remoting/src/main/java/org/apache/rocketmq/remoting/RPCHook.java) 定义RPC钩子接口：

```java
public interface RPCHook {
    /**
     * 请求前置钩子，在请求处理前执行
     * @param remoteAddr 远程地址
     * @param request 请求命令
     * @throws Exception 抛出异常可中断请求处理

    void doBeforeRequest(final String remoteAddr, final RemotingCommand request);

    /**
     * 响应后置钩子，在响应返回前执行
     * @param remoteAddr 远程地址
     * @param request 请求命令
     * @param response 响应命令
     * @throws Exception 抛出异常可中断响应返回
     */
    void doAfterResponse(final String remoteAddr, final RemotingCommand request,
                         final RemotingCommand response);
}
```

[NettyRemotingAbstract.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingAbstract.java#L165-L179) 提供RPC钩子调用：

```java
protected void doBeforeRpcHooks(String addr, RemotingCommand request) {
    if (rpcHooks.size() > 0) {
        for (RPCHook rpcHook : rpcHooks) {
            rpcHook.doBeforeRequest(addr, request);  // 按顺序执行前置钩子
        }
    }
}

public void doAfterRpcHooks(String addr, RemotingCommand request, RemotingCommand response) {
    if (rpcHooks.size() > 0) {
        for (RPCHook rpcHook : rpcHooks) {
            rpcHook.doAfterResponse(addr, request, response);  // 按顺序执行后置钩子
        }
    }
}
```

**Hook注册方法**：

[NettyRemotingAbstract.java](../remoting/src/main/java/org/apache/rocketmq/remoting/netty/NettyRemotingAbstract.java#L360-L368) 提供Hook注册：

```java

    }
```


**关键概念**：
- **doBeforeRequest**：请求前置钩子，可用于权限验证、参数校验
- **doAfterResponse**：响应后置钩子，可用于日志记录、性能统计
- **Hook链**：支持注册多个Hook，按顺序执行

**应用场景**：

| 场景 | Hook类型 | 说明 |
|------|---------|------|
| 权限验证 | doBeforeRequest | 检查用户权限，拒绝非法请求 |
| 流量控制 | doBeforeRequest | 实现请求限流、熔断 |
| 日志记录 | doAfterResponse | 记录请求响应日志 |
| 性能监控 | doBeforeRequest + doAfterResponse | 统计请求耗时 |
| 链路追踪 | doBeforeRequest | 注入TraceID，实现分布式追踪 |
